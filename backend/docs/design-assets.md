# Файлы дизайна: API и постоянное хранение

Состояние на18 октября2026: реализованы SQL-слой, upload/content/import API,
worker, атомарные привязки в cart/order и frontend upload/import. Приватный
показ исключён из Next Image cache. Локальный Nginx logging gate проверяет
восемь конфигураций. Метрика изолирована от DOM приложения, её локальный
standalone/Chromium gate прошёл. Публичный proxy/CDN, настройки счётчика
и реальные отчёты ещё требуют проверки.

## Проблема текущего потока

Конструктор допускает изображения до8МиБ и передаёт data URL в customization.
Вход cart/order ограничивает customization64КиБ. Сохранённые проекты получают
временные presigned URL. Обычная строка URL внутри JSON заказа не удерживает
MediaObject: очистка проекта или аккаунта может удалить изображение заказа.

## Новая схема

`design_assets.media_object_id` с FK RESTRICT удерживает MediaObject.
`cart_design_assets` и `order_design_assets` связывают asset с корзиной/заказом.
Существующая проверка media references читает FK из ORM metadata и видит эту
связь. Строка JSON продолжит хранить параметры дизайна; FK удерживает файл.

Случайный capability token создаётся из32 криптографических случайных байтов.
В БД только SHA256 digest. Ссылка `/api/design-media/{token}/content` даёт
доступ только к изображению. Её нельзя логировать целиком, включать в аналитику
или использовать как ключ доступа к аккаунту. Backend access event сохраняет
шаблон маршрута; Nginx-конфигурации используют категории без URL, см.
`deploy/nginx/README.md`. Метрика получает только постоянные публичные категории
через opaque sandbox, см. `frontend/docs/analytics-privacy.md`. Активацию на
внешнем reverse proxy/CDN и реальные отчёты ещё нужно проверить перед публикацией.
Сам API не раскрывает SQL/storage причины отказа.

## HTTP-контракт

- `POST /api/design-media`: raw bytes изображения, без multipart и JSON/base64.
  Stream ограничен до8МиБ до Pillow и SQL. Содержимое действительно декодируется,
  нормализуется в lossless WebP с alpha, metadata удаляются. Ограничения пикселей,
  стороны и числа кадров общие с private project images. Поддельный MIME заголовка
  не заменяет проверку содержимого. Ограничение нормализованного файла также8МиБ.
- Ответ201: `url`, `content_type`, `size_bytes`, `expires_at`. Новый asset
  первоначально живёт7 дней; последующая FK-привязка продлевает удержание.
  Гость может загрузить файл без identity, user ID и имя исходного файла не нужны.
  Сохраняются durable pending metadata, затем PUT под SQL lock, ready+asset
  в одной транзакции. Прерывание оставляет pending/failed для worker.
- `POST /api/design-media/import`: `{media_ids: [id, ...]}`, максимум102 ID,
  действующая identity-сессия. Активный владелец и private ready project media
  блокируются перед созданием ссылок. Чужие, CRM/public и неизвестные файлы
  не принимаются. Вся пачка атомарна; дубликаты ID не создают повторных ссылок.
- `GET /api/design-media/{token}/content`: проверяет TTL/удержание, status,
  private MinIO bucket и MIME, затем читает ограниченные байты указанной версии
  и проверяет размер/SHA256. Не делает presigned redirect. Ответ имеет
  `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: no-referrer`. Отсутствующий/истёкший token или объект —404,
  неподдерживаемое изображение —415, превышение upload —413, storage/целостность —503.

Маршруты включены при CARTS_V2_ENABLED. Импорт дополнительно требует
IDENTITY_API_ENABLED; при отключённой identity не зарегистрирован. Состояние
бизнес-данных остаётся в PostgreSQL, байты — в приватном MinIO.

## Транзакции и очистка

`lock_available` сначала блокирует assets по ID, затем отдельным свежим пакетным
запросом блокирует MediaObject по его ID и проверяет удержание. Раздельный
порядок нужен потому, что несколько capabilities могут ссылаться на один файл:
два запроса с разными capabilities не должны брать общие файлы в обратном порядке.
Проверяются ready/private/MinIO/bucket, растровый MIME и TTL. Ошибка не раскрывает
причину недоступности файла. Предел10300 уникальных файлов соответствует100
строкам с максимум100 размещениями,2 изображениями модели и миниатюрой на строку.

Сервис корзины держит lock корзины и вызывает `lock_available` перед
`replace_cart_links` в той же транзакции. Привязка продлевает TTL asset до TTL
корзины; замена/очистка удаляет старые связи. Точный повтор operation ID возвращает
предыдущий ответ, не продлевая TTL и не переписывая FK. Offline импорт старой
корзины также учитывает новые capability URL, если они в ней присутствуют.
Сервис заказа блокирует проверенные assets и вызывает `retain_order` атомарно
с принятием заказа до резерва остатков. Она создаёт FK и устанавливает expires_at=NULL:
такой файл не участвует
в сканировании истёкших assets. Удаление аккаунта сохраняет бухгалтерский
заказ. Будущее явное удаление заказа должно отдельно согласовать его файлы:
автоматического снятия бессрочного удержания сейчас нет.

Извлечение capabilities читает только image строки, modelImages.front/back
и decorations[].image. Комментарии и произвольные вложенные JSON-поля не
удерживают файлы. Принимается точный относительный content URL; его абсолютные,
экранированные и другие неканонические варианты отклоняются, чтобы не сохранить
рабочую браузерную ссылку без FK. Неизвестные/истёкшие capabilities дают409 с кодом
`cart_design_unavailable` или `checkout_design_unavailable`, без частичной записи.
После такого отказа frontend освобождает операцию оформления и предлагает
повторную загрузку. Это не конфликт ревизии корзины и не неопределённая оплата.

Ошибка резерва откатывает заказ, FK и бессрочное удержание вместе. Платёжный
вызов происходит после принятия заказа: неопределённый ответ провайдера сохраняет
заказ и его файлы. Точный повтор checkout использует прежний заказ и одну оплату.

`prune_expired` ограничен1–1000 записями, использует SKIP LOCKED и свежую
проверку удержания после блокировок. Удаляет лишь метаданные истёкших assets
и связи старых корзин. MediaObject и файл остаются для следующего устойчивого
шага физической очистки. Worker `scripts.reconcile_project_media` запускает
prune перед поиском файлов. Namespace designs/ включён в тот же механизм
tombstone/retry и удаления всех S3-версий. Dry-run только выбирает записи;
не снимает FK, не меняет expiry и не пишет в S3. Batch дополнительно считает
`design_media` — число файлов с истёкшими asset ссылками, не количество строк.
Перед изменением файлов worker блокирует MediaObject по ID тем же порядком,
что корзина и checkout. Пакет25 файлов: lookup2 SQL, prune6 SQL, без N+1.

## Frontend: подготовка до изменения корзины

`frontend/lib/constructor/cartPreparation.ts` собирает уникальные изображения
копии дизайна. Уже подтверждённые ссылки каталога и DesignAsset сохраняются;
private project media импортируются по ID одним запросом; локальные растровые
данные загружаются отдельно от JSON. После подтверждения всех файлов ссылки
заменяются, проверяется лимит customization64КиБ и только затем меняется корзина.
Произвольные URL не превращаются в загрузку. Снимок редактора сохраняет исходные
ссылки и геометрию. Замена строк не меняет цену, рост человека или замеры изделия.

`useConstructorCartPreparation` связывает операцию с lifetime редактора и входа
в аккаунт. Одна операция, общий deadline120s, явная отмена, проверка сессии после
каждого await. Ошибка оставляет корзину нетронутой; явный retry переиспользует
успешные файлы с запасом TTL не меньше минуты. Уход со страницы и смена аккаунта
сбрасывают кэш и отменяют запрос. При обновлении строки сохраняется количество;
удалённая или изменённая за время загрузки строка не перезаписывается.

ProjectEditor отдаёт подтверждённые public URLs и private media IDs раздельно.
Покупка проекта не зависит от скачивания его временной S3-ссылки. Обратный путь
«дизайн корзины → сохранить проект» читает только точную capability-ссылку,
ограничивает поток8МиБ и загружает копию в собственное private media аккаунта.
Это сохраняет существующие проверки прав проекта без общей анонимной media FK.

## Приватные изображения и Next Image

Ответ content API с `private, no-store` нельзя передавать оптимизатору Next:
он создаёт собственный публичный файл. На копии standalone-сборки воспроизведено:
исходный `no-store` превратился в `public, max-age=14400, must-revalidate`.
Это поведение установленного Next16.3.0, а не предположение по документации.

`frontend/lib/media/imagePolicy.ts` задаёт разрешённые публичные пути без query:
статические картинки, каталожные uploads и известные папки public. API,
подписанные URL и storage исключены. Next `images.localPatterns` ограничивает
оптимизатор этим списком. Proxy дополнительно отклоняет неподходящий источник
до оптимизатора, включая закодированные разделители и вложенное кодирование:
400 с `private, no-store`, без отражения URL в ответе.

`CustomerMediaImage` сохраняет оптимизацию публичного каталога, а приватные,
подписанные и неизвестные источники открывает напрямую с `no-referrer`.
Подключён в корзине, деталях товара, checkout, истории заказов и preview проекта.
Прямая загрузка продолжает использовать ограничения и заголовки исходного API.
Изменение не отключает кеш всех публичных изображений.

528 frontend tests, lint и production build прошли. Отдельный runtime тест
скопированного standalone-пакета подтвердил: приватный запрос и алиасы получают
400, upstream не вызван, токен не попадает в логи Next. Публичная картинка
по-прежнему оптимизируется с200. Upstream в этом сравнении синтетический.
Логи Nginx/CDN и поведение сторонней аналитики требуют отдельной проверки:
эта защита оптимизатора не подтверждает приватность всей опубликованной системы.
