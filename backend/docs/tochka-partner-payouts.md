# Выплаты партнёрам через Точка Банк

Интеграция выключена по умолчанию. Поддержаны рублёвые выплаты на расчётный счёт ИП
из существующего партнёрского баланса. YooKassa для оплаты заказов не меняется.
Телефон, карта и СБП не используются как реквизиты этой выплаты.

## Как проходит выплата

1. Партнёр сохраняет реквизиты ИП и создаёт заявку через существующий
   `POST /api/partner/payouts`. Сумма резервируется из созревших начислений.
2. Администратор с `partners.manage` одобряет заявку через существующий
   `PATCH /api/admin/partners/payouts/{id}` (`status: approved`).
3. Администратор вызывает `POST /api/admin/partners/payouts/{id}/bank-payment`:

   ```json
   {"payment_purpose": "Вознаграждение по договору №… за период … . Без НДС."}
   ```

   Это **пример**, основание и формулировку НДС заполняет бухгалтер по реальному
   договору. Backend не выдумывает договор/ставку. К назначению добавляется
   `[GB-PAYOUT-{id}]` для сверки. Сумму и получателя API берёт из заявки и
   зашифрованных реквизитов, а не из тела запроса администратора.
4. Backend создаёт платёжку методом Точки `POST /payment/v1.0/for-sign`.
   Ответ администратору содержит `signing_url` — ссылку на подписание в Точке.
   **Уполномоченный сотрудник подписывает платёж в интернет-банке**. Backend
   не вводит SMS-коды, не подписывает платежи и не хранит ключ электронной подписи.
5. Фоновая задача проверяет `GET /payment/v1.0/status/{requestId}`. Можно запросить
   проверку вручную: `POST /api/admin/partners/payouts/{id}/bank-payment/refresh`.
   Только подтверждённый `Paid` меняет выплату на `paid`.

| Статус Точки | Состояние операции | Заявка / баланс |
| --- | --- | --- |
| WaitingForCreate | awaiting_signature | approved, сумма зарезервирована |
| Created | processing | approved, это ещё не выплата |
| Paid | paid | paid, сумма учтена как выплаченная |
| Canceled / Rejected | canceled / rejected | резерв освобождается |
| Таймаут, 5xx, невалидный ответ создания | unknown | резерв сохраняется, повтор POST запрещён |

Чтение операции: `GET /api/admin/partners/payouts/{id}/bank-payment`.
Партнёр видит только свою операцию через `GET /api/partner/payouts/{id}/bank-payment`:
без ссылки на подписание, банковского requestId, внутренних ошибок и реквизитов.
Чтение истории доступно и при выключенной интеграции.

## Конфигурация

До запуска приложения применить миграцию `20260908_0033` (`alembic upgrade head`).
Нужны существующие `DATABASE_ENABLED`, `IDENTITY_API_ENABLED`,
`PARTNER_PROGRAM_ENABLED`, секрет атрибуции, ключ шифрования реквизитов и
актуальные migration fingerprints проекта.

| Переменная | Значение |
| --- | --- |
| TOCHKA_PAYOUTS_ENABLED | false по умолчанию; true включает создание и опрос |
| TOCHKA_ENVIRONMENT | sandbox (по умолчанию) или production |
| TOCHKA_API_TOKEN | JWT своего предприятия; только приватный env/secret store |
| TOCHKA_ACCOUNT_CODE | 20 цифр счёта плательщика, только для production |
| TOCHKA_BANK_CODE | БИК банка плательщика; по умолчанию 044525104, сверить со счётом |
| TOCHKA_CA_FILE | необязательный путь к CA bundle внутри контейнера |
| TOCHKA_TIMEOUT_SECONDS | 15 по умолчанию, 1–60 |
| TOCHKA_POLL_SECONDS | 60 по умолчанию, 30–3600 |

Песочница использует только публичный тестовый JWT `sandbox.jwt.token` и
официальный тестовый счёт. Она должна работать на отдельной тестовой базе,
не на копии актуальных финансовых обязательств. При `APP_ENV=production`
песочницу включить нельзя. Реальный банк запрещён в dev/test/staging.
Никогда не переключать окружение уже созданных операций: сверка таких операций
блокируется. Для production нужны отдельная база и её реальные заявки.

JWT создаётся в банке для собственной компании. По текущей спецификации:
создание требует `CreatePaymentForSign`; метод статуса перечисляет
`CreatePaymentForSign` и `CreatePaymentOrder`. Права и счёт сверить при выдаче
токена. OAuth для доступа к счетам чужих компаний и API Pro для автоматического
подписания реестров в этот этап не входят.

### TLS

Точка использует цепочку Russian Trusted CA. Публичный корневой сертификат
`app/integrations/tochka/russian_trusted_root_ca.pem` загружен с официального
адреса `https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt`.
Он добавляется **только в SSLContext клиента Точки**, без изменения доверия ОС
или других HTTP-клиентов. Проверка имени хоста/цепочки обязательна;
`verify=False` и `curl -k` не нужны. При ротации CA обновить bundle/TOCHKA_CA_FILE.
SHA-256 текущего публичного сертификата:
`D26D2D0231B7C39F92CC738512BA54103519E4405D68B5BD703E9788CA8ECF31`.

## Надёжность и ручная сверка

У `for-sign` в текущей OpenAPI нет документированного Idempotency-Key.
Поэтому одна заявка имеет ровно одну банковскую операцию (UNIQUE payout_id),
записанную в БД **до** отправки HTTP POST. Конкурирующие запросы сериализуются
блокировкой заявки. Повтор с теми же параметрами возвращает сохранённую операцию;
с другим назначением — 409. Автоматических повторов отправки нет.

Если процесс упал после записи операции или банк принял POST, но ответ потерялся,
состояние становится `unknown`. Это осознанная остановка ради защиты от дублей.
Не создавать заменяющую заявку и не снимать резерв по одному таймауту.
Сотрудник сверяет интернет-банк/выписку по маркеру GB-PAYOUT, сумме, получателю,
дате и назначению. Дальнейшее восстановление требует отдельного проверенного
операторского действия с банковскими доказательствами; публичного endpoint для
произвольного присвоения `paid` или привязки чужого requestId нет.

HTTP 400/401/403 при создании считаются однозначным отказом: заявка отклоняется,
резерв освобождается. Исправление причины и новая заявка — отдельное решение
администратора. HTTP 429, 5xx, редиректы, повреждённые ответы — неопределённый
исход, резерв сохраняется. Ошибка GET статуса никогда не освобождает резерв.

Ручной `PATCH` статуса запрещён для всех заявок с банковской операцией, даже
если интеграция выключена. При включённой Точке ручная отметка `paid` запрещена
и для ещё не отправленных заявок. Изменение реквизитов партнёра после отправки
не меняет платёжку: её снимок зашифрован AES-GCM, хранится отдельно и привязан
к партнёру. В событиях сохраняются только состояния и безопасные коды ошибок.

Не редактировать созданный платёж в банке: документация предупреждает, что после
редактирования API может оставлять статус `Created`. Нужна ручная сверка,
автоматически признавать его оплаченным нельзя. Опрос не отправляет новые
платежи и не повторяет подпись. Существующий модуль баланса учитывает возвраты;
перед отправкой повторно проверяется покрытие всех резервов начислениями.

## Проверка

`make PYTHON=/path/to/python check` — unit/HTTP-contract/ledger tests, Ruff,
генерация PostgreSQL SQL upgrade/downgrade. Тесты не используют реальный банк.
Отдельный smoke-тест песочницы выполняется только с синтетическими реквизитами;
песочница возвращает фикстуры и не доказывает фактическое движение денег.
Production включать только после выдачи ключа, проверки прав, реквизитов,
договоров и отдельной согласованной проверки реального платежа.
