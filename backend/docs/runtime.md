# Запуск и диагностика backend

Работа над новым релизом продолжается. Этот документ описывает уже реализованную
основу запуска; полный список оставшейся работы — в `docs/release-refactoring.md`
от корня проекта. Production в рамках этих изменений не переключался.

## Точка входа и ресурсы

ASGI-приложение — `app.main:app`. Импорт собирает приложение и настраивает
логирование. Он не импортирует прежний `backend/main.py`, не создаёт SQLite,
каталог uploads или таблицы, не открывает соединения.

`app/factory.py` собирает сервисы и маршруты. `app/runtime.py` управляет ресурсами:

1. Запускает DatabaseManager и сверяет PostgreSQL revision с Alembic head
   текущего релиза. Отсутствующая или отставшая схема останавливает startup.
2. Запускает storage и HTTP transports интеграций.
3. Запускает необходимые фоновые задачи.
4. При остановке отменяет и дожидается задач, затем закрывает ресурсы в обратном
   порядке. Освобождение регистрируется до startup, поэтому действует и при
   частичной инициализации. Ошибка закрытия одного ресурса не пропускает другие.

Схему изменяет отдельная команда Alembic, а не запуск API. Из каталога backend:

```sh
rtk proxy .venv/bin/python -m alembic upgrade head
rtk proxy .venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Команды используют текущую конфигурацию окружения; для проверки нужна отдельная
локальная БД. Не следует применять команды проверок к production.

Новый entrypoint больше не подставляет legacy API при выключенном модуле — его
маршрут отсутствует. Каталог, корзины, identity и чтение заказов запускаются на
мигрированной PostgreSQL без fingerprints старого импорта. Проверки импорта
остались отдельными инструментами и не выполняются при запуске API.
В шаблонах окружения и локальном compose основные новые API включены; секреты
JWT/OTP/outbox нужно задать отдельно. Платежи и другие внешние операции включаются
с собственной конфигурацией, автоматически они не активируются.

История заказов в identity всегда читается из основной БД, в том числе при
выключенном отдельном маршруте ORDER_READS_ENABLED. SQLite order bridge и его
reader удалены. Импортированные заказы сохраняют защищённую привязку к владельцу
и после смены email; совпадение телефона не предоставляет доступ к заказу.

Factory и runtime больше не принимают `legacy_app` и не монтируют прежнее
приложение. Локальный и серверный compose не создают `legacy-init` и не монтируют
SQLite/uploads; Dockerfile также не создаёт эти каталоги. Backup архивирует
основные PostgreSQL/MinIO и, при наличии в предыдущем контейнере, старые данные.
Существующие volumes не удаляются. На изолированных native PostgreSQL17/MinIO
проверен restore синтетического комплекта:106 таблиц,10 000 заказов,3 объекта,
публичные/частные права и запуск API. Backup теперь открывает окно обслуживания:
общий замок с deploy, остановка приложений/обработчиков и затем MinIO перед
чтением, возврат ранее работающих сервисов при успехе и обрабатываемой ошибке.
Старые mounted данные читаются read-only helper без запуска API.
Полноценный контейнерный выпуск, изоляция внешних писателей и restore на
production-объёме ещё не проверены;
подробности и инструмент проверки — в `deploy/README.md`.

Старые `backend/main.py`, корневой `docker-compose.yml`, SQLAdmin и отдельные
корневые CDEK/payment/email/image wrappers удалены. Действующие Compose:
`docker-compose.local.yml` и `deploy/docker-compose.server.yml`. SMTP находится
в `app/integrations/smtp.py`, обработка изображений — в `app/modules/media/images.py`.
Письма по-прежнему проходят через transactional outbox и retry worker; SMTP
пишет только тип ошибки, без сырого ответа провайдера. Runtime не зависит от
SQLAdmin, YooKassa SDK или aiosqlite; SQLite async driver нужен только dev-тестам.

GET/PUT `/api/settings` удалены вместе с прежним редактором лендинга.
`/api/options` и отдельный PUT `/api/variants/{id}` также удалены вместе со
старой формой товара. Общий редактор сохраняет товар и варианты одной операцией.
Размеры и допустимые ткани читаются из производственных таблиц через
постраничный `/api/catalog-editor` (staff) или production `editor-options`.
Прежний отдельный справочник свободных названий цветов/размеров не используется.
Миграция0070 вводит версию товара. Оба PUT требуют `expected_version`, проверяют
её под блокировкой строки и возвращают409 с `catalog_product_version_conflict`
для устаревшей формы без изменения товара. Подтверждённый расход физического
запаса и первая привязка CRM модели тоже меняют версию. Нужен согласованный
выпуск frontend/backend; старый клиент без версии получает422.
Исторический импорт settings/options расположен в `catalog/migration/content.py`
и запускается только явной командой. Архивные документы и fingerprints сохранены.

## Логи

API и шесть существующих worker entrypoints используют одинаковую конфигурацию:
одна JSON-запись на строку stdout. `LOG_LEVEL` принимает DEBUG, INFO, WARNING,
ERROR или CRITICAL; по умолчанию INFO. Factory не меняет глобальное логирование,
чтобы приложения и тесты могли собираться независимо.

Основные поля:

| Поле | Значение |
| --- | --- |
| timestamp | Время UTC в ISO 8601 |
| level, logger, message | Уровень, источник и сообщение |
| event | Тип события: http.request.completed, runtime.starting/ready/failed/stopped, runtime.task.failed |
| request_id | Связь HTTP-запроса, ответа и логов текущего контекста |
| method, route, status_code, duration_ms | Метод, шаблон маршрута, статус и длительность |
| component | Имя фоновой задачи при её неожиданном завершении |
| error_type, frames | Тип исключения и позиции стека без текста исключения, исходных строк и локальных переменных |

Access event содержит шаблон `/api/products/{product_id}`, а не значение ID.
Query string, тело, cookies и Authorization в него не записываются. Для
несопоставленного маршрута используется `<unmatched>`. Стандартный Uvicorn access
log отключён, иначе он повторно записывал бы сырой URL.

Это ограничение относится к access event и полям исключения. Произвольный текст
`logger.info(...)` не очищается автоматически: бизнес-код не должен вставлять
в сообщения токены, пользовательские данные, тела ответов провайдеров или DSN.

## Request ID

Ответ содержит `X-Request-ID`, в том числе при 404 и необработанной ошибке 500.
Допускается один входной ID длиной 1–128 символов из ASCII букв, цифр, `_` и `-`.
При отсутствии, дублировании или неверном формате создаётся новый ID.

Необработанная ошибка возвращает безопасный JSON с `detail` и `request_id`.
Frontend сохраняет заголовок в `ApiError.requestId`, включая не-JSON ответы.
При расследовании ошибки достаточно ID, времени и сценария пользователя; токены
и содержимое запроса для поиска этой записи не требуются.

## Health endpoints

- `/health/live` показывает, что HTTP-приложение отвечает.
- `/health/ready` проверяет включённые БД и storage. Неожиданно завершившаяся
  фоновая задача делает ответ 503. Готовность API не доказывает доставку письма,
  работу платёжного провайдера или готовность всего пользовательского сценария.
- Для MinIO проверяются media, crm-private и projects buckets. Projects должен
  существовать без bucket policy; при нарушении readiness возвращает 503.
  Upload/access также проверяют policy перед записью или выдачей временной ссылки.
- Выключенные ресурсы обозначаются `disabled`; это не fallback к старой БД или
  файловому хранилищу. Для рабочего релиза БД и требуемое storage включаются
  в конфигурации. SQLite используется в изолированных тестах доменной логики;
  проверка Alembic revision при startup относится к PostgreSQL.

## Проверки миграций

`rtk proxy make PYTHON=.venv/bin/python lint migration-check` проверяет код и
генерацию SQL в обе стороны. Генерация SQL не заменяет применение на PostgreSQL.

Для настоящей проверки используется отдельная БД с именем `test_*` и переменная
`SCHEMA_TEST_POSTGRES_URL`. Запуск из backend:

```sh
rtk proxy .venv/bin/python -m pytest -q tests/integration/test_postgres_schema.py
```

Без переменной эти проверки пропускаются. Они применяют миграции, сравнивают
живую схему с ORM и проверяют upgrade/downgrade миграции удаления индексов, сохранность
записи пользователя, уникальность email и неизменность ограничений.
Не использовать общую тестовую БД параллельно с другими процессами миграций.

Проверки приватных файлов дополнительно требуют `MINIO_TEST_CONFIG_PATH` — путь
к локальному JSON с `endpoint`, `access_key`, `secret_key`. Не передавайте рабочие
ключи: тесты создают и удаляют собственные buckets в отдельном MinIO. Конфиг
должен иметь права `0600` и удаляться после прогона; ключи не выводятся в журнал.
В CI шаг **Run complete backend suite with PostgreSQL and MinIO without skips**
поднимает временный MinIO той же версии, что Compose, и создаёт четыре отдельные
БД для schema/contracts, Tochka, production и order workflow. После готовности
зависимостей запускается весь каталог `tests`, включая PostgreSQL-варианты
публичных профилей, сообществ, лендингов владельцев и справочников.

Тот же строгий запуск доступен локально из backend:

```sh
.venv/bin/python -m scripts.check_tests --report /absolute/path/test-results.xml
```

Перед запуском нужны `SCHEMA_TEST_POSTGRES_URL`, `TOCHKA_TEST_POSTGRES_URL`,
`PRODUCTION_TEST_POSTGRES_URL`, `ORDER_WORKFLOW_TEST_POSTGRES_URL` — четыре
разные БД `test_*` с драйвером `postgresql+asyncpg` — и приватный конфиг
`MINIO_TEST_CONFIG_PATH`. Команда не создаёт зависимости: их владелец поднимает
и удаляет отдельно. Она передаёт pytest только тестовое окружение, удаляет старый
отчёт и отклоняет пустой отчёт, ошибки и любой пропуск. Обычный `make check`
без этих переменных допускает пропуски и не заменяет этот запуск.

В CI контейнер MinIO, его volume, конфиг и отчёт удаляются при любом исходе;
БД принадлежат временному PostgreSQL service задания. Это дополняет проверку
релизных образов в job `containers`.

Миграция `20261013_0056` убирает 24 неуникальных индекса, дублирующих отдельные
UNIQUE constraints. Ограничения и их собственные индексы сохраняются; downgrade
восстанавливает удалённые структуры. Сравнение схемы учитывает физические имена
CHECK constraints, которые PostgreSQL сокращает до своего лимита длины.

Миграция `20261013_0057` добавляет `user_favorites`. Серверный API
`GET /api/profile/favorites` возвращает ограниченную страницу и `next_cursor`;
`PUT/DELETE /api/profile/favorites/{product_id}` идемпотентно меняют избранное
текущего аккаунта. Требуется действующая identity-сессия; user ID не принимается
из браузера. Данные хранятся в PostgreSQL, а не Redis/localStorage. Неактивные,
демонстрационные товары и товары неактивных категорий не показываются.

`GET /api/profile/favorites/status?product_ids=…` возвращает принадлежность
избранному только для запрошенных опубликованных карточек; максимум 100 ID.
Все ответы избранного имеют `Cache-Control: no-store`.

## Новая витрина

`GET /api/catalog/products` возвращает страницу карточек (по умолчанию 24,
максимум 100) с одной готовой публичной картинкой. Это отдельный компактный
контракт: без вариантов, полного описания и расчёта складской доступности.
`query`, `category_ids`, `colors`, `source`, `min_price`, `max_price`, `sort`,
`ids` и `cursor` валидируются до чтения. Группы фильтров объединяются через AND,
элементы одной группы — OR; границы цены включительны. Пустой `max_price`
не ограничивает цену. Цена в ответе — десятичная строка.

Сортировки `newest/oldest` используют дату создания и ID, `cheap/expensive` —
цену и ID. Keyset cursor содержит позицию и отпечаток параметров; смешивать
страницы разных поисков нельзя. На одну страницу выполняются два SELECT:
карточки с LIMIT и выбор одного подходящего медиа для их ID. Медиа в статусе
pending, приватные объекты и видео исключены. URL строится из публичной S3 базы,
bucket и object key; старый `/uploads` здесь не используется.

`GET /api/catalog/options` получает доступные категории и цвета из опубликованных
товаров. Это DISTINCT SQL, без загрузки полных документов каталога; число
уникальных опций пока не ограничено. Кеш и нагрузку этого endpoint нужно
проверить на реальном объёме ассортимента, а не объявлять решёнными.

Миграция `20261013_0058` добавляет три частичных индекса опубликованных товаров:
по цене ASC/DESC и по дате создания. Контрактные проверки на PostgreSQL 17
включают настоящие планы четырёх сортировок на 20 000 строк: выбран соответствующий
индекс, отдельного Sort нет. Это доказательство плана выборки, не итоговой скорости
главной. Для кириллического поиска используется встроенная UTF8 collation
PostgreSQL 17 `pg_c_utf8`, независимо от locale тестовой ОС.

Локальный frontend подключён к новой витрине: главная получает четыре товара,
каталог — страницы по 24. Поиск отменяет предыдущие запросы; сбой следующей
страницы сохраняет карточки. Избранное товаров использует identity API,
сохраняется после ответа сервера и очищается при смене сессии. Постоянного
локального списка товаров в избранном нет. Сообщества получают карточки
опубликованных лендингов владельцев через `/api/communities`; их избранное
хранится в PostgreSQL через identity API `/api/profile/community-favorites`.
«Люди» получают опубликованные публичные профили через `/api/people`;
свой профиль пользователь редактирует через `/api/profile/public`.
Проекты и профиль используют
настоящую identity-сессию, PostgreSQL и частный MinIO; явный перенос старых
записей доступен по действию. Их contracts и эксплуатация описаны в
`backend/docs/customer-projects.md`. Новый production-релиз не выполнен.

Очистка проектов выполняется отдельным `scripts.reconcile_project_media`,
профиль Compose `project-media`. Он проверяет Alembic head до работы, обрабатывает
ограниченную пачку и пишет JSON event `project_media.cleanup` с `cleanup_counts`
и `dry_run`. Поля событий не содержат документов, имён файлов и подписанных URL.
`--dry-run` завершает один цикл без изменений; `--once` делает один настоящий
цикл. Deployment активирует worker при включённом identity API. Контейнерная
активация и production-проверка нового релиза остаются обязательными.
