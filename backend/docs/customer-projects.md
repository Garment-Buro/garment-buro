# Постоянные проекты конструктора

Этап нового релиза. Конструктор сохраняет и открывает документы через backend;
частные изображения загружаются в MinIO и читаются по временной ссылке.
Явный перенос подходящих локальных записей подключён в профиле. Очистка
неиспользуемых файлов выполняется отдельным worker; контейнерный выпуск и
production-проверка остаются частью полного рефакторинга.

## Источник данных и границы

`customer_projects` хранит владельца, исходный товар, вид проекта, название,
версию и даты как отдельные SQL-поля. Snapshot холста — типизированный документ
в PostgreSQL JSONB: его структура отражает `ConstructorDraftState`. Это не файл
JSON и не browser cache; документ записывается в транзакции с метаданными.
Redis не участвует в подтверждении сохранения.

`schemaVersion=1` обязателен. Snapshot сохраняет обе стороны модели, посадку,
размер, координаты и размеры холста, положение/масштаб/поворот декора, параметры
текста и комментарий. Ограничения: до 100 украшений, 256 KiB документа, 4000
символов комментария, конечные числа и допустимые диапазоны размеров. Неизвестные
поля/версии отклоняются. Все строки, включая вложенный текст, отклоняют нулевой
символ и непарные Unicode-суррогаты до записи в PostgreSQL. Цена в документе —
только предварительный расчёт редактора; она не является серверной котировкой заказа.

В полях изображений находятся только `{mediaId: number}`. Data URL, blob URL,
произвольные внешние адреса и просроченные подписанные ссылки не сохраняются.
`customer_project_media` удерживает ссылки FK RESTRICT на `media_objects`:
используемый файл нельзя физически удалить раньше документа.

При записи допускаются готовые JPEG/PNG/WebP, прикреплённые к исходному товару,
либо частные изображения текущего владельца в bucket
`{MINIO_BUCKET_PREFIX}-{APP_ENV}-projects`, с префиксом `projects/{user_id}/`.
CRM-файлы и изображения другого аккаунта недоступны. Уже прикреплённые изображения
можно сохранить при последующем редактировании после удаления товара.
Local/server minio-init создаёт этот bucket и отключает анонимный доступ.
Readiness проверяет его существование и отсутствие bucket policy. Загрузка и
выдача ссылки также отказывают при наличии policy, даже если обойти health gate.

## API

Все операции `/api/profile/projects` требуют текущую identity-сессию.
Владелец берётся из проверенной сессии, поле `user_id` в запросе запрещено.
Маршрут подключается вместе с identity API.

| Операция | Контракт |
| --- | --- |
| `POST /api/profile/projects` | `client_key`, `product_id`, `kind`, `title`, `snapshot`; новая запись 201, повтор 200 |
| `GET /api/profile/projects?kind=draft&limit=24&cursor=...` | Только метаданные; `kind=draft\|collection`, limit 1–50, ID keyset cursor |
| `GET /api/profile/projects/{id}` | Метаданные и полный snapshot своего проекта |
| `GET /api/profile/projects/by-client-key/{key}` | Свои метаданные по ключу создания; 404 если нет, 410 если удалён; без snapshot |
| `PUT /api/profile/projects/{id}` | `expected_version`, `kind`, `title`, `snapshot`; версия увеличивается на 1 |
| `DELETE /api/profile/projects/{id}?expected_version=...` | Проверка версии, удаление документа и ссылок на файлы; повтор той же операции допустим |

Для чужого/несуществующего документа GET/PUT/DELETE возвращают 404. Устаревшая
версия или повтор client_key с другим первоначальным содержимым дают 409.
Повтор POST с исходным содержимым возвращает текущую версию проекта и не затирает
последующие изменения. После удаления остаётся метка с ключом/хешем; повтор POST
даёт 410 и не воскрешает документ после сетевой задержки. Snapshot и связи с
изображениями при этом очищаются. Удаление аккаунта каскадно удаляет его проекты;
удаление исходного товара сохраняет документ с `product_id=null`.

Список получает одну ограниченную SQL-выборку метаданных без snapshot и без N+1.
Частичный индекс `(user_id, kind, id) WHERE deleted_at IS NULL` исключает просмотр
меток удалённых проектов. Цена/описание товара не копируются в каждую строку списка.

Миграция `20261013_0059` создаёт таблицы, ограничения и индексы. HTTP startup
не создаёт таблицы. Все ответы проектов имеют `Cache-Control: no-store`.
Ошибки входной валидации сохраняют `loc/msg/type`, но не копируют пользовательский
документ и служебный контекст. Неконечные числа дают 422 вместо ошибки сериализации.

## Частные изображения

`POST /api/profile/project-media` принимает multipart `file` с действующей
identity-сессией. Ответ 201 содержит `id`, `content_type`, `size_bytes`; публичного
URL в нём нет. Максимум — меньшее из 8 MiB и MEDIA_MAX_UPLOAD_BYTES, сторона до
8192 px и суммарно до 16 777 216 пикселей. MIME/расширение клиента не определяют
тип: backend полностью декодирует единственный кадр JPEG/PNG/WebP. SVG, видео,
анимация и повреждённые изображения отклоняются с 415, превышение размера — 413.
EXIF orientation применяется, метаданные удаляются, результат сохраняется как
lossless WebP с прозрачностью. Декодирование выполняется вне async event loop.

Перед PUT в storage фиксируется pending-запись с владельцем, checksum и размером.
Только после успешного PUT она становится ready и возвращается клиенту. Сбой PUT
помечает её failed и возвращает 503; такой ID нельзя использовать в документе или
читать. Незавершённая pending-запись остаётся доступной reconciler.

## Жизненный цикл частных файлов

`python -m scripts.reconcile_project_media` запускает отдельный процесс с той же
проверкой Alembic head и JSON-логированием, что и API. Нужны включённые database,
MinIO и identity API. Он не запускается внутри HTTP lifespan и не использует
браузер либо Redis как очередь подтверждённого удаления.

По умолчанию неподключённые `pending`/`failed` удаляются через час, готовые файлы
без ссылок — через семь суток с последней отвязки. При снятии картинки с проекта
время обновляется, поэтому старый файл получает полные семь суток. Проекты и
избранное soft-deleted аккаунта удаляются пачками; его готовые частные файлы без
оставшихся связей не ждут неделю. Заказы, аудит, публичные файлы, CRM bucket и
неизвестные ключи не входят в эту очистку. Допустим только точный namespace
`projects/{positive_user_id}/{32_hex_chars}.webp` частного projects bucket.

Проверяются все FK к `media_objects`, в том числе nullable SET NULL связи CRM.
Запись проекта блокирует прежние и новые media в стабильном порядке ID;
CRM сохраняет share lock готового media до commit. Worker использует SKIP LOCKED
и повторную проверку связей после получения блокировки. Создание проекта,
избранного и upload сериализуются с удалением аккаунта через блокировку user.
После durable pending upload удерживает SQL-lock до окончания SDK PUT и ready;
отмена HTTP-задачи также ждёт завершения PUT перед освобождением блокировки.

Перед обращением к MinIO фиксируется `status=deleted`. При сбое SQL-строка
сохраняется и повторно обрабатывается через минуту. После успешного физического
удаления удаляется строка media. Для versioned bucket удаляются версии и delete
markers точного ключа, до 1000 за попытку; большой набор продолжается следующей
попыткой. Частный bucket с непустой policy блокирует физическую очистку.

Один цикл выбирает до 100 media, до 100 проектов и до 100 записей избранного,
затем ждёт 60 секунд, в том числе при большом backlog. Discovery использует до
шести SQL-выборок за пачку: отдельные status/age диапазоны и ветки deleted/null
owner. Миграция `20261014_0060` создаёт частичный индекс private bucket/status/time/id.
Каждый prefetched ID повторно проверяется перед изменением. Старый referenced
архив может просматриваться при discovery, но не перечитывается для каждого
удалённого файла. Полного прохода по свежим файлам при возрастной выборке нет.

Безопасная проверка кандидатов: `python -m scripts.reconcile_project_media
--dry-run --max-items 100`. Она выполняет один цикл без изменения SQL и storage;
в лог выводятся только агрегаты `cleanup_counts` и `dry_run`, без имён/URL.
`--once` выполняет один настоящий цикл. Интервалы задаются `--stale-upload-hours`,
`--unattached-hours`, `--retry-seconds`, `--poll-seconds`; принимаются только
положительные конечные значения. Размер пачки ограничен 1–1000.

Local/server Compose содержит профиль `project-media` и `project-media-worker`.
Remote deploy активирует его вместе с `IDENTITY_API_ENABLED`. Локальный запуск:
`docker compose -f docker-compose.local.yml --profile project-media up -d
project-media-worker`. Это конфигурация будущего выпуска, не подтверждение
активного production worker.

`GET /api/profile/project-media/{id}/access` проверяет ready, владельца, частный
bucket и его префикс. Чужой, CRM или публичный файл получает 404, гость — 401.
Ответ содержит временный URL и `expires_in`; URL не записывается в snapshot.
Ссылка является временным разрешением на чтение: получивший её может читать до
истечения срока. Backend-ответ и скачивание имеют no-store. Storage proxy снимает
публичный префикс и передаёт внутренний Host для сохранения SigV4 подписи.

`GET /api/profile/projects/{id}/media?version=N` возвращает все изображения
документа одним ответом `{version, items}`. Основной SQL-запрос одновременно
проверяет владельца, отсутствие удаления и ожидаемую версию, без чтения snapshot.
Чужой/удалённый проект даёт 404; изменившаяся версия — 409; недоступное изображение
— 422. Частные объекты проходят те же проверки bucket/prefix/policy и получают
временный URL с expires_in. Публичные изображения получают обычный URL и
expires_in=null. Нет отдельных HTTP или SQL-запросов для каждого изображения.

Деталь настоящего товара содержит media_assets с серверными ID, ролями,
порядком, URL и MIME только готовых публичных JPEG/PNG/WebP. Компактный список
витрины не расширен. Сравнение миграции строго проверяет прежние поля, исключая
только новое поле media_assets, отсутствовавшее в старом контракте.

Frontend lib/api/projects.ts предоставляет типизированные CRUD, upload и
пакетное чтение. lib/projects/snapshot.ts переводит ConstructorDraftState в
schemaVersion=1 с ID изображений и обратно, сохраняя обе стороны, геометрию,
текст и посадку. Одинаковые источники разрешаются один раз; ошибка/отмена
останавливает сериализацию; отсутствие изображения запрещает восстановление
частичного холста. Nullable поля API нормализуются к типам редактора.
Конструктор и списки профиля используют общий `useCustomerProject` и `ProjectEditor`.
После подтверждённого сохранения адрес содержит постоянный `projectId`.
Повтор POST после потери ответа сохраняет исходный idempotency key и документ;
более поздние правки не выдаются за подтверждённые. При 409 локальные правки
остаются до явной команды загрузить сохранённую версию. Неудачная перезагрузка
не стирает доступный редактору документ.

Идентификатор аккаунта отделён от поколения access token: обычный refresh,
в том числе из другой вкладки, не пересоздаёт редактор. Выход и смена аккаунта
отменяют операции и исключают поздние ответы. Сохранённая геометрия, размеры
холста и масштабы по осям восстанавливаются из документа даже после изменения
размеров товара в каталоге. Явный выбор другой посадки пересчитывает геометрию.

Профиль (`/unfinished`, `/mycollection` и вкладки `/profile`) читает серверные
списки отдельно по `kind`. `useCustomerProjectLibrary` получает до 24 строк
метаданных на страницу, следующая страница добавляется по ID cursor. Холст и
пакет ссылок загружаются только для выбранного проекта, без N+1 для карточек.
Карточки списка показывают серверные номер/название; фиктивная фотография
коллекции удалена. Выбранный проект открывается по постоянному `projectId`.
Ошибка списка или preview показана отдельно от пустого состояния. Удаление
требует подтверждения для конкретного аккаунта/ID и проверяет версию; при 409
проект остаётся в списке. Выход/смена аккаунта отменяет операции и скрывает данные.
Старые browser записи не приписываются вошедшему аккаунту автоматически.

## Явный перенос старых записей

В настройках профиля есть отдельное действие «Перенести старые проекты из
браузера». Экран показывает аккаунт назначения; записи нужно выбрать вручную.
Модуль переноса загружается по открытию экрана. Он не участвует в обычном
чтении списка серверных проектов и не сохраняет новые проекты в браузере.

Frontend-модуль `lib/projects/legacyRecords.ts` содержит только исторический
тип, проверку формата и чтение старой constructor-ссылки. Прежние общие
функции создания, сериализации, записи и удаления локальных проектов удалены.
Читатель не исправляет исходный JSON; запрет доступа к localStorage и
повреждённые данные не выбрасывают ошибку в эффекте редактора. Экран явного
переноса отдельно сообщает о проблемах чтения. Единственная оставшаяся
запись в эти namespaces — подтверждённая очистка в `legacyMigration.ts`
после проверки серверной квитанции и неизменности исходной записи.

Переносятся записи с полным распознанным состоянием редактора и постоянным ID
товара. Backend проверяет доступность товара; сопоставления по названию/позиции
и подстановки демонстрационного холста нет. Изображения должны быть готовыми
публичными media этого товара либо локальными PNG/JPEG/WebP. Произвольные URL,
неизвестные старые статические адреса и недоступные blob не скачиваются как
пользовательские файлы. Все новые источники читаются до первого upload.
Геометрия, обе стороны и текст проходят общий snapshot adapter.

Ключ `legacy-v1-<sha256>` зависит от namespace и исходного текста отдельной
записи. Для UTF-8 кодирования строка предварительно оборачивается в well-formed
JSON: непарные UTF-16 surrogates не схлопываются. Любое изменение текста записи
считается новой локальной версией. Ключ на сервере изолирован владельцем.
До upload клиент проверяет receipt по ключу; повтор после перезагрузки или
потерянного committed POST получает существующий проект без повторной загрузки
файлов и без перезаписи последующих серверных правок. Конкурентный POST409
также проверяет receipt; tombstone410 не восстанавливается автоматически.
Receipt использует один SELECT метаданных по уникальному индексу без JSONB.

После переноса локальная копия остаётся. Отдельная кнопка её удаления повторно
проверяет live receipt в текущей сессии и точное исходное содержимое. Операция
сериализуется между вкладками через Web Locks; без их поддержки копия остаётся.
Scanner выделяет исходные JSON-фрагменты: удаление выбранного элемента не
пересериализует соседние неизвестные записи, включая большие числа и escape
sequences. Изменённая локальная версия не удаляется. Ошибки чтения/сети/формата,
отсутствующее состояние и смена аккаунта сохраняют исходные данные.

Проверено на настоящих PostgreSQL/MinIO: явный выбор, потерянный POST, повтор и
reload без новых документов/upload, независимый браузер, геометрия, неизвестные
записи и изменённый источник, чужой receipt404. Дополнительный UI-прогон удерживает
ответ уже committed POST, выполняет logout другой вкладкой и настоящий OTP-вход
в другой аккаунт без reload: поздний ответ не публикуется, выбор сброшен, исходник
остаётся. Ширины 320/390/736/1280, ошибок JS во всех контекстах нет.

## Проверка и оставшаяся работа

HTTP-контракты проверяют реальную БД и сессии, чтение другим экземпляром
приложения, владельца, версии, повторные запросы, обе стороны/посадку/текст,
ссылки на файлы, пределы пагинации и отказ невалидного документа.
PostgreSQL-проверки используют Alembic: параллельные POST и PUT, FK файлов,
удаление товара, повторное удаление и очистку snapshot, план запроса при 24
активных и 10 000 удалённых проектах. Сопоставление миграций с ORM проверяется
отдельно. Контрактные тесты используют fake только на границе MinIO SDK;
это отдельно от проверки настоящего storage.

Прогон основы документов до добавления image API: **548 passed** с четырьмя
PostgreSQL test DB. Целевая проверка проектов, схемы, миграций и наблюдаемости:
53 passed. Проверка NUL сначала воспроизвела 500 PostgreSQL, после исправления
подтвердила 422 без частично созданной записи или изменения сохранённого проекта.
Независимое ревью нового модуля завершено; найденный дефект валидации исправлен.

Интеграционный test_project_media_minio.py проверен с настоящими PostgreSQL и
локальным MinIO из официального тега RELEASE.2025-07-23T15-54-02Z: upload, alpha,
checksum/размер, чтение после нового экземпляра приложения, подписанный GET через
proxy, анонимный GET 403, чужой аккаунт 404 и гость 401. Установка публичной policy
блокирует readiness/upload/access, её удаление восстанавливает readiness.
Повреждённый EXIF сначала воспроизвёл HTTP 500, после исправления даёт 415 без
частичной записи или файла. Независимое ревью этого этапа завершено.
Финальный backend-прогон после всех исправлений: **559 passed**, с четырьмя
PostgreSQL test DB и настоящим MinIO. Ruff изменённых файлов и diff check прошли.
Для повторения нужны SCHEMA_TEST_POSTGRES_URL и MINIO_TEST_CONFIG_PATH: путь к
локальному JSON с endpoint/access_key/secret_key одноразового loopback MinIO.
Этот файл не сохраняется в репозитории; интеграционный тест создаёт уникальные
buckets и удаляет только свои fixtures. Проверка не доказывает production storage.

Браузерная проверка конструктора на настоящих PostgreSQL/MinIO прошла:
