# Stage 32: private CRM files in MinIO

Status: complete locally; staff HTTP/RBAC path and live MinIO proof pending

Quality score: 94/100

## Safety boundary

This stage gives patterns, tech-card source documents, and production evidence a
private object-storage path. CRM objects never use the public catalog bucket or
its CDN URL. The database stores immutable object evidence and attachment
metadata; a short-lived MinIO URL is created only for an authenticated actor and
is never persisted.

No HTTP route is introduced. The service boundary is ready for the staff API,
where `crm.access` authorization must happen before either upload or download.

## Delivered

- revision `20260812_0025` adds one-target CRM attachments and append-only file
  access events;
- the environment-specific private bucket is
  `<MINIO_BUCKET_PREFIX>-<APP_ENV>-crm-private`;
- local MinIO initialization creates that bucket with anonymous access set to
  `none`; the existing catalog media bucket remains public-download;
- application readiness requires both the public media bucket and private CRM
  bucket when MinIO is enabled;
- uploads accept verified PDF, JPEG, PNG, and WebP bytes only; SVG and arbitrary
  active content are rejected regardless of filename;
- filenames are reduced to a safe basename and object keys are generated by the
  backend under role/date namespaces;
- size, SHA-256, detected content type, bucket, object key, ETag, and version ID
  are retained in `media_objects`; CRM rows reference that evidence instead of
  duplicating object state;
- every attachment belongs to exactly one permitted target: an immutable
  tech-card revision, production project, or production unit;
- pattern and tech-card-source roles are restricted to tech-card revisions;
  production evidence is restricted to projects or units;
- pending metadata is committed before the object write, storage failures become
  visible `failed` rows, and a failed database finalization removes the private
  object on a best-effort basis before marking metadata failed;
- download links force attachment/octet-stream behavior, expire using the
  configured presigned TTL, and are never stored;
- every returned link writes `download_url_issued` with attachment, actor,
  issuance time, and expiry time; user deletion may anonymize the actor but
  cannot remove the historical access event;
- online downgrade refuses to remove the schema while attachments or access
  events exist.

## Bucket policy and activation order

Production and staging use external object storage, so their private buckets
must be provisioned explicitly before deploying this code:

1. Create the environment-specific `crm-private` bucket.
2. Deny anonymous access and do not place it behind the public CDN origin.
3. Grant the application principal only the object operations required for its
   own public-media and private-CRM buckets.
4. Confirm both bucket existence checks from the application network.
5. Apply Alembic revision `0025`.
6. Deploy the backend with CRM HTTP routes still disabled.
7. Exercise a disposable private upload/download and verify no anonymous or CDN
   URL can read it before enabling a staff route.

Because readiness now checks both buckets, deploying before step 1 intentionally
keeps the instance out of service rather than accepting traffic with incomplete
private storage.
