# Покупатель, получатель и справочник СДЭК

## Текущий checkout

Раскрытая корзина использует отдельные формы `RecipientSheet` и `DeliverySheet`.
`buyer` содержит ФИО, телефон и почту покупателя. `recipient` содержит контакты
получателя, который может быть другим человеком. Телефон используется для связи
по доставке, а не как доказательство владения кабинетом.

На текущем dev включён identity API, но checkout и каталог ещё используют legacy
хранилище. Адаптер `checkout/legacy_contact.py` проверяет ПВЗ по серверному
справочнику, повторно получает тариф и подготавливает неподтверждённый аккаунт
через существующий `IdentityRepository`. Вход и получение заказов требуют OTP
покупателя; существующий `OrderOwnershipBridgeService` связывает заказы по
подтверждённой почте. Контакт получателя не используется для владения заказом.
Создание аккаунта не выдаёт сессию и не перезаписывает профиль.

В legacy `orders.email` остаётся почтой покупателя для чека и владения заказом.
Поля `first_name`, `phone` относятся к получателю; добавлены `buyer_name`,
`buyer_phone`, `recipient_email`. Совместимые nullable колонки добавляет
существующий механизм legacy migrations при старте. Они не меняют старые заказы.

Новые формы подключены к раскрытой корзине. Старый `/checkout` также передаёт
покупателя для создания кабинета, но сохраняет прежний экран доставки. Выключенный
target checkout V2 не переключается автоматически: его миграция — отдельный этап
переноса каталога/заказов. Базовая legacy упаковка 500 г, 20×20×10 см на изделие
сохранена, количество изделий учитывается. До включения реальной доставки нужно
сверить упаковку с производством; target quote уже поддерживает логистику каталога.

## Постоянный справочник

- PostgreSQL: `delivery_pickup_points`, `delivery_directory_state`, миграция 0032.
- `GET /api/cdek/points?q=Тверь&offset=0&limit=50` ищет только в БД.
- Все слова поиска объединяются через AND; город, регион, улица, название и код.
- Максимум 100 записей на страницу; `total`, `updated_at`, `stale` в ответе.
- Фоновый процесс API проверяет срок обновления раз в минуту. Успешный снимок
  используется сутки. Источник — `GET /v2/deliverypoints?country_code=RU&type=PVZ`.
- Атомарная SQL lease не допускает параллельных загрузок из разных API процессов.
  Повтор после ошибки через 15 минут; нет запросов в СДЭК на каждый поиск.
- Снимок заменяется одной транзакцией только после успешной загрузки и проверки.
  Пустой/битый ответ не удаляет сохранённые ПВЗ.
- До первой синхронизации API отвечает 503. При сбое доступны сохранённые данные
  не старше семи суток; более старые данные нельзя выбрать или оформить.
- Карта и список используют один набор точек. При отказе картографического API
  список остаётся рабочим. Демо-точек в рабочем коде нет.

## Включение

Серверу нужны `CDEK_CLIENT_ID`, `CDEK_CLIENT_SECRET`, `CDEK_API_URL` и настроенная БД.
Секреты только в серверном env. После рестарта API справочник загрузится в фоне.
Публичный ключ карт передаётся через `NEXT_PUBLIC_YANDEX_MAPS_API_KEY` при сборке
frontend; ограничить его доменами сайта/стенда. Не путать с runtime переменной.
Справочник и расчёт не включают `CDEK_CREATION_ENABLED` или создание отправлений.

На проверенном dev ключи СДЭК отсутствовали. Это блокирует реальную загрузку ПВЗ и
расчёт тарифа, но не работу форм. Ошибка тарифа больше не обозначает бесплатную
доставку. Вход по телефону остаётся выключенным до выбора провайдера.

Официальная документация: https://apidoc.cdek.ru/.
