# Покупатель, получатель и справочник СДЭК

## Текущий checkout

Раскрытая корзина использует отдельные формы `RecipientSheet` и `DeliverySheet`.
`buyer` содержит ФИО, телефон и почту покупателя. `recipient` содержит контакты
получателя, который может быть другим человеком. Телефон используется для связи
по доставке, а не как доказательство владения кабинетом.

Это описание форм, а не доказательство готового сквозного оформления. В текущем
worktree старое SQLite-приложение, `checkout/legacy_contact.py` и
`OrderOwnershipBridgeService` удалены. Новое приложение не подставляет их при
выключенном checkout. Заказы и их владение хранятся в PostgreSQL; телефон не
является основанием доступа. `checkout/contact.py` валидирует отдельные
контакты покупателя и получателя для современного HTTP-контракта.

Обнаруженное расхождение, которое блокирует выпуск: `frontend/lib/api/orders.ts`
и обе формы отправляют прежние `cart_items`/`total_price`, а действующий
`POST /api/orders` принимает `CheckoutCommand` с отдельными `buyer`, `recipient`, `items`,
`claimed_total_price` и обязательным `delivery_quote_token`, требует
`Idempotency-Key` и проверяет identity/guest access. Текущий клиент не выполняет
этот контракт. Новый серверный checkout использует каталог, inventory
reservations, проверенную доставку, раздельные снимки контактов и идемпотентные
платежи. Жизненный цикл двух frontend-форм ещё требует переноса.
Возвращать старый HTTP fallback для обхода этого расхождения нельзя.

Следующий этап полного релиза: один контракт для раскрытой корзины и `/checkout`,
подписанный расчёт, отдельные контакты и защищённый guest ownership,
повтор запроса без второго заказа/платежа и восстановление после потерянного
ответа. До реальной доставки нужны также подтверждённые размеры и вес упаковки
в каталоге. Успешная покупка, SMTP и платежный провайдер пока не проверены E2E.

## Независимые снимки контактов

`buyer` и `recipient` содержат `name`, `phone`, `email`. Оба контакта обязательны
и валидируются до заказа или платежа. Имя сохраняется целиком; сервер не
угадывает фамилию и отчество. Покупатель может указать другого получателя.

Миграция0061 добавляет nullable `orders.buyer_name`, `buyer_phone`,
`recipient_email`. Существующие `email`/`email_normalized` — адрес чека
покупателя, `first_name`/`phone` — контакт доставки. Новые поля заполняются
вместе; SQL constraint запрещает частичный снимок. Исторические строки
сохраняют NULL: неизвестные контакты не восстанавливаются предположениями.

Чек и письмо об оплате используют покупателя; запрос отправления СДЭК —
получателя. Административные заказы, поиск/карточка клиента и поддержка
показывают контакт покупателя; сведения для упаковки/отправки — получателя.
Чтение заказа возвращает отдельные `buyer` и `recipient` (NULL для неизвестных
исторических снимков) рядом с существующей проекцией заказа.

Ни один контакт из формы не создаёт identity session и не доказывает владение.
Авторизованный заказ принадлежит проверенной сессии, гостевой — capability,
хеш которой хранится в PostgreSQL. Вход получателя по OTP не открывает чужой
заказ. Совпадение почты с гостевым заказом также не присоединяет его к кабинету
автоматически. Перенос guest ownership требует отдельного доказанного потока.

## Проверенный расчёт доставки

`POST /api/cdek/calculate` получает `city`, `delivery_method`, `cart_items`
(`product_id`, `quantity`) и выбранное место доставки. Для `cdek_pickup`
обязателен `cdek_point_code`; город и адрес берутся из PostgreSQL, а не из
браузера. Для `cdek_door` обязателен `delivery_address`. Параметры упаковок
берутся из каталога; клиентские размеры/вес не используются.

Ответ содержит `delivery_price`, `quote_token`, канонические `delivery_city`,
`delivery_address`, `cdek_point_code`, тариф и сроки. `quote_token` действует
15 минут и связывает сумму провайдера, отправителя/тариф, фактические упаковки,
количество товаров и место доставки. Адреса и контакты в токен не записываются.
Для подписи нужен серверный `JWT_SECRET`; ключ отделён от подписи identity JWT.
Токен не должен попадать в URL или логи.

При первом `POST /api/orders` сервер восстанавливает расчёт из доверенных
данных и проверяет `delivery_quote_token`. Браузерный `delivery_price` не
определяет списание: итог сравнивается с ценами каталога и подписанной суммой.
Отсутствующий, изменённый или просроченный расчёт возвращает422 до создания
заказа, резервирования или платежа. Недоступный справочник возвращает503;
изменённый каталог может вернуть409. Ошибка СДЭК не заменяется доставкой за0 ₽.

Уже сохранённый заказ повторяется по тому же `Idempotency-Key`, actor и
исходному payload, включая исходный токен, даже после истечения15 минут или
сбоя справочника. При неопределённом результате нельзя получать новый токен
и заменять payload той же операции. СДЭК вызывается только при расчёте,
вне транзакции; создание заказа проверяет доставку локально. Платёжный
провайдер вызывается после сохранения заказа и попытки платежа.

Проверено HTTP-тестами с настоящими схемами/сервисами и заменой только внешних
транспортов: канонический ПВЗ, подмена суммы/количества/логистики/адреса,
истечение срока и повтор при сбое справочника. Настоящий PostgreSQL проверяет
пять одновременных повторов во время ожидающего платежа: один заказ, резерв
и попытка платежа. Эти проверки не подтверждают работу реальных провайдеров
или ещё не перенесённых frontend-форм.

## Постоянный справочник

- PostgreSQL: `delivery_pickup_points`, `delivery_directory_state`, миграция 0032.
- `GET /api/cdek/points?q=Тверь&offset=0&limit=50` ищет только в БД.
- Все слова поиска объединяются через AND; город, регион, улица, название и код.
- Максимум 100 записей на страницу; `total`, `updated_at`, `stale` в ответе.
- Фоновый процесс API проверяет срок обновления раз в минуту. Успешный снимок
  используется сутки. Источник — `GET /v2/deliverypoints?country_code=RU&type=PVZ`.
- Атомарная SQL lease не допускает параллельных загрузок из разных API процессов.
  Повтор после ошибки через 15 минут; нет запросов в СДЭК на каждый поиск.
- Снимок заменяется одной транзакцией только после успешной загрузки и проверки.
  Пустой/битый ответ не удаляет сохранённые ПВЗ.
- До первой синхронизации API отвечает 503. При сбое доступны сохранённые данные
  не старше семи суток; более старые данные нельзя выбрать или оформить.
- Карта и список используют один набор точек. При отказе картографического API
  список остаётся рабочим. Демо-точек в рабочем коде нет.

## Включение

Серверу нужны `CDEK_CLIENT_ID`, `CDEK_CLIENT_SECRET`, `CDEK_API_URL` и настроенная БД.
Для `CDEK_QUOTE_ENABLED=true` также обязателен `JWT_SECRET`.
Секреты только в серверном env. После рестарта API справочник загрузится в фоне.
Публичный ключ карт передаётся через `NEXT_PUBLIC_YANDEX_MAPS_API_KEY` при сборке
frontend; ограничить его доменами сайта/стенда. Не путать с runtime переменной.
Справочник и расчёт не включают `CDEK_CREATION_ENABLED` или создание отправлений.

При отсутствии ключей реальная синхронизация и расчёт недоступны. Наличие форм
не подтверждает готовность оформления. Ошибка тарифа не должна превращаться в
бесплатную доставку. Вход по телефону остаётся выключенным до выбора провайдера.

Официальная документация: https://apidoc.cdek.ru/.
