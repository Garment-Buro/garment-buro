# История заказов покупателя

`GET /api/auth/orders?limit=24&cursor=<id>` требует identity-сессию и
`orders.read_own`. Возвращает `{items, next_cursor}`; limit от 1 до 100,
cursor — положительный PostgreSQL integer. Порядок по ID от новых к старым.
Последняя страница имеет `next_cursor: null`. Новые заказы между запросами
не сдвигают уже выбранную границу. Число всех заказов не подсчитывается.

Карточка содержит ID, дату, принятую сумму, статус заказа/оплаты, известный
этап workflow и номер/статус доставки. Состав, кастомизация, контактные поля
и raw JSON старого заказа в список не загружаются. Одна SQL-выборка карточек
объединяет две ограниченные ветки: прямое владение и сохранённые legacy claims.
Пересечение убирается до окончательного LIMIT; каждый заказ виден один раз.
Состав доступен отдельным `GET /api/orders/{id}` с прежней проверкой владельца
либо staff-разрешения. Успешное чтение и 404 имеют `Cache-Control: no-store`.

Привязка ранее импортированных заказов к подтверждённому email сохранена.
Вместо получения всех ID и повторного большого INSERT используется один
`INSERT ... SELECT` только ещё не привязанных импортов, с conflict do nothing.
Существующая квитанция владения не обновляется и не передаётся другому
пользователю после смены email. Телефон и данные получателя не дают владение.

Миграция `20261017_0066` заменяет одиночные индексы владельца составными
`orders(user_id,id)` и `legacy_order_claims(user_id,legacy_order_id)`.
Обратная миграция восстанавливает прежние индексы; документы и суммы не меняет.
Границы ключа включают owner и ID. Это существенно для пустой ветки:
воспроизведённый план с одним `user_id = ...` выбирал глобальный PK и
отбрасывал 20 000 чужих строк. Теперь EXPLAIN ANALYZE на 40 000 строк проверяет
первую, глубокую и пересекающуюся страницы, отсутствие Seq Scan и не более
100 просмотренных строк на каждом узле чтения orders/claims при странице25.

Обе поверхности frontend (`ProfileOrders`, `AuthOrdersPanel`) используют
`useAuthOrders`: отдельные PagedResource для карточек и выбранного документа.
Ошибка следующей страницы сохраняет карточки и позволяет повторить ту же
границу; ошибка документа имеет отдельный повтор. Только выбранный ID из
списка текущего аккаунта может вызвать чтение документа. Смена account epoch,
выбор другого заказа, закрытие и unmount отменяют запрос; старые ответы
скрыты проверкой ключа аккаунта/ID. В localStorage история не сохраняется.
Этап показывается только из ответа backend; UI не выводит успешную оплату
из суммы, наличия заказа либо выбранного способа оплаты.

## Состояние заказа и подтверждение оплаты

Workflow теперь подписывает также `awaiting_payment` («Ожидает оплаты»),
`cancelled` («Отменён») и `attention` («Требуется проверка менеджера»).
`capture_pending`/`cancel_pending` по-прежнему показываются как модерация;
неизвестный или отсутствующий workflow возвращает null. Переходы, решения
модерации и обработка провайдера не менялись.

`customerStatus` — общая функция представления для OrderContent, ProfileOrders
и AuthOrdersPanel. Она показывает отдельно этап и `payment_status`:
pending — оплата не подтверждена, paid — подтверждена, failed — не прошла,
неизвестное значение — статус неизвестен. Зелёный знак требует paid и
известного положительного этапа; attention остаётся нейтральным, отмена
остаётся отменой даже при paid. Интерфейс не делает вывод о возврате денег.
Раскрытая история использует свежий документ вместо состояния старой карточки.

В OrderContent действие «Обновить статус» перечитывает документ с no-store.
Номер попытки входит в ключ UI: пока запрос идёт, прежнее состояние не
выглядит обновлённым; ошибка имеет повтор. Смена аккаунта и abort по-прежнему
исключают старый ответ. Обновление не вызывает checkout/payment-attempts.
Неактивная кнопка отслеживания удалена; реальные номер/статус СДЭК показаны
при наличии в документе. Старая ссылка /order/error больше не утверждает,
что заказ отсутствует; /order/success по-прежнему перенаправляет в профиль.

Проверка этого изменения:50 backend tests, два PostgreSQL concurrency tests
явно исключены (эта проверка не заменяет прежний полный прогон);459 frontend
tests, полный lint и production build. Матрица включает все workflow states
и неизвестные значения; сохранённые этапы совпадают в summary и документе.
Отрендеренные три UI проверены отдельно. Chromium с настоящим production-built
Next и синтетическими HTTP-ответами проверяет ожидание → подтверждение,
attention, отмену, удержанный refresh,503/retry, старую error-ссылку и
320/390/736/1280px. Зафиксировано ноль платёжных мутаций и ошибок JS.
Живые provider/webhook/worker сценарии требуют общего E2E выпуска.

Ответ `/api/auth/orders` изменился с массива полных документов на страницу
карточек. Frontend и backend этого релиза нужно выпускать вместе. Staff API
списка `/api/orders` и гостевой доступ `/api/order-access` не изменялись.

Локальная проверка 17.10: 46 focused API/service/migration tests; полный
backend851 без пропусков с PostgreSQL17/MinIO, Ruff; frontend452 без пропусков,
ESLint, production build/TypeScript. Chromium с настоящими Next/API/PostgreSQL:
24+5,503 следующей страницы/повтор,503 документа/повтор, старый принятый снимок,
выход в другой аккаунт при удержанном ответе. Отдельно проверен popup и его
узкая/короткая геометрия. Внешние провайдеры и production не проверялись.
