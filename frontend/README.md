# Frontend GARMENT BURO

Веб- и PWA-интерфейс проекта на Next.js 16 и React 19. Браузер обращается к backend через same-origin маршруты `/api/*` и `/uploads/*`; серверный адрес задаётся переменной `INTERNAL_API_URL`.

## Локальный запуск

Требуется Node.js 20.9+; CI и Docker используют Node24.

```bash
npm ci
INTERNAL_API_URL=http://localhost:8000 npm run dev
```

Приложение будет доступно на `http://localhost:3000`.

## Проверка перед коммитом

```bash
npm run check
npm audit
npm audit --omit=dev --audit-level=high
```

Команда `check` последовательно запускает ESLint, тесты и production-сборку.
Версии Next и ESLint-конфига зафиксированы на16.3.8. Результат и оставшиеся
dev-only advisories описаны в [dependency-audit.md](docs/dependency-audit.md).
После сборки `npm run check:analytics` запускает Chromium и настоящий standalone
для проверки границ публичной аналитики. Подробности и установка браузера —
[analytics-privacy.md](docs/analytics-privacy.md).

## Переменные окружения

- `INTERNAL_API_URL` — внутренний URL backend, по умолчанию `http://backend:8000`.
- `NEXT_PUBLIC_IDENTITY_SESSION_V2_ENABLED` — включает новую серверную авторизацию.
- `NEXT_PUBLIC_CATALOG_WRITES_ENABLED` — разрешает запись каталога; требует новую авторизацию.
- `NEXT_PUBLIC_CRM_CABINET_ENABLED` — включает кабинет CRM; требует новую авторизацию.
- `NEXT_PUBLIC_YANDEX_MAPS_API_KEY` — браузерный ключ Яндекс.Карт; ограничьте его разрешёнными доменами.

Полный набор переменных и безопасные значения по умолчанию находятся в корневом `.env.example`. Переменные с префиксом `NEXT_PUBLIC_` попадают в клиентскую сборку, поэтому секреты в них хранить нельзя.

## PWA-контуры

- публичные лендинги открываются в обычном браузере без установки;
- `/constructor` показывает установку, если страница открыта не в standalone PWA;
- основной manifest запускает `/?source=pwa`; прежний `id=/constructor` сохранён для уже установленного приложения;
- `partner.garment-buro.ru` получает отдельный manifest с `id`, `start_url` и `scope` для `/partner`;
- `widget.garment-buro.ru` разворачивается как отдельное приложение на своём origin.

Service worker регистрируется только в production-сборке. Он не кэширует API,
uploads и storage; переходы по страницам используют сеть с отдельной offline-страницей.
Отказ регистрации обрабатывается: обычный интерфейс продолжает работать.

## Публичная аналитика

Метрика работает в отдельном sandbox iframe с фиксированным адресом. SDK
не получает DOM страницы, cookies и localStorage; ему передаются только
разрешённые постоянные URL без query, hash, имён и идентификаторов. На приватных
маршрутах iframe отсутствует. Webvisor, автоматические клики, ссылки и ecommerce
отключены. Это ограничивает уникальных посетителей и атрибуцию; доступ к
сетевым метаданным у поставщика остаётся. См. [границы и проверку](docs/analytics-privacy.md).

## Чтение публичной витрины

`lib/api/http.ts` задаёт общий срок ожидания `PUBLIC_READ_TIMEOUT_MS` — 10 секунд
до завершения чтения JSON. `requestPublicJson` используют одежда, люди,
сообщества, параметры фильтров, товар конструктора и расчёт его цены. Отмена
владельцем запроса действует сразу; таймер и подписка освобождаются после ответа.
Автоматического повтора нет: интерфейс предлагает повторить запрос. При сбое
следующей страницы каталог сохраняет загруженные карточки и прежний cursor.
Первый SSR-запрос отдельно ограничен двумя секундами.

Если сервер отвечает 422 с `detail.code=invalid_cursor`, `lib/api/publicPages.ts`
переводит ответ в ошибку списка. Одежда, люди и сообщества сохраняют карточки и
предлагают «Обновить список»: первая страница заменяет прежние карточки и cursor.
Обычные ошибки 422 и сетевые ошибки не считаются истечением cursor. Повторная
отправка заведомо отклонённого cursor блокируется; автоматического сброса нет.

Покупка, авторизация, запись избранного и загрузка файлов имеют собственные
правила операций: срок публичного чтения на них не распространяется.

## Публичные и приватные изображения

Оптимизатор Next создаёт публичный кеш даже для исходного ответа `no-store`.
Поэтому API, подписанные ссылки S3 и private storage не входят в
`images.localPatterns`. `lib/media/imagePolicy.ts` задаёт разрешённые публичные
пути без query. Proxy также отклоняет непубличные источники и закодированные
алиасы до оптимизатора. Новую папку публичных картинок нужно явно добавить
в эту политику.

В корзине, checkout, истории и preview используется `CustomerMediaImage`:
публичный каталог сохраняет оптимизацию, приватные и подписанные ссылки идут
напрямую с `no-referrer`. Холст использует `RawMediaImage`, чтобы сохранить
геометрию и исходные данные. Права, сроки и `no-store` приватного файла задаёт
backend. Снижение общего `minimumCacheTTL` не заменяет эту границу.

## Синхронизация корзины

PostgreSQL хранит снимок гостевой корзины, localStorage — локальный кэш и
несинхронизированные изменения. `lib/cart/snapshotSync.ts` владеет очередью
одного документа: начальный GET и PUT выполняются последовательно; изменения,
сделанные во время PUT, объединяются в следующий актуальный снимок. Debounce
250 мс остаётся в store; очистка отправляется сразу после текущей операции.
Серверная ревизия защищает от записи старой вкладки. Поздний GET не заменяет
локальную правку: различие с изменившейся серверной версией требует выбора.

Ошибка HTTP не превращается в пустую корзину или успешную инициализацию.
Мобильная корзина и оформление заказа показывают общий `CartSyncNotice` с
ручным повтором. После ошибки записи локальные правки сохраняются; скрытого
цикла повторов нет. Публичный таймаут запросов витрины на запись не перенесён.
Начальный GET корзины ограничен 10 секундами, включая JSON и тело ошибки:
зависшее чтение освобождает очередь для текущих правок. PUT не получил
автоматического повтора или таймаута с неясным результатом записи.

PUT содержит `expected_revision` и случайный `operation_id`. Сервер сравнивает
ревизию под блокировкой PostgreSQL и отклоняет устаревшую запись409. При конфликте
пользователь выбирает серверный или локальный состав; обе операции сначала
читают текущую версию. Потерянный ответ повторяется с тем же ID и телом, включая
reload; сервер хранит результат последней операции. Старые локальные снимки
без ревизии не перезаписывают отличающийся серверный состав молча. Время браузера
не определяет порядок записи. Корзина остаётся гостевой по случайному ключу.

## Кабинет партнёра

Маршрут `/partner` показывает текущего партнёра на верхней подложке и открывает
основную панель управления внахлёст. В кабинете доступны реальные баланс и история
выплат, заявки на вывод, заполнение банковских реквизитов, готовые ссылки на лендинги,
текущие правовые документы и обращение в поддержку. Изменение названия и описания
партнёра, подписчики и сообщества в этот интерфейс не входят.

## Основная структура

- `app/` — маршруты, layout и серверные точки входа.
- `components/` — интерфейсные компоненты по предметным областям.
- `hooks/` — клиентские контроллеры и переиспользуемое поведение.
- `lib/` — API-клиенты, состояние, конфигурация и предметная логика.
- `public/` — используемые статические ресурсы и PWA-файлы.

Для запуска всего проекта вместе с PostgreSQL, Redis, MinIO и backend используйте Docker Compose из корня репозитория.

## Проверка административного каталога

Перед браузерной проверкой соберите release с
`NEXT_PUBLIC_IDENTITY_SESSION_V2_ENABLED=true` и
`NEXT_PUBLIC_CATALOG_WRITES_ENABLED=true`, затем выполните
`npm run check:admin-catalog` из frontend. Gate запускает свой standalone Next
и Chromium с синтетическим HTTP backend, не пишет в действующие аккаунты,
не обращается к внешним сайтам и очищает свои процессы/файлы.
Он проверяет24+9 карточек, ошибки/повтор дозагрузки, отмену поиска,
серверные фильтры, invalid cursor/refresh, bearer и сбой/повтор детали.
Роли, настоящее SQL-наличие и20 000 товаров отдельно проверяет backend pytest.

Публичные списки и управление используют общий `usePagedCatalog`; только
публичный wrapper повторно использует совпавшую SSR-страницу. Private списки
имеют владельца сессии, отмену запросов и не сохраняются в localStorage.

Редактор товара теперь один: `ProductEditorDialog` и `useCatalogProductEditor`.
Production передаёт cookie-клиент, прямые admin-адреса — Bearer-клиент через
`catalogEditorClients`. Старые формы/variantOptionsStore удалены. Выбор моделей
и разрешённых тканей использует страницы24 и отдельное чтение выбранных ID;
`check:admin-catalog` также проверяет записи за первой сотней, оба upload пути,
физический товар и размеры общего диалога, включая736×390.

Деталь товара содержит `version`; существующий товар отправляет её как
`expected_version`. При `catalog_product_version_conflict` черновик остаётся
в форме, повторный PUT блокируется. Открытие актуальной версии требует явного
действия и заменяет черновик только после успешного чтения. Browser gate покрывает
оба входа и возврат к черновику при ошибке такого чтения.

Административные лендинги читаются через `useAdminLandingDirectory` страницами24:
production открывает их по запросу, identity `/admin/partners` — своим reader.
Summary содержит `product_count` и `version`, публикация — status/expected_version.
Карточки каталога получают variant_count/sku; production дополнительно получает
community_count и до3 communities;
полная деталь с вариантами и фотографиями читается при открытии редактора. Ошибки, поиск,
cursor, граница аккаунта и публикация из summary покрыты browser gate.

Сведения о членстве товара в лендингах включены только для production.
В identity/CRM каталоге community_count и счётчик лендингов могут быть null:
это отсутствие этих данных в данном чтении, а не нулевое членство.

Основной интерфейс товаров — `/production?section=presets`; старые `/admin/models` и `/admin/products/*` перенаправляют туда. Производственная сессия и системные права обязательны. Поиск товаров для коллекции постраничный, выбранные ID/порядок сохраняются независимо от страницы; лимит 50. См. `docs/superpowers/plans/2026-10-18-primary-presets.md`.

Партнёры: отдельные страницы справочника и выбора владельца читают по 24 записи.
Выбранный профиль не зависит от поиска/страницы; команды меняют revision, отменяя
запоздалые чтения. История выплат имеет самостоятельное состояние, ошибки/повтор
и продолжение после 100; её массив больше не загружается в usePartnerCabinet.
Чтения используют no-store, отмену по аккаунту и срок ожидания 10 секунд.
См. `docs/superpowers/plans/2026-10-18-partner-private-reads.md`.

Кабинет владельца: owner list возвращает краткие карточки с product_count;
полный контент читается через detail endpoint. Dashboard содержит has_requisites
без банковских полей; отдельный редактор реквизитов читает их по открытию блока.
Ошибка этого GET не закрывает кабинет и не разрешает пустое сохранение.
DTO требуют согласованного выпуска frontend/backend. Подробности:
`docs/superpowers/plans/2026-10-18-owner-cabinet-boundaries.md`.


### История клиента производства

Карточка клиента получает профиль отдельно; заказы и обращения читаются при
открытии вкладки по 24 записи через `/api/production/admin/clients/orders`
и `/tickets`. `useProductionClientHistory` использует существующий
`PagedResource`, отмену, срок чтения и поколение производственной сессии.
При создании тикета доступны все страницы заказов без сброса черновика.
Проверка браузером после production-сборки: `node scripts/check-client-history.mjs`
(синтетический HTTP backend; SQL и права проверяются backend-тестами).
