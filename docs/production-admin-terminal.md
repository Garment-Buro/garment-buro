# Терминал администратора

Единый адрес входа после развёртывания: `production.garment-buro.ru/production`. Форма одна для всех ролей: после ввода личного кода административная сессия автоматически открывает админку, а сотрудник попадает в свой рабочий терминал. Старый адрес `/production/admin` перенаправляет на общий вход. Ссылка «Производство» появляется только у администратора, которому также назначен хотя бы один участок; прямой переход без участка показывает понятное сообщение вместо чужого рабочего места.

## Разделы

- Все заказы: поиск по номеру, имени, почте, телефону; фильтр статуса; постраничная загрузка; состав, параметры конструктора и доставка выбранного заказа. Показаны и неоплаченные заказы, не только производственная очередь. Современные этапы берутся из order workflow, для старых заказов — сохранённый legacy-статус.
- Заявки на выплаты: партнёр, сумма, статус заявки, состояние банковской операции, комментарий. До передачи в банк можно одобрить или отклонить заявку с обязательным комментарием. Решение фиксируется через существующий партнёрский сервис в одной транзакции с аудитом. Повтор/устаревшее состояние возвращает 409; UI предлагает обновить данные.
- Сотрудники: создание и изменение производственного сотрудника, один или несколько участков, основной участок, доступность, блокировка и одноразовая выдача нового личного кода. Фамилия, телефон и почта необязательны. Поиск работает по имени, телефону, почте, ID и действующему коду; сам код в ответах API не раскрывается. Существующий активный цеховой код автоматически восстанавливает отсутствующую запись сотрудника, а миграция выравнивает уже выданные доступы.
- Клиенты: зарегистрированные покупатели с заказами и гостевые группы. Аккаунты группируются строго по user_id, гости — по сохранённой почте, затем телефону; без контактов заказ остаётся отдельной группой. Гости не объединяются с зарегистрированным аккаунтом автоматически. Совпадение контактных данных не доказывает совпадение личности. Контакты показываются из последнего заказа по ID.
- Проблемы: сообщения, созданные действием `report_issue` в цеховом терминале. Запись содержит участок, заказ, проект и единицу изделия; повторную открытую проблему для той же вещи создать нельзя. При `resolve_issue` или `rework` связанная запись автоматически получает статус `resolved`. Миграция переносит уже открытые значения `production_work_items.issue` в этот inbox.
- Поддержка: сообщения авторизованных пользователей о сайте, оплате и заказах. `POST /api/support` принимает текст, необязательную тему и необязательный номер только собственного заказа; сохраняет снимок контактов автора и возвращает ID обращения. Для одного аккаунта действует предел 10 обращений в час.
- Товары и склад: семь вложенных разделов для моделей, лекал, техкарт, тканей, фурнитуры, коробок и товаров. Администратор создаёт и изменяет размерные сетки, загружает файлы лекал и изображения, задаёт расход ткани и фурнитуры, правила упаковки, версии техкарт и варианты товаров. Интерфейс использует текущую production-сессию; отдельный вход или identity token не требуется. Запись справочников остаётся под флагом `CRM_WRITES_ENABLED`, запись товаров дополнительно требует `CATALOG_WRITES_ENABLED`.
- Статистика за всё время: количество заказов, аккаунтов, клиентских групп; сумма всех заказов и сумма заказов с payment_status=paid; распределение заказов и заявок по состояниям. Суммы включают доставку, не являются чистой выручкой и не вычитают возвраты/комиссии. Неподтверждённый холд не засчитывается как paid.

Удаление сотрудников, ответы пользователю из поддержки, создание и подписание банковских платёжек в этой версии интерфейса отсутствуют. Никакие реальные выплаты при разработке не создавались. Одобрение заявки не равно переводу денег.

## Специальный личный код

Для администратора — **8 цифр: 99 + 6 случайных цифр**. Для цеха сохранены шестизначные коды. Это не общий пароль и не порядковый номер. Длина отделяет административный код от кода отправки, который также может начинаться на 99.

Новая роль `production_admin` даёт только `production.access` и `production.admin`. Рабочие роли, включая технолога, не получают эти разрешения автоматически. Общая роль платформы `admin` имеет административное разрешение, но тоже должна войти отдельным административным кодом.

Проверяется не только роль аккаунта, но и категория credential, которым получена текущая сессия. Выдача роли админа сотруднику с уже открытой цеховой сессией не повышает права этой сессии. Нужен перевыпуск личного кода с категорией admin. Коды по-прежнему хранятся как HMAC, сессии изолированы от основного identity API, POST проверяет Origin, действуют общие лимиты входа и немедленный отзыв доступа. Рекомендовано дополнительно ограничить административный доступ сетью производства/VPN; сетевые правила этим изменением не менялись.

После применения миграций до `20260914_0043` оператор выдаёт роль существующему активному пользователю штатным скриптом с проверкой ID:

```sh
python -m scripts.bootstrap_role --email EMAIL --role production_admin
python -m scripts.bootstrap_role --email EMAIL --role production_admin --apply --expect-user-id ID
python -m scripts.production_code --user-id ID --station admin
```

Последняя команда запускается в интерактивном терминале, показывает код один раз и отзывает прежние коды этого сотрудника. Код не должен попадать в Git, журналы CI или этот документ. Администратора нужно выбрать явно; реальные назначения ролей данным изменением не выполнялись.

## Архитектура и проверка

Сервер: отдельные admin router/read projections, inbox service/repository и авторизованный intake поддержки; переиспользованы production auth, identity permissions, партнерский сервис рассмотрения заявок. Данные читаются из основной БД, отдельной базы клиентов/копии заказов не создаётся. Все запросы ограничены страницами до 100 записей, ответами no-store и проверкой прав на backend; скрытых кнопок недостаточно для доступа. Реальные сотрудники не видят и не меняют учебные заказы, а учебные аккаунты — реальные.

Frontend: отдельные экран, адаптивные карточки списков, детали заказа, формы сотрудников и обращений, статистика, товарный workspace, типы данных и hooks загрузки. Товарные формы разбиты по предметным разделам, вложенные списки размеров, операций и вариантов превращаются в карточки на телефоне, а редактор открывается полноэкранно. Списки основной админки тихо обновляются раз в 30 секунд, очередь цеха — раз в 20 секунд, но только в видимой вкладке. Навык `landing-page-design` использован для структуры разделов, состояний интерфейса, мобильной плотности и размеров элементов; сохранены фон и визуальный характер производственного терминала. На вложенных страницах отключены маркетинговая заставка и cookie-баннер, как на основном production-экране.

Проверено локально 18 сентября 2026 года: backend `make check` — 460 тестов прошли, 3 PostgreSQL-зависимых сценария пропущены, Ruff и offline Alembic upgrade/downgrade прошли; frontend `npm run check` — 285 тестов, ESLint, TypeScript и production build прошли. Контрактные тесты дополнительно проверяют наличие семи товарных разделов, production admin API и одноточечный мобильный layout. API-тесты покрывают отказ цеховым сотрудникам, отсутствие повышения старой сессии, пагинацию, фильтрацию, отсутствие секретов в ответах, создание поддержки, связь производственной проблемы с inbox и разделение учебных/реальных заказов.

**Развёртывание этим документом не подтверждается.** Для выкладки нужны согласованное обновление frontend/backend, миграции `20260914_0043` и `20260918_0044`, включённые флаги записи, затем публичная проверка входа, товарных форм, мобильных списков и загрузки медиа. Локальные тесты не являются подтверждением работы live production.
