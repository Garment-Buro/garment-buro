# Главные сущности товара и производства

Документ фиксирует целевую предметную модель. Он не создаёт второй каталог: публичные товары
остаются в `catalog`, а производственные справочники и складские нормы развиваются в `crm`.

## Главная логика

1. **Модель изделия** — производственная основа вещи. В ней находятся собственная размерная
   сетка, вес, фотография размерной сетки, лекала, техкарта и нормы материалов.
2. **Товар** — коммерческое представление модели: название, описание, цена, старая цена, slug,
   категория, активность, остаток и медиа. Один товар относится максимум к одной модели. Одна
   модель может использоваться несколькими товарами.
3. **Вариант товара** уточняет размер, цвет и остаток. Внутренне вариант может ссылаться на
   точный размер модели и конкретную ткань; текстовые `size`/`color` сохранены для действующего
   публичного контракта.
4. **Лендинг партнёра** не создаёт отдельную копию товара и не меняет владельца товара. Он
   размещает выбранные канонические товары. Это позволяет один раз менять цену, остаток,
   модель и варианты.
5. **Техкарта** принадлежит модели, имеет неизменяемые ревизии и шаги. Каждый шаг содержит
   производственный этап и роль исполнителя. Опубликованная ревизия не переписывается.
6. **Лекало** принадлежит модели и конкретному размеру. Оно задаётся для точной точки сетки:
   ширина и длина обязательны, длина рукава и рост/высота вариативны. Все оси идут с шагом
   2 см от нижней границы размера. Файл хранится через `media_objects`, а не URL-строкой.
7. **Склад** разделяет справочник и движение остатка. Для ткани уже используется отдельный
   журнал поступлений, резервов, списаний и корректировок в метрах. Минимальный остаток хранится
   в карточке ткани. Фурнитура и коробки пока имеют версионируемый остаток в штуках; следующим
   складским этапом их нужно перевести на общий журнал движений.
8. **Состав модели (BOM)** задаётся нормами: метры ткани с процентом отхода и количество
   фурнитуры на единицу изделия. Допустимая ткань варианта обязана входить в нормы модели.
9. **Упаковка** — отдельный справочник коробок. Правило упаковки связывает коробку с моделью,
   задаёт фактическую вместимость для этой модели и приоритет выбора.

## Реализованные сущности

| Сущность | Назначение | Основные ограничения |
| --- | --- | --- |
| `ProductCategory` | Категория товара | уникальный slug, версия, архивирование через `is_active` |
| `Product` | Публичный товар | slug, категория, модель, цены, активность, остаток, медиа |
| `ProductVariant` | Размерно-цветовой вариант | точный размер модели и разрешённая ткань |
| `CrmGarmentModel` | Производственная модель | вес, размерная сетка, фото сетки, версия |
| `CrmGarmentSize` | Диапазоны одного размера | рост/высота, длина, ширина, рукав, сортировка |
| `CrmGarmentPattern` | Файл лекала для точки сетки | уникальная комбинация измерений, шаг 2 см, ready media |
| `CrmTechCard` | Техкарта модели | одна карта на модель, ревизии draft/published/archive |
| `CrmTechCardCheckpoint` | Операция техкарты | позиция, этап, роль, время и стоимость труда |
| `CrmFabric` | Карточка ткани | состав, цвет, ширина, плотность, цена/метр, минимум |
| `CrmGarmentFabricRequirement` | Расход ткани | метры на изделие, отход, одна основная ткань |
| `CrmAccessoryCategory` | Категория фурнитуры | код, название, активность, версия |
| `CrmAccessory` | Фурнитура | цена, фото, остаток, минимум, доступность |
| `CrmGarmentAccessoryRequirement` | Применимость/BOM фурнитуры | модель, количество, обязательность, примечание |
| `CrmPackagingBox` | Коробка | внутренние габариты, общий предел, цена и остаток |
| `CrmGarmentPackagingRule` | Упаковка модели | коробка, вместимость именно этой модели, приоритет |

## API

Чтение производственных справочников требует `crm.access`. Изменение дополнительно включается
флагом `CRM_WRITES_ENABLED`; все update-запросы используют `expected_version`.

- `GET/POST/PUT /api/product-categories`
- `GET /api/crm/assortment/products`
- `GET/POST/PUT /api/crm/reference/fabrics`
- `GET/POST/PUT /api/crm/reference/garment-models`
- `POST /api/crm/reference/garment-models/{id}/products`
- `POST /api/crm/reference/garment-models/{id}/tech-cards`
- `POST /api/crm/reference/tech-cards/{id}/revisions`
- `POST /api/crm/reference/tech-cards/{id}/revisions/{number}/publish`
- `POST /api/crm/reference/tech-cards/{id}/revisions/{number}/discard`
- `GET/POST/PUT /api/crm/assortment/patterns`
- `GET/POST/PUT /api/crm/assortment/fabric-requirements`
- `GET/POST/PUT /api/crm/assortment/accessory-categories`
- `GET/POST/PUT /api/crm/assortment/accessories`
- `GET/POST/PUT /api/crm/assortment/accessory-requirements`
- `GET/POST/PUT /api/crm/assortment/boxes`
- `GET/POST/PUT /api/crm/assortment/packaging-rules`
- существующие `/api/crm/materials/...` — поступление, резерв, расход и корректировка ткани.

## Что пользователь не назвал, но понадобится

Следующие сущности не следует маскировать полями в уже созданных таблицах:

1. **Поставщики и закупочные партии.** Цена ткани или фурнитуры меняется от партии; карточка
   материала не должна терять историческую закупочную стоимость.
2. **Рулоны ткани.** Остаток в метрах недостаточен для раскроя: понадобятся номер рулона,
   фактическая ширина, партия, оттенок, брак и складская ячейка.
3. **Склады и ячейки.** Сейчас баланс общий. При появлении нескольких помещений нужны
   `warehouse/location/bin` и перемещения между ними.
4. **Единый штучный ledger.** Фурнитуру и коробки нужно проводить через поступления, резервы,
   списания, инвентаризацию и идемпотентные движения, как сейчас ткань.
5. **Ревизии состава модели.** Заказ должен хранить снимок BOM, иначе изменение расхода модели
   поменяет расчёт уже запущенного изделия.
6. **Ревизии лекал.** Для запущенного производства требуется неизменяемая опубликованная версия,
   а не только текущий активный файл.
7. **Штрихкоды/SKU поставок.** Нужны для приёмки и инвентаризации с телефона или сканера.
8. **Себестоимость.** Отдельный расчёт из ткани, фурнитуры, труда, упаковки и отходов; цена
   продажи не должна использоваться вместо себестоимости.
9. **Нормализация товаров лендинга.** Сейчас партнёрский лендинг хранит `product_ids` как JSON.
   Для строгих внешних ключей, сортировки и индивидуальной видимости нужна таблица связи
   `partner_landing_products`; это отдельная безопасная миграция.

## Рудименты и совместимость

- `crm_catalog_product_model_links` удаляется миграцией после переноса данных в
  `products.garment_model_id`. Планирование производства, справочники и API читают одну
  каноническую связь; downgrade восстанавливает старую таблицу из нового FK.
- Строковые `products.sizes`, `products.colors` и `product_variants.size/color` остаются в
  публичном контракте. Новые FK дают точную производственную связь, после миграции всех данных
  строковые поля можно оставить только как отображаемые снимки.
- Изображения товара уже нормализованы через `media_objects`; новые сущности используют тот же
  механизм и не создают ещё одну таблицу файлов.
