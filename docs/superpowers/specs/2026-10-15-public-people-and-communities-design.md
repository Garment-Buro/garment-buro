# Реальные люди и сообщества

Основание: уточнение пользователя 15.10.2026. Люди — пользователи с публичными
профилями: владелец редактирует свой профиль, другие читают публичную страницу.
Сообщества — опубликованные лендинги с коллекциями; владельцы сообществ
управляют своими коллекциями и лендингами. Это разные предметные области.

## Границы данных

- Identity User остаётся аккаунтом. Публичный профиль хранится отдельно,
  принадлежит одному User и содержит только явно опубликованные поля:
  адрес/slug, публичное имя, описание и изображение. Публикация явная;
  существующие аккаунты автоматически не публикуются. Email, phone, дата
  рождения, размеры, заказы, черновики, сессии и права не входят в public DTO.
- Community directory читает существующие PartnerLanding и PartnerProfile.
  Нет второго справочника сообществ и копии JSON landing content. Публикация,
  выбранные товары и текущие `/p/[slug]` остаются источником истины.
- Владелец сообщества — User с существующим PartnerProfile и partner permissions.
  Не каждый пользователь получает права партнёра. Owner mutation выводит
  partner_id из текущей identity, а не принимает его от клиента. Администратор
  сохраняет существующие административные полномочия.
- Опубликованное сообщество доступно только при active partner и active User.
  Draft/archived/suspended/blocked/deleted отсутствуют в directory и по ссылке.
- Избранное сообщества хранится в PostgreSQL отдельно от избранного товара:
  FK на User и PartnerLanding, уникальная пара, idempotent PUT/DELETE. Preview
  IDs не мигрируют в реальные записи: они не доказывают выбор реального landing.

## Чтение и интерфейсы

Оба каталога используют ограниченные серверные выборки, keyset pagination и
компактные DTO. Поиск не загружает всю таблицу в браузер; public reads не
зависят от пользовательских cookies. Начальные карточки главной рендерятся
на сервере параллельно с одеждой, без повторного первого browser GET.
Пустой ответ, ошибка и загрузка имеют отдельные состояния и явный retry.

Карточка сообщества открывает настоящий `/p/[slug]`, а не повторённую картинку.
Карточка человека открывает его публичный профиль; владелец может открыть
редактирование. Публичная карточка без фото использует визуальный placeholder,
не фотографию другого человека. Формы сохраняют подтверждённые backend данные;
pending operations и поздние ответы привязаны к account lifetime.

## Последовательность самостоятельных этапов

1. Session/profile ownership: guarded refresh/restore/logout/write; token rotation
   сохраняет draft, новый login/account отменяет старый результат.
2. Реальный directory и избранное сообществ, замена hardcoded/repeated community
   cards, SSR главной и поиск/пагинация. Без изменения партнёрских финансов.
3. Публичные профили пользователей: schema/migration, владелец редактирует и
   публикует, безопасное фото/lifecycle, публичная страница/каталог/SSR;
   удаление servicePeople и локального serviceFavoritesStore после последнего
   потребителя. Изменение публичного профиля не изменяет приватный аккаунт.
4. Owner create/edit/publish коллекции через существующие валидаторы и UI
   партнёра; запрет чужих записей, проверки доступности товаров и concurrency.

Это порядок реализации, а не уменьшение объёма релиза. Карта и журнал показывают
как реализованное поведение, так и оставшиеся этапы. Production не изменяется
до необходимых проверок выпуска; локальные изменения не commit/stage/push.

## Доказательства

SQLite + реальный PostgreSQL: ограничения, ownership, публикация, literal
поиск, bounded SQL, отсутствие N+1/private fields, избранное между клиентами
и после restart. Migration upgrade/downgrade и совпадение ORM metadata.
Frontend: реальный HTTP boundary, отмена/смена account, ошибки/retry, pagination.
Браузер: SSR без JavaScript, выбранные ссылки, private/public/other-account,
320/390/736/1280, нормальный и отсутствующий контент, отсутствие JS ошибок.
Фото проверяется с реальным MinIO, очистка — при снятии публикации/смене фото/
удалении аккаунта. Full tests/build/lint и независимое ревью каждого этапа.
