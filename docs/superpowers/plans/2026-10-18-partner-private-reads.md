# Партнёры и история выплат: ограниченное чтение

Статус: локальный этап рефакторинга. Это не выпуск на сервер. Основной кабинет товаров остаётся «Производство → Пресеты».

## Что подтвердил аудит

- Административный GET `/api/admin/partners` читал все профили. Один массив одновременно кормил справочник и выбор владельца лендинга. Запоздавший начальный GET мог заменить список после успешного создания партнёра.
- GET `/api/partner/payouts` молча возвращал максимум 100 записей без продолжения. Кнопка «Все» показывала только этот обрезанный массив.
- Показатели кабинета уже считались на сервере в SQL, а не в браузерном кэше. Но один баланс собирался шестью SELECT: визиты, заказы, начислено, созрело, зарезервировано и выплачено.
- Точные старые списковые GET `/api/partner/landings` и `/api/partner/commissions` не имели потребителей в текущем frontend. Первый был неограниченным, второй также скрыто обрезался.

## Что изменено

`PartnerReadRepository` выбирает только необходимые столбцы. `PartnerReadService` отвечает за cursor и DTO, маршруты — за прежние права. `read_schemas.py` отделяет списковые контракты от команд.

Справочник профилей: поиск по имени/коду, статус, режим selectable, limit 24 по умолчанию и максимум 100, порядок ID по убыванию. Cursor привязан к фильтрам; смена размера страницы допускается. Символы %, _ и обратный слеш в поиске буквальные, PostgreSQL поддерживает Unicode-регистр. Выбор владельца использует отдельный небольшой компонент и собственные страницы; приостановленные профили не предлагаются. Выбранный профиль хранится отдельно от результатов поиска. Созданный сервером профиль сразу становится выбором формы, а изменение revision отменяет старое чтение. В `useAdminPartners` остались команды, а не копия всего справочника.

История выплат: `{items,next_cursor}` с limit 24/max100, прежний порядок created_at DESC дополнен ID DESC для одинаковых дат. Cursor содержит владельца и позицию даты/ID. Первая область показывает три записи, раскрытие — загруженную страницу, далее есть «Ещё выплаты». Чтение истории отделено от загрузки основного кабинета; отказ виден внутри истории. Создание заявки обновляет историю с сервера. Прежние записи не теряются при ошибке продолжения; неверный cursor требует явного обновления.

Показатели: одна SQL-команда с независимыми агрегатами. Визиты и заказы не перемножают комиссии и выплаты. Decimal, удержание комиссии, статусы резервирования, нижняя граница ноль и блокировка профиля при создании заявки сохранены. Redis здесь не добавлен: денежный баланс читается из основного источника под прежними правилами согласованности.

Удалены неиспользуемые списковые маршруты и их функции/DTO. Публичный `/api/partner/landings/{slug}` и текущий owner editor `/api/partner/own-landings` сохранены.

Миграция `20261018_0071` добавляет индексы `(status,id)` профилей и `(partner_id,created_at,id)` выплат. Новых финансовых полей и переноса денежных данных нет. Изменённые контракты списков требуют согласованного выпуска frontend/backend.

## Проверки

Контрактные проверки выполняются на SQLite и настоящем PostgreSQL: 130 профилей, 134 выплаты владельца, продолжение после 100, одинаковые даты, поиск/статусы, запрет чужого cursor, лишних параметров и превышения лимитов. По одной странице и один расчёт показателей выполняются одной SQL-командой каждый и не загружают ORM-объекты/связи. Проверяется отсутствие реквизитов в проекции профилей.

Нативная проверка миграции проходит upgrade → downgrade → upgrade, сохраняя профиль, сумму 10.01 ₽, статус и примечание выплаты. Полный backend: 1039 passed, 0 skipped за 296.94s на Python 3.12.12 с отдельными PostgreSQL 17/MinIO. Временные процессы, данные и конфигурация удалены. Frontend: 551 passed, 0 skipped; lint/build и браузерный gate прошли. Остались прежние предупреждения CustomerMediaImage alt, Alumni Sans SC fallback и тестового клиента Starlette. Ruff и форматирование проходят.

Frontend проверяет типы ответов, авторизацию, предел страницы, старые массивы как явную ошибку, таймаут, отмену и восстановление cursor. Браузерный `check:admin-catalog` использует настоящий standalone Next/Chromium и синтетический HTTP API; отдельно проверены 130 профилей/выплат, страницы выбора владельца, его сохранность при поиске, создание во время позднего чтения, ошибки/повтор, статус, cursor и ширины 320/390/736. SQL/RBAC подтверждаются отдельными backend тестами.
