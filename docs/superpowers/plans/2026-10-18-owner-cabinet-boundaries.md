# Кабинет владельца: краткий список и независимые реквизиты

Этап выполнен локально. Изменения не закоммичены, не отправлены и не опубликованы. Основной кабинет товаров — производство → «Пресеты».

## Проблема и результат

Owner list раньше читал полные ORM лендинги с content и всеми product_links для каждой из 24 записей. Теперь SQL выбирает только id/version/slug/title/image_url/status/product_count. Один запрос ограничен limit+1; полный текст и product_ids читаются отдельно при открытии редактора. Командный ответ превращается в краткую карточку перед обновлением списка, поэтому после сохранения полная деталь не размножается в массиве списка. Поиск доступных товаров, порядок коллекции, CAS версии лендинга и публикация сохранены.

Список и деталь используют no-store и срок ожидания 10 секунд. Cursor остаётся привязанным к владельцу; неизвестные параметры и пустой cursor отклоняются. Ошибка продолжения сохраняет карточки. Неверный cursor убирает неработающее продолжение и предлагает обновить список. Неудачный GET детали не открывает пустую форму.

Реквизиты раньше загружались одновременно с dashboard через Promise.all; отказ чтения или расшифровки прятал кабинет. Теперь сводка возвращает только has_requisites, полученный индексированным EXISTS в той же SQL-команде показателей. Банковские поля не попадают в сводку, расшифровка не вызывается. Полные реквизиты запрашиваются только при открытии своего блока. Для сохранённой записи закрытый блок сначала показывает только подтверждённый сервером факт наличия.

## Разделение состояния

- `usePartnerCabinet`: финансовая сводка, отдельная история выплат и команда заявки. У него больше нет банковского черновика и операции сохранения реквизитов.
- `PartnerRequisitesCard → usePartnerRequisites → RequisitesEditor`: самостоятельная загрузка и форма банковских данных. Дополнительного Provider нет. Реквизиты не передаются через общий объект кабинета.
- Чтение с ошибкой отличается от подтверждённого null: при ошибке формы и кнопки сохранения нет; null разрешает создание. Неизвестное или неверное тело ответа не превращается в пустую запись.
- При сохранении поля и закрытие блока блокируются; повторный запрос не отправляется. Отказ оставляет черновик. Закрытие и повторное открытие сохраняют несохранённый ввод в памяти этого аккаунта. Закрытие во время GET отменяет чтение; запоздавший ответ не возвращается в блок.
- Смена аккаунта/epoch отменяет старые запросы и отделяет данные. Подтверждённые записи хранятся на сервере в существующем зашифрованном виде; localStorage и JSON-файлов для реквизитов нет.
- Обновление сводки после PUT реквизитов — отдельное чтение. Успешная запись остаётся успешной при его отказе.
- Подтверждённая POST заявка выплаты также не становится ошибкой из-за последующего GET. Уведомление о создании сохраняется; при недоступной или обновляемой сводке новая отправка заблокирована до свежих данных. Ручной повтор чтения не повторяет POST.

Схема БД не менялась; текущая последняя миграция — `20261018_0071`. Изменены DTO owner list и dashboard: frontend/backend должны выпускаться согласованно.

## Проверки

Полный backend: **1043 passed, 0 skipped**, 289.51s на Python 3.12.12, отдельных PostgreSQL 17 и настоящем MinIO. Временные процессы/данные/конфигурация удалены. Новые контрактные проверки идут на SQLite и PostgreSQL: 130 лендингов с валидным контентом около 10 КБ каждый; первая страница меньше 12 КБ; ровно семь полей карточки, один SELECT без ORM объектов и чтения content/description, доступность полной детали и порядок product_ids. Чужой cursor не принимается.

Наличие реквизитов проверяется до и после настоящего зашифрованного сохранения. При принудительно недоступной расшифровке dashboard и список сообществ работают, GET реквизитов возвращает 503. В DTO сводки банковских полей нет.

Frontend: **559 passed, 0 skipped**, lint/build. Domain tests проверяют запрет пустого overwrite после ошибки чтения, создание только после null, сохранность черновика, одиночное сохранение, отмену GET при закрытии и смену аккаунта во время записи. Проверяются также краткая карточка после команды и отказ старого полного формата списка.

Браузерный `check:admin-catalog`: настоящий standalone Next/Chromium с синтетическим HTTP API; SQL/RBAC отдельно проверяются pytest. 130 кратких owner карточек, отсутствие detail prefetch, cursor/ошибка продолжения/повтор, отказ детали без пустого редактора. Закрытый блок не вызывает GET реквизитов; ошибки чтения/записи остаются внутри блока, поля не очищаются, повторное сохранение блокируется. Ошибка сводки после подтверждённых PUT/POST исправляется чтением без повторной команды. Открытая банковская форма проверена на 320/390/736/1280 px. Остаются прежние предупреждения CustomerMediaImage alt, Alumni Sans SC fallback и тестового клиента Starlette.
