# Переключение фоновых workers при выпуске

Статус: локальное исправление скрипта; весь релиз продолжается.

Следующий [этап остановки приложений](2026-10-19-deployment-application-cutover.md)
закрыл описанное ниже ограничение работающего API при миграциях: API/frontend
теперь тоже приостанавливаются. Числа проверок ниже относятся к этому этапу.

## Найденное поведение

`remote-deploy.sh` передавал в `compose up` только workers, включённые флагами
нового релиза. Уже работающий worker, выключенный новым флагом, оставался
со старым образом и настройками. Новые workers запускались вместе с API и
frontend до HTTP-проверок. Частичная остановка старого набора и миграция до
переключения API не имели отдельного пути восстановления workers.

## Исправление

1. Сохраняется набор ранее работавших workers, существующих в прежнем Compose.
   После проверки копии и подготовки инфраструктуры этот набор останавливается
   перед миграциями. Состояние паузы фиксируется до stop, чтобы обработать
   частично выполненную команду.
2. Новый API/frontend запускаются отдельно. Проверяются readiness и четыре
   страницы; только затем запускается набор workers из новых флагов.
   Выключенные workers остаются остановленными. Текущие семь сервисов включают
   `payment-reconciler` и `order-workflow-worker`; последний требует обоих
   платёжных флагов.
3. До создания новых workers ошибка возвращает прежние существующие контейнеры
   командой `start`, сохраняя их образ и окружение. После начала их пересоздания
   сначала останавливается выбранный кандидатный набор, затем возвращаются
   прежние приложения и ранее работавшие workers. Спящие сервисы не включаются.
4. Частичный сбой восстановления явно сообщает о ручном восстановлении.
   Пойманные INT/TERM проходят через тот же обработчик с кодом130/143.
   После успешного отката возвращается прежняя `.release`, в том числе если
   ошибка произошла уже после записи новой метаинформации.
5. Пустые массивы profiles/workers не передаются через небезопасное для
   Bash3 сочетание nounset/пустого array expansion. Выпуск без workers допустим.

Список workers определяется прежним запущенным набором и текущими флагами;
нового реестра или второго источника бизнес-данных нет. PostgreSQL, MinIO,
модель товаров и клиентские Provider этим этапом не менялись.

## Проверки и границы

61 профильная проверка/0skip:21 сценарий release и40 backup/verifier.
Проверены все workers при полном отключении и двух выбранных наборах,
отсутствие workers во время миграции и пяти HTTP-проб, ошибка приложения,
HTTP, миграции, частичной остановки/запуска, обеих веток восстановления,
поздней записи метаданных, INT/TERM и отсутствие активации спящих сервисов.
Скрипт реально выполняется Bash3.2; Docker и Linux host tools эмулируются.
Shell syntax, Ruff и format696 проходят.

Карта обновлена:18 offline Chromium-сценариев,320/390/736 px, выбор сохраняется
после reload, нет ошибок JS и сетевых запросов. Проверены664 ссылки file:line,
включая deployment и workflow-файлы. Размер fragment997521 байт; прежние
перезаписывавшиеся строки сводки удалены без удаления исходных доказательств.

Настоящие контейнеры и GitHub Actions здесь не запускались: локально нет Docker
CLI или другого контейнерного runtime. Эти проверки доказывают поведение
shell-оркестрации, не восстановление старого образа на новой схеме и не работу
платёжных/почтовых провайдеров. Предыдущий полный набор1227 backend/0skip и
621 frontend/0skip не повторялся: runtime API и frontend не менялись.

Сам API во время миграции пока остаётся работающим. Требование совместимости
старого образа с новой схемой сохраняется; автоматического downgrade нет.
После пересоздания workers откат использует сохранённый Compose и текущий
`.env`: изменения конфигурации/секретов автоматически не откатываются.
Полный rollback старого образа/окружения, контейнерный выпуск, производственный
объём, SIGKILL/сбой хоста и внешние unmanaged writers остаются воротами релиза.
