# Пакетная проверка состава пресета

Статус: локальный этап общего рефакторинга. Основной редактор товаров — производство → «Пресеты».

## Подтверждённая проблема

`CatalogWriteService._validate_product_references` вызывал отдельную проверку каждой строки. Размер загружался как ORM-объект, ткань — другим SELECT, применимость ткани к модели — третьим. При матрице200 вариантов число обращений росло вместе с матрицей, даже когда размеры и ткани повторялись. Кэш identity map не давал надёжной границы и мог вернуть устаревший активный размер/категорию.

Теперь сервис сначала собирает уникальные `garment_size_id` и `fabric_id` из проверенного payload. Репозиторий получает только ID и код активных размеров данной модели, а также ID активных тканей через JOIN с её нормативами. Результаты проверяются для каждой строки в памяти: повтор размера с неверным кодом в последней строке тоже отклоняется.

При наличии всех видов ссылок выполняются максимум четыре SELECT: активная категория, активная модель, размеры одним запросом и ткани с применимостью одним запросом. Пустые наборы не вызывают запросы; полностью несвязанный товар без категории — ни одного reference SELECT. Предел200 вариантов ограничивает каждый набор200 ID. В тестовом составе100 размеров и200 тканей получены соответственно101 и201 параметр с учётом модели. Эти запросы выбирают скаляры и не наполняют ORM identity map.

Это граница **проверки ссылок**, а не всего POST/PUT. Блокировка товара, проверка резервов, чтение старого состава, разрешение медиа, запись строк, журнал и расчёт доступности сохраняют собственные запросы. Время всего сохранения на production этим этапом не измерялось. Сами справочники не блокируются на весь срок команды: изменения их активности после проверки остаются отдельным вопросом конкурентной политики.

## Сохранившиеся правила

- Категория и модель должны быть активными. Размер должен быть активным и принадлежать модели; явно переданный код должен совпадать. Ткань должна быть активной и входить в норматив этой модели. Неизвестные/архивные/чужие ссылки отклоняются.
- Ссылки размера/ткани требуют модель; при отсутствии обеих ссылок прежний контракт не придумывает их автоматически.
- Создание и обновление используют один сервис. Production cookie/роль, identity RBAC, флаги записи, блокировка товара и `expected_version` не менялись. Ошибка ссылки в production по-прежнему409.
- Входные FK категории/модели/размера/ткани ограничены положительным32-битным ID PostgreSQL, включая обязательную модель `PresetWriteRequest`. Слишком большой ID отклоняется схемой до SQL.
- Удалены прежние методы поштучного чтения размера, ткани и применимости: альтернативного пути проверки нет.

## Пресет без изображений

Настоящий POST выявил прежний дефект: если в payload не было медиа, коллекция `Product.media_links` оставалась неинициализированной. После flush mapper пытался лениво прочитать её в async-коде и падал с `MissingGreenlet`. Создание теперь явно начинает с пустых `variants` и `media_links`; это полные коллекции нового объекта, а не подмена частично загруженных данных. Создание без изображений и без вариантов возвращает корректные пустые массивы.

## Что не является архивом

В текущем `ProductVariant` нет признака архивирования. `product.variants` — действующий состав SKU; PUT сохраняет переданные ID и удаляет пропущенные варианты по существующим правилам резервов. Поэтому прежнее обозначение следующей работы как «история вариантов пресета» было неточным. Отдельный архив этим этапом не создаётся. На момент этого этапа source пресета/медиа использовал общий ORM reader. Чтение состава ограничено следующим этапом: [источник редактора](2026-10-19-preset-editor-source.md); число медиа допустимого состава ещё требует отдельной границы.

## Проверки

Профильные **24 теста без пропусков** прошли на SQLite и собственном PostgreSQL17/MinIO, Python3.12.12:

- 200 строк,100 уникальных размеров и200 тканей: ровно четыре scalar SELECT без ORM-гидратации. Повтор одного размера/ткани200 раз оставляет четыре SELECT и уменьшает набор параметров. Пустой состав без ссылок не делает reference SQL.
- Неверный код в последней строке повторяющегося размера, чужой/архивный/несуществующий размер, неприменимая/несуществующая ткань, неактивная модель и отсутствие модели отклоняются. Прямое изменение активности в БД при оставшемся активном объекте в identity map не обходит проверку категории, модели, размера или ткани.
- Реальные POST/PUT200 вариантов: прежние SKU/ID, сырой остаток7, мерки64,25×72,35 сохранены при обратном порядке payload. Неверная последняя строка не меняет деталь; устаревшая версия1 после успешной версии2 даёт409. POST без медиа и POST без вариантов также проходят.
- Проверки FK на0/-1/2³¹ и допустимой границе2³¹−1, прежние media/RBAC/reservation/CAS сценарии и native catalog integration.

Полная регрессия: **1121 backend/0skip**, Python3.12.12, свои PostgreSQL17/MinIO; runner завершился за358с и удалил собственные процессы/базы/объекты/приватную конфигурацию. Ruff/format670 прошли. Frontend этим этапом не менялся; предыдущие615 тестов, TypeScript/lint/build и standalone browser gate здесь повторно не запускались.

Доказательства: `backend-dependencies/preset-bulk-focused*`, `preset-bulk-verified*` в локальном каталоге задачи. Новых миграций и Provider нет; схема остаётся0076. Commit/push/deploy не выполнялись.

## Продолжение

Границы source пресета/медиа, стоимость подстроки/применимости тканей/агрегатных сортировок и общие ворота выпуска остаются в работе. Production и Docker/Actions этим этапом не проверены.

Проверка контейнерного окружения19 октября: команда `docker` недоступна; CLI не найден также в стандартных Docker.app/OrbStack/Homebrew/usr-local путях, Colima/Podman в Homebrew отсутствуют. Это не подтверждение контейнерного запуска. Native PostgreSQL/MinIO в тестах запускаются отдельно и не подменяют это требование выпуска.
