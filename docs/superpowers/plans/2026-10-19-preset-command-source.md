# Проверки перед сохранением и потоковый журнал удаления

Статус: локальный этап общего рефакторинга. Основной редактор товаров — новый кабинет производства → «Пресеты».

Это описание предыдущего этапа. Загрузка старых медиа допустимого PUT устранена следующим изменением: [сохранение без прежних изображений](2026-10-19-preset-media-replacement.md). Проверки ранних отказов, формат удаления v2, индекс0078 и ограничения потокового DELETE остаются актуальными.

## Что изменено

Прежний `get_product_for_update` блокировал товар и сразу гидратировал все SKU и медиа. Версия, резервы и ссылки payload проверялись после этого. Удаление дополнительно собирало полный публичный DTO со строками URL ради контрольной суммы журнала.

Теперь блокировка читает только Product по PK с `FOR UPDATE`, `populate_existing` и `raiseload`. PUT сначала проверяет актуальную версию, затем читает максимум 201 вариант, проверяет принадлежность/уникальность переданных ID, физические и тканевые резервы, ссылки модели/размера/ткани и готовность новых медиа. Только допустимая команда с полным составом до 200 вариантов загружает прежние media-коллекции и выполняет прежнее изменение aggregate. Эта полная загрузка явно обновляет скаляры и отношения из БД; обычный публичный reader сохраняет прежнюю политику кэша.

Слишком большой состав получает общий с GET код HTTP409 `catalog_editor_variant_limit` до медиа. Никакая частичная `Product.variants` не присваивается. Устаревший PUT отклоняется после одного SELECT родителя. Идентичность, SKU, резервы, геометрия, теги, исходный источник пресета и версия сохраняются по прежним правилам; пропущенный SKU по-прежнему имеет семантику удаления. Production и identity используют один сервис с прежними раздельными правами и флагами записи.

## Проверка резервов

Проверка физического резерва варианта — отдельный скалярный SQL по product_id, `reserved_quantity > 0`, `ORDER BY id LIMIT 1`. Ноль остаётся SQL-константой, чтобы настоящий generic plan мог применить частичный индекс. Миграция `20261019_0078` добавляет `(product_id,id) WHERE reserved_quantity > 0`; общий индекс0077 для состава остаётся.

Просто добавить LIMIT без порядка оказалось недостаточно: на проверенном наборе планировщик выбирал Seq Scan и отбрасывал 40 000 строк при отсутствии резерва. Согласованные порядок и частичный составной индекс дают Index Only Scan: 0 строк для пустого резерва и 1 для зарезервированного последнего SKU. Это подтверждено custom и настоящим generic plan, а не отключением Seq Scan. Перестроение индекса нужно оценить по длительности блокировки перед production-выпуском.

Резервы ткани проверяются прежним запросом активных holds. Его стоимость по длинной истории не объявляется постоянной. Обычные операции каталога и инвентаря сначала блокируют тот же Product, поэтому после ожидания команда видит новую версию/резерв. Прямые записи в обход этих сервисов такой политики не получают.

## Удаление большого старого пресета

DELETE не ограничен 200 вариантами: это предел формы, а не запрет убрать старый неиспользуемый пресет. После проверки резервов сервис читает три скалярных потока: варианты, ссылки медиа товара с метаданными объектов, ссылки медиа вариантов с метаданными объектов. `AsyncSession.stream` и `yield_per=256`/`partitions(256)` ограничивают пакет Python. ORM-объекты детей и полный публичный DTO не создаются; контрольная сумма считается постепенно.

Затем удаляется родитель; FK каскадно удаляют варианты/ссылки. Реестр MediaObject и ссылки другого пресета сохраняются. PostgreSQL является рабочей БД. SQLite здесь — тестовый диалект; новый контрактный fixture явно включает FK для проверки тех же cascade/RESTRICT правил, вместо прежнего молчаливого режима SQLite без FK.

DELETE и запись журнала находятся в одной транзакции. Ссылка из лендинга по-прежнему запрещает удаление: ошибка откатывает детей и не создаёт запись об успешном удалении. HTTP-контракты успешного удаления и ошибки связи сохранены.

## Формат доказательства удаления v2

`details.snapshot_schema = "catalog.product-deleted.v2"` отличает новый формат от прежнего публичного DTO. Старые записи не переписываются; create/update продолжают использовать прежний checksum payload.

Хешируется канонический UTF-8 JSON с алфавитным порядком ключей, без пробелов, с Decimal как строкой и datetime в UTC с шестью знаками микросекунд. Верхние поля: `schema`, `product`, `variants`, `product_media`, `variant_media`. Product включает хранимые скалярные колонки под именами БД, включая version/type/остатки/признаки и timestamps. Варианты содержат все хранимые колонки, включая SKU, ссылки размера/ткани, резервы и мерки; порядок — id. Медиа-ссылки включают свои колонки и колонки MediaObject с префиксом `media_`; порядок товара — id, вариантов — `(product_variant_id,id)`. Покрыты также private/pending ссылки, которых нет в публичном ответе. Изменение структуры этого формата требует новой версии схемы.

Журнал содержит только SHA-256, версию схемы, актёра и счётчики. Это доказательство состояния, а не резервная копия строк. `media_links_count` считает все хранимые связи; прежний `media_references_count` сохраняет семантику видимых ready/public ссылок по ролям, включая только первое preview и одиночные роли. Подсчёт не строит строки URL и не зависит от домена MinIO.

Общий набор multi-media ролей теперь берётся из mapper: отдельная копия в write service удалена. Старый подсчёт deletion DTO удалён.

## Проверки

- SQLite с FK и PostgreSQL: stale parent в ORM-кэше, ровно один SELECT до version conflict; 201 и 20 000 SKU дают409 до медиа и без мутаций/журнала. Последний зарезервированный SKU запрещает DELETE.
- PUT200 в обратном порядке сохраняет SKU/ID, сырой остаток7, мерки64,25×72,35, медиа и версию2. Повтор со старой версией отклоняется. Чужой и повторный ID варианта отклоняются до медиа в обоих административных входах.

- Новый digest сравнивается с независимо собранным каноническим JSON из БД; изменение SKU/мерки и private media меняет checksum, rollback восстанавливает исходный. Подтверждены29 всех и21 видимая ссылка малого источника.

- Два сеанса PostgreSQL: ожидающий PUT после commit победителя видит новую версию и даёт conflict; ожидающий DELETE после commit резерва видит резерв и не удаляет товар.

## Оставшиеся границы

Успешный PUT до200 SKU пока гидратирует все старые media links, чтобы сохранить прежнюю семантику изменения ORM aggregate. Количество медиа допустимого состава ещё требует отдельного решения; этот этап устраняет тяжёлые чтения **до** проверок и полную ORM-гидратацию при DELETE, а не все чтения медиа.

Полное доказательство удаления и каскадный DELETE линейны по числу строк; поток ограничивает память Python, но не делает удаление O(1), не отменяет возможную сортировку БД и держит блокировку на время транзакции. Нагрузку и длительность нужно измерить на production-объёме перед выпуском. Стоимость нормативов/holds, подстроки, применимости, агрегатных сортировок и общие ворота выпуска остаются в работе. Production и Docker/Actions этим этапом не проверены.
