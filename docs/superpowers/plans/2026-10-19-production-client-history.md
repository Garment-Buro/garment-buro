# История клиента в новом кабинете производства

Основной интерфейс редактирования товаров — производство → «Пресеты».
Этот этап исправляет связанную карточку клиента, без изменения providers,
оболочек страниц, зависимостей или схемы базы данных.

## Проблема

`ProductionAdminReads.client_detail` загружал до 100 полных ORM-заказов,
профиль пользователя и до 100 обращений сразу при открытии карточки. Продолжения
истории не было. Обращения определялись через автора либо ID этих первых
100 заказов: обращение без прямого автора к более старому заказу могло исчезнуть
из карточки. Счётчики вкладок отражали длину усечённых массивов.

## Новое чтение

- `GET /api/production/admin/clients/detail?key=…` возвращает профиль, последнего
  получателя и агрегаты `orders_count`, `orders_total`, `paid_orders_total`,
  `tickets_count`. Массивов истории в нём больше нет.
- `GET /api/production/admin/clients/orders?key=…&limit=24&cursor=…` возвращает
  краткие заказы. `clients/tickets` возвращает краткие обращения без сообщений.
  У обоих ответ `{items, next_cursor}`; допустимый лимит 1–100, стандартный 24.
- Заказы сортируются по `(created_at, id)` по убыванию; обращения — по
  `(updated_at, id)`. Cursor привязан к ключу клиента и виду истории.
  Неверный cursor даёт 422 `invalid_cursor`.
- Общий scope сохраняет группы зарегистрированных покупателей, гостевой почты,
  гостевого телефона и одиночного заказа без контактов. Демозаказы исключены.
  Связанные обращения определяются подзапросом по всем заказам этой группы.
- В router остаются права системного администратора. Успешные ответы,
  ошибки доступа и ошибки cursor не кешируются.

`client_repository.py` выбирает скалярные поля и агрегаты. `client_service.py`
собирает результат и проверяет cursor. `client_schemas.py` задаёт контракт.
Прежнее чтение карточки удалено из `admin_reads.py`.

## Интерфейс и срок данных

Вкладка «Данные» читает небольшой профиль. Заказы читаются при открытии
«Заказы» или «Новый тикет»; обращения — при открытии «Обращения».
Один список заказов используется для истории и выбора заказа в новом тикете.
Продолжение выбора сохраняет текст формы и выбранный заказ.

Используются существующие `usePagedCatalog`/`PagedResource` и производственная
сессия. В ключ входят клиент, вид списка, пользователь и поколение входа.
JSON проверяется на границе API. История читается через same-origin `/api`,
с `no-store`, отменой и сроком 10 секунд, без автоматического повтора.
Закрытие карточки и выход отменяют запрос; поздние ответы не возвращают данные.
Ошибка продолжения сохраняет уже загруженные строки и cursor. Обычный повтор
продолжает список; неверный cursor требует явного обновления с первой страницы.

`AdminClientHistory.tsx` содержит отдельные представления заказов и обращений;
общие только управление продолжением и отображение состояния загрузки.
Нового Provider, глобального кеша или браузерного постоянного хранилища нет.

## Проверки

- 30 профильных backend-тестов без пропусков на SQLite и свежем PostgreSQL 17.
  История из 131 заказа и 132 обращений доступна полностью, включая одинаковые
  даты и обращение к старому заказу; чужие и демозаказы не попадают в группу.
  Гостевые группы не смешиваются с аккаунтом с такими же контактами.
- 626 frontend-тестов без пропусков; TypeScript и production Next build прошли.
  ESLint без ошибок; остаётся прежнее предупреждение `CustomerMediaImage.tsx`
  об `alt`. Сборка сообщает прежнее предупреждение fallback-шрифта Alumni Sans SC.
- Настоящий standalone Next и Chromium с синтетическим HTTP backend:
  130 заказов/обращений, первая страница 24, загрузка только нужной вкладки,
  ошибка/повтор профиля и продолжения, обновление cursor, выбор заказа после
  100-й записи, сохранение черновика/выбора, поздние ответы после закрытия
  и выхода через другую вкладку. Ширины 320/390/736/1280 px без переполнения;
  ошибок JavaScript нет. SQL и права проверены отдельно настоящим backend.
- Полный backend-прогон: 1295 тестов без пропусков за 503 секунды, Python
  3.12.12 с зафиксированными зависимостями, четыре свежие базы PostgreSQL 17
  и настоящий MinIO. Собственные процессы, базы, объекты и приватный
  синтетический конфиг удалены после завершения.

## Сравнение с сохранённым исходником до этапа

Отдельная SQLite-проверка запустила прежний `client_detail` из неизменяемого
локального архива на 131 заказе и 132 обращениях. Он вернул 100/100 и не нашёл
обращение к старому заказу. Новый профиль сообщает точные 131/132, полные
страницы отдельно покрыты контрактными тестами.

Первоначальный JSON прежней карточки — 35 784 байта, нового профиля — 591 байт
на этом синтетическом наборе. SQL SELECT при открытии остаётся 3 → 3: изменены
объём полей и момент загрузки истории, а не число запросов. Это сравнение
только первоначального профиля, без последующих страниц; оно не измеряет
LCP, сетевую компрессию или production-нагрузку.

## Границы выпуска

Контракт detail изменён: frontend и backend этого этапа нужно выпускать вместе.
Старые массивы намеренно не сохраняются как второй способ чтения.
Новых миграций и индексов в этом этапе нет. Устранена усечённая история и
загрузка неоткрытых списков; процентное ускорение или LCP здесь не измерялись.
Счётчики и страницы читаются отдельными запросами, поэтому при новых заказах
число в профиле может устареть до повторного открытия карточки.
Обращение, изменённое между страницами, может переместиться выше cursor;
обновление списка начинает чтение заново.

Изменения локальны. Docker/CI/production для нового контракта ещё не проверены.
Stage/commit/push/deploy не выполнялись; общий релиз остаётся в работе.
