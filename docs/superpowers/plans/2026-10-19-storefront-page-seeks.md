# Продолжение каталога с позиции курсора

## Подтверждённая проблема

Публичный `/api/catalog/products` возвращал короткую страницу, но условие
курсора через OR оставалось фильтром поверх упорядоченного индекса. PostgreSQL
читал начало каталога заново и отбрасывал уже показанные товары. Наличие LIMIT
и индекса само по себе не ограничивало эту работу.

На 30 000 товаров, трёх группах по 10 000 одинаковых цен, размер страницы24:

| Сценарий продолжения | Посещено строк до | После | Буферов до / после |
|---|---:|---:|---:|
| Новые, глубокая страница | 22 526 | 25 | 567 / 5 |
| Старые, глубокая страница | 22 525 | 25 | 722 / 5 |
| Дороже, внутри группы цен | 22 526 | 25 | 567 / 5 |
| Дешевле, внутри группы цен | 12 526 | 26 | 316 / 8 |
| Дешевле, переход к следующей цене | 20 025 | 25 | 505 / 6 |
| Дешевле, конец каталога | 30 000 | 0 | 754 / 4 |

25-я запись нужна для определения следующей страницы. У дешёвой сортировки
Merge Append может прочитать ещё одну запись второй ветки. Числа — фактические
EXPLAIN ANALYZE/BUFFERS на локальном PostgreSQL17, не оценка production/LCP.

## Реализация

Repository сохраняет существующие router → service → repository, DTO и курсор
версии1. Сервис по-прежнему проверяет fingerprint фильтров; некорректный курсор
даёт422/no-store. Стоимость, видимость, картинки и фронтенд не меняются.

Для новых/старых товаров и «Дороже» обе части ключа направлены одинаково:
сравнивается пара `(created_at,id)` или `(price,id)`. Это становится Index Cond,
а не фильтром уже прочитанных строк. SQLite сохраняет julianday для одинаковой
обработки форматов времени; это тестовый диалект, не рабочее хранилище.

У «Дешевле» направления разные: цена ASC, ID DESC. Продолжение разделено на две
непересекающиеся ветки одного SQL: остаток текущей цены с меньшими ID и большие
цены. Каждая получает весь исходный набор фильтров и LIMIT+1 до UNION ALL;
результат снова ограничен и упорядочен. Максимальный промежуточный набор —
2×(limit+1), а не весь остаток каталога. Повторных HTTP или SQL round trip нет.

Равные границы BETWEEN сохраняют ведущую цену в сортировке первой ветки.
Обычное равенство позволяло PostgreSQL выбрать PK по ID и снова фильтровать
тысячи записей других цен. Это отдельно воспроизведено и проверено в custom
и настоящем prepared generic плане. Используются существующие индексы0058;
новой миграции, Redis, денормализации и кеша нет.

## Проверки и ограничения

60 профильных тестов прошли без пропусков: HTTP-контракты на SQLite/PostgreSQL
и два сценария больших планов. 88 custom/generic EXPLAIN ANALYZE/BUFFERS:
первые и глубокие страницы24/100, отдельные и одинаковые даты, одинаковые цены,
переходы между ценами и конец каталога. Сравниваются реальные ID/порядок,
посещённые строки и буферы. Перед каждым набором VACUUM убирает мёртвые записи
от предыдущего rollback fixture: тест измеряет поиск, а не темп autovacuum.

HTTP-регрессии проходят через публичный API с limit1 и всеми видами фильтров:
категории, цвета, источник, точная/диапазонная цена, literal поиск и IDs.
Скрытые, demo и товары выключенных категорий не появляются в продолжении.
Сортировка ID внутри одной цены сохраняется в обоих направлениях цены.

Полный backend: **1196 passed, 0 skipped**,409,95с; Python3.12.12, свежие
PostgreSQL17 с четырьмя отдельными БД и настоящий MinIO. Runner exit0;
собственные процессы, БД, объекты и приватная конфигурация удалены.
Ruff и проверка форматирования636 файлов прошли. Новая регрессия входит в
существующий `tests/integration`, который настроен в CI с PostgreSQL;
сам Actions workflow этим локальным запуском не проверялся.

Граница доказательства — тестовый набор без редких фильтров и длинного префикса
скрытых категорий. Поиск подстроки и редкий цвет могут потребовать просмотра
большого диапазона после курсора; работа autovacuum и конкурентные изменения
влияют на число прочитанных буферов. Нельзя обещать O(1) для любого фильтра.
Глобальный справочник цветов/категорий и другие публичные reader ещё требуют
отдельного анализа. Это не нагрузочный тест и не проверка production.

Frontend продукта не менялся: прежние617 тестов/build/browser gate не
повторялись. Главный редактор остаётся производство → «Пресеты».
Commit/push/deploy не выполнялись; весь релиз остаётся в работе.
