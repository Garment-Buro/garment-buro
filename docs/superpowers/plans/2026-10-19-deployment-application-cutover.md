# Пауза приложений на время миграций

История этапа: последующее [непрерывное окно backup](2026-10-19-release-backup-boundary.md)
переносит архив после остановки writers. Описанный ниже зазор для записей закрыт;
76 проверок — результат этого прежнего этапа, новый набор содержит82.

Локальный этап подготовки релиза, 19 октября 2026. Production не переключён.

## Подтверждённая проблема

Скрипт уже приостанавливал workers, но старые backend/frontend продолжали
работать во время Alembic. Регрессионная проверка на настоящем Bash-скрипте
показала оба прежних приложения в состоянии `applications_at_migration`.
Также прежний rollback безусловно поднимал backend и frontend, включая тот,
который до выпуска был остановлен.

## Теперь

После проверенного архива и инициализации хранилища/роли скрипт запоминает
действительно работающие приложения и workers из прежнего Compose. До
переключения он отклоняет orphan, paused/restarting, активные setup jobs и
неизвестные writer-сервисы, даже объявленные в Compose: их обновление нельзя
молча поручать старому образу. Поддерживаются семь явно перечисленных workers.

Порядок переключения:

1. Приостановить прежние workers, затем прежние API/frontend. Отметить паузу
   до stop, чтобы восстановить также частично остановленный набор.
2. Повторно проверить running-сервисы прежнего проекта: разрешены только
   PostgreSQL, Redis и MinIO. Успешный код stop сам по себе не доказательство.
3. Выполнить миграции и запустить API/frontend кандидата. Инфраструктура этим
   переключением не останавливается и не пересоздаётся.
4. Дождаться readiness API и четырёх HTTP-страниц, затем включить workers
   выбранных новых флагов. После этого записать `.release`.

Это окно обслуживания: API/frontend недоступны на время паузы и миграций.
Zero-downtime не заявляется. Нового Provider, кеша или схемы БД нет.

## Восстановление

До создания кандидата запускаются существующие контейнеры через `start`:
сохраняются их прежние image/environment. Ошибка восстановления приложения
останавливает восстановление до запуска workers.

После попытки создания кандидата сначала останавливаются его workers, затем
его frontend/backend. Ошибка любого stop не разрешает запуск старого набора.
Затем восстанавливаются прежние образы только ранее работавших приложений и
workers. Ранее остановленный frontend/backend не включается при rollback,
даже если кандидат успел создать его. Пустые наборы поддерживаются Bash 3.2.
Поздний отказ записи метаданных возвращает прежнюю `.release` после успешного
восстановления. Сигналы INT/TERM сохраняют коды 130/143.

## Что остаётся условием выпуска

Настоящие Docker/CI и предыдущий образ с новой схемой не проверены. Строгая
проверка Alembic head может отклонить старый API даже после добавления индекса;
автоматический downgrade отсутствует. Ошибка health при восстановлении
оставляет workers остановленными и требует ручного восстановления.

После пересоздания контейнеров используется текущий `.env`; старые настройки
и секреты сами не возвращаются. Backup выполняется собственной остановкой
и возобновлением writers до этого cutover: между архивом и миграциями есть
интервал работы старого приложения. Архив не является точным снимком момента
переключения. Нужны реальный restore, проверка внешних writers, измерение простоя
и отдельная процедура восстановления данных. SIGKILL/сбой хоста/daemon
выходят за пределы shell traps. Stage/commit/push/deploy не выполнялись;
общий релиз продолжается.
