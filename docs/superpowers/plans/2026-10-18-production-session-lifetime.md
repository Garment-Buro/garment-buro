# Производственный вход: срок жизни сессии и согласование вкладок

Этап выполнен локально, без stage/commit/push/deployment. Backend, схема БД и права производственных ролей на этом этапе не менялись. Основной редактор товаров — производство → «Пресеты».

## Подтверждённая проблема

Проверка справочников обнаружила более раннюю общую проблему: productionAuthStore записывал любой завершившийся ответ initialize/login, выход очищал состояние только после HTTP, а runAuthenticated очищал вход при любом 401, даже пришедшем из прежней сессии. Команда могла запускаться и без локального входа. Эти три случая воспроизведены RED на настоящем store, затем GREEN.

Теперь каждый вход имеет собственный sessionEpoch. Выход немедленно очищает сотрудника, маркер формы и локальное разрешение команд. Старый успех не возвращает данные, старый отказ не завершает новый сеанс. Повторный вход того же сотрудника создаёт новый epoch. Product/floor рабочие области пересоздаются по id+epoch, поэтому старый черновик не переживает новый вход. Страницы каталога/лендингов и общие ресурсы также учитывают epoch.

## Cookie и вкладки

Production использует существующую отдельную HttpOnly cookie gb_production_session с path /api/production. Это подтверждено текущим auth_router; личный код не создаёт identity-сессию покупателя. У production свой Web Lock, отдельный от покупательского refresh.

Login/logout и начальная проверка /me выполняются под одним browser lock этого origin. Lock сохраняется до завершения cookie-ответа, даже если пользователь уже начал следующий вход/выход. Более новый intent сразу отзывает старые формы, но HTTP мутации идут по очереди. Запрос /me имеет существующий общий срок ожидания чтения; дубли initialize объединяются в один запрос.

В localStorage хранится только {epoch, phase}: случайный непрозрачный маркер и pending/active/signed_out. Ни код, ни cookie/token, ни профиль сотрудника, ни предметные данные туда не попадают. Это механизм согласования браузерных вкладок, а не хранение учётных данных или разрешение доступа. Права по-прежнему проверяет backend.

Storage events сразу закрывают старую область; focus/pageshow/visibilitychange перепроверяют актуальный маркер, а не доверяют запоздавшему event payload. После нового active каждая вкладка отдельно читает сотрудника с сервера. Ошибка logout сохраняет signed_out: перезагрузка не восстанавливает ещё действующую cookie без явного нового входа. Браузер без реального общего хранилища или Web Locks показывает ошибку; cookie mutation в таком режиме не запускается.

Согласование действует между обновлёнными клиентами одного origin. Вкладки со старой версией и другие origins не используют этот протокол; при выпуске требуется обновить открытые терминалы. Серверное завершение сессии при недоступной сети не обещается.

## Общие чтения и запись

Все assortment helpers, включая upload, проходят через production runAuthenticated. Запрос из отозванного входа не запускается; запоздавшие данные не принимаются. useAssortmentResource больше не показывает данные прошлого path/epoch, использует отмену и ограниченное по времени чтение; Strict Mode отменяет первую микрозадачу до сетевого запроса. useAdminResource тоже ключует результат по epoch/path. Нового Provider нет: это прежний Zustand store, browser coordination и обычные hooks.

## Проверки

13 новых тестов настоящего store/helper: поздний initialize; старый 401/успех; новый вход того же сотрудника; запрет команд без входа; порядок logout→login и login→logout; одиночный initialize и сохранение epoch при повторном чтении; failed logout/перезагрузка; актуальный 401 и временный отказ; remote intent; отсутствие credentials в marker; запрет обхода ассортиментными helper; недоступные storage/lock.

Полный frontend: **575 passed, 0 skipped**, lint и production build с TypeScript. Сохраняется прежнее предупреждение CustomerMediaImage alt. Последняя полная проверка backend из предыдущего этапа — **1051 passed, 0 skipped**, PostgreSQL17/MinIO; текущие изменения backend не затрагивают, повтор полного backend не выполнялся.

`check:admin-catalog`: настоящий standalone Next/Chromium, два настоящих окна одного browser context, storage events и navigator.locks; HTTP backend синтетический. Проверены немедленное закрытие старого редактора в обеих вкладках, новый login после held logout, новая epoch при том же user ID, отсутствие старого черновика, failed logout и reload без нового /me, held startup /me перед logout, cookie HttpOnly/path/SameSite и 320/390/736/1280 px. Прежние сценарии редактора, страниц, owner кабинета и реквизитов также проходят. Native RBAC/cookie endpoints подтверждены исходниками и предыдущим backend набором; это не публичный E2E.

## Продолжение

Справочники моделей и тканей в production всё ещё вызывают read service с limit=100/cursor=None, а их таблицы фильтруют полученный срез в браузере. Нормативы и другие производственные справочники также требуют отдельного масштабирования. Это следующий этап после устранения общей гонки входа. Общие ворота выпуска: Docker/Actions, сайт, реальный телефон, производительность, backup/restore/внешние writers, совместимость предыдущего образа и публичная оплата остаются незакрытыми.
