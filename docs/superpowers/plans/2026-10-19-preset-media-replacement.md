# Сохранение пресета без чтения прежних изображений

Статус: локальный этап общего рефакторинга. Основной интерфейс — новый кабинет производства → «Пресеты».

Это описание предыдущего этапа. Неограниченное чтение GET заменено следующим изменением: [источник медиа редактора](2026-10-19-editor-media-source.md). Ответ PUT теперь использует скалярные проекции вместо гидратации восьми итоговых ORM-ссылок; его прежняя семантика сохранения сохраняется.

## Изменение

Раньше даже допустимый PUT после всех проверок повторно загружал весь ORM aggregate: старые изображения товара и вариантов, включая скрытые ссылки. Эти коллекции очищались, а затем создавались заново. Стоимость чтения и память зависели от старого состава медиа.

Теперь сервис блокирует Product, проверяет актуальную версию, полный состав до200 вариантов, принадлежность ID, резервы и новые ссылки. `CatalogEditorCommands.clear_media` удаляет старые связи прямыми SQL DELETE по product_id и не более200 ID вариантов. Запрос не возвращает и не гидратирует старые ссылки. Пропущенные варианты удаляются, перед созданием замен выполняется flush для освобождения уникальных сочетаний размера/ткани. Медиа-объекты остаются в реестре: удаляются связи, а не файлы.

Скалярные поля вариантов обрабатывает один `_apply_variant` для create/update. Существующие ID/SKU сохраняются; новый вариант не получает SKU из входного JSON. Для пресета с моделью сохранение не перезаписывает физический остаток существующих строк вычисленным остатком из формы; новый вариант начинает с нуля. Без модели используется переданный физический остаток. Мерки, ссылки справочников, цвет и размер сохраняются. Пропуск tags/preset_source сохраняет прежние значения.

Общие генераторы `_product_media`/`_variant_media` задают одинаковую семантику create/update: одиночная роль использует первую ссылку, множественная сохраняет порядок и повторения. Новые ссылки вставляются Core-пакетами не более256 строк. Это предел буфера вставки, а не новое ограничение количества фотографий в продукте.

Ответ собирается через `CatalogEditorRepository.media_snapshot` из уже сохранённых Product/вариантов и новых связей. Повторного чтения родителя и SKU нет; варианты сортируются по ID, как в прежнем reader. `load_availability` получает явный полный состав, mapper — явные медиа. ORM-коллекции Product.variants и media_links остаются незагруженными: пустой или частичный aggregate не подставляется вместо данных БД. Публичный HTTP-ответ сохраняет прежние вычисленные остатки; административный GET отдельно возвращает физические остатки и SKU.

После предшествующего reader в той же сессии уже закэшированные удалённые ссылки отсоединяются без SQL. Загруженные обратные коллекции MediaObject, содержащие эти ссылки, истекают. Для этого читается только существующий identity map, без загрузки старых коллекций. Обычные API используют сессию на запрос. Сохранённые внешним кодом ссылки на отсоединённые ORM-объекты не являются новым состоянием БД; после rollback состояние читается заново.

Удалены больше не нужные `clear_product_media`, параметр полного reader `refresh` и неиспользуемый helper variant media references. Parent-only блокировка, общий сервис двух административных входов, разграничение прав, флаги и checksum create/update сохранены. Транзакцию по-прежнему завершает вызывающий API.

## Проверки

SQLite с включёнными FK и настоящий PostgreSQL17:

- Источник200 SKU и12 029 старых media links, с холодной сессией и после полного reader. До удаления связей нет SELECT старых таблиц связей, после — гидратируются ровно8 итоговых ссылок. Сохранены199 SKU/ID и физический остаток7; пропущенный SKU удалён, новый имеет stock0/SKU NULL. Сырой остаток родителя17 не заменяется входным999; мерки65,50×78,25, tags/source и порядок ответа сохранены.
- Одиночные роли берут первую ссылку; галерея и изображения варианта сохраняют порядок и дубликаты. Оба ORM набора отношений остаются unloaded. Старые закэшированные ссылки отсоединены, соответствующие обратные коллекции истекли.
- По600 присланных изображений товара и варианта: фактические пакеты вставки256/256/88 для каждой таблицы, одинаковый порядок0…599 и полные строки URL в ответе.
- Пустая замена удаляет весь состав и медиа, сохраняет физический остаток9 для товара без модели.
- Неизвестное новое медиа вызывает отказ до DELETE. Ошибка уникального slug после DELETE и исключение после записи аудита откатывают варианты, ссылки, версию и журнал. Полное сохранённое состояние сравнивается по независимому потоковому digest до/после rollback.
- Прежние проверки200 SKU,201/20 000 SKU, чужих/повторных ID, физических/тканевых резервов, раздельных прав и флагов остаются в регрессии. Два реальных PostgreSQL-сеанса проверяют ожидание Lock и свежую версию/резерв после commit; планы индекса0078 и обратимость миграции также повторяются.

Проверено: **1165 backend/0skip**, профильные **104/0skip**, Python3.12.12, собственные PostgreSQL17/MinIO. Полный runner завершился за404с и удалил свои процессы/базы/объекты/приватную конфигурацию. Ruff/format681 прошли. Доказательства в каталоге задачи: `backend-dependencies/preset-media-focused*`, `preset-media-verified*`, `preset-media-verification.json`. Frontend не менялся; прежние615 тестов и browser gate в этом этапе повторно не запускаются.

## Границы

Открытие допустимого пресета до200 SKU пока читает все его медиа. Нужен отдельный контракт полного редактируемого источника, согласованный с уже существующими ограничениями входных полей. Без этого нельзя молча обрезать изображения или объявить GET ограниченным по числу ссылок. Для PUT итоговый состав ограничивается существующим валидируемым payload, но суммарный разрешённый объём всё ещё может быть большим.

DELETE старых связей остаётся линейным по затронутым строкам и держит блокировку родителя до commit. Потоковый журнал удаления большого пресета также линейный. Устранение чтения старых медиа не доказывает постоянное время работы БД или ускорение главной/публичных каталогов. Стоимость нормативов/holds, применимости, подстроки, агрегатных сортировок и общие ворота выпуска продолжают проверяться отдельно.

Production, Docker/Actions и длительность блокировок на реальной базе этим этапом не проверяются. Commit/push/deploy не выполняются.
