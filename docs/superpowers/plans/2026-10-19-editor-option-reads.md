# Ограниченные чтения редакторов моделей и пресетов

Статус: изменения локальны; общий выпуск продолжается. Основной редактор товаров — производство → «Пресеты».

## Что изменилось

Раньше выбор размера пресета через `CatalogEditorOptions.model` загружал полную ORM-модель и всю историю её размеров. Даже короткие страницы моделей/тканей получали полные ORM-записи. Источник формы самой модели также читал архивные размеры, хотя интерфейс редактирует только рабочую сетку.

SQL выбора вынесен в `catalog/editor_option_repository.py`, входные и выходные DTO — в `editor_option_schemas.py`. `editor_options.py` собирает проверенные DTO и маршруты с прежними независимыми guard для identity/production. Короткие чтения выбирают только нужные скаляры, не загружают коллекции и не заполняют identity map.

## Контракты пресета

- `GET .../editor-options/sizes?model_id=ID&limit=24&cursor=...&query=...` возвращает короткую страницу активных размеров `{id,code,is_active}` с настоящим продолжением. Нет ограничения первыми 100 размерами; поиск и страницы исполняются сервером.
- `GET .../editor-options/models/ID?selected_size_ids=...` возвращает заголовок модели и только явно запрошенные размеры, максимум 200. Без выбранных ID нет запроса к таблице размеров. Выборка привязана к модели и включает выбранные архивные размеры. Чужие ID не раскрываются.
- Frontend проверяет точное соответствие запрошенному набору, типы и уникальность. Неполный ответ блокирует сохранение и допускает повтор. Запрос и состояние привязаны одновременно к модели, набору ID и revision, поэтому старый ответ не подменяет новую выборку.
- `PresetVariantFields` объединяет выбранные размеры с текущими страницами. Поиск, отсутствие совпадений и продолжение не сбрасывают ID, существующие варианты, физические остатки и медиа. Матрица остаётся ограниченной 200 вариантами.

## Источник редактора модели

`ReferenceDirectoryRepository.model_detail` делает два скалярных SELECT: одну модель и только активные размеры по `sort_order,id` с `LIMIT 101`. Сервис принимает максимум 100, как и действующий write-контракт. Если активных размеров больше, GET возвращает явный `409 / model_size_limit`; данные не обрезаются до первых 100 и не открываются для неполного PUT. Архивная история остаётся в БД; этот GET больше не передаёт её форме, которая и раньше исключала архив из редактирования.

На момент этого этапа создание/обновление модели ещё читали историю целиком. Следующий этап [ограничил команды и их ответы](2026-10-19-model-command-bounds.md), сохранив блокировку, версии и архивные ID.

## Индексы и реальные планы

Миграция `20261019_0075` добавляет индексы `(is_active,id)` для моделей/тканей и `(garment_model_id,is_active,id)` для страниц размеров. Индекс рабочей сетки расширен до `(garment_model_id,is_active,sort_order,id)` с обратимой миграцией.

Проверка выявила, что простой `id > cursor` даже после добавления индекса позволял PostgreSQL выбрать PK и отбрасывать архивные строки. Курсор теперь задаёт диапазон полного составного ключа. На 20 000 моделей, 20 000 тканей и 20 000 размеров с редкими активными строками проверяются настоящие repository-запросы, включая первую и глубокую страницы, custom plan и реальный `PREPARE / force_generic_plan`. В проверенных страницах индекс читает 25 строк без сортировки и отбрасывания архива; источник рабочей сетки читает не более 101. Это доказательство для данного порядка без поисковой подстроки и фильтра применимости ткани; произвольный поиск и EXISTS требуют отдельной оценки стоимости.

## Проверки текущего этапа

- Профильные backend: 45 тестов без пропусков, SQLite и собственный PostgreSQL17/MinIO. Сценарии с 130 активными и 5 000 архивными размерами, последними страницами, выбранным архивом/чужим ID, полным набором полей, SQL-проекциями, превышением рабочей сетки, CAS и сохранностью архивных записей.
- 615 frontend-тестов без пропусков; TypeScript, lint и production build прошли. Осталась прежняя alt-text warning в `CustomerMediaImage.tsx`.
- Полный standalone Next/Chromium gate с синтетическим HTTP API прошёл: 130 размеров, выбор последнего, пустой поиск с сохранением выбора, архивный выбранный размер в PUT, неполный selected context и восстановление. Прежние проверки upload/save, 503/409, черновиков, прав и четырёх ширин также прошли.
- Полный backend: **1100 тестов без пропусков**, 370,46 с; Python3.12.12, собственные PostgreSQL17/MinIO. Миграция дважды понижена/повышена с проверкой сохранности строк и состава индексов. Ruff/format: 667 файлов. Процессы, базы, объекты и приватная конфигурация тестового запуска удалены его runner.

Локальные доказательства: `editor-options-frontend.log`, `editor-options-lint.log`, `editor-options-build.log`, `editor-options-browser.log`; backend — `backend-dependencies/editor-options-focused*`, `editor-options-verified*`. Сохранены 14 реальных планов в `editor-options-query-plans.json` и краткая сводка в `editor-options-query-plan-summary.json`. Результат текущего этапа подтверждается итоговым JSON и JUnit, а не промежуточными точками pytest.

## Что осталось

Canonical CRM reads с полными дочерними массивами, серверный source пресета с историей вариантов, стоимость поисковой подстроки/агрегатных сортировок и общие ворота выпуска. Model command-path выполнен следующим этапом по ссылке выше. Новых Provider и бизнес-данных в localStorage нет. Commit/push/deploy не выполнялись. Docker/Actions, production, реальная оплата и настоящий телефон данным локальным этапом не подтверждены.
