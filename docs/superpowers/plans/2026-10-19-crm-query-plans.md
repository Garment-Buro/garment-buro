# Стоимость SQL-запросов справочников производства

Статус: локальная реализация и серверные проверки завершены. Выпуск всего проекта не завершён.

## Зачем этот этап

Страница из 24 карточек не гарантирует, что БД читает только 24 строки. После разделения справочников на страницы проверен следующий уровень: реальные планы SQL, который строят repositories моделей и лекал. Основной редактор товаров по решению пользователя остаётся производство → «Пресеты».

Использован отдельный PostgreSQL 17 с миграциями проекта, 20 000 моделей, 20 000 размеров и 199 995 файлов. У одной модели/размера 100 000 файлов, у остальных по пять; размеры имеют дробные минимумы 50,25 и 60,35 см. Это синтетический набор, а не копия production. Планы получены через `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` после настоящего выполнения соответствующего repository-запроса. Время отражает повторное SQL-чтение с прогретым кэшем, без HTTP, браузера и внешнего файлового хранилища.

## Изменения

- Миграция `20261019_0073` добавляет четыре индекса: Unicode имя+ID и код+ID модели, Unicode код+ID лекала, модель+размер+ширина+длина лекала. Схема ORM содержит те же индексы. Прежние ограничения, данные и права не меняются.
- Продолжение общего справочника использует сравнение пары `(sort_value, id)`, а не дизъюнкцию двух условий. Все используемые значения сортировки ненулевые, обе части имеют одинаковое направление. PostgreSQL получает диапазон индекса и на глубокой странице; ID продолжает разрешать одинаковые значения. SQLite также поддерживает этот контракт.
- Для сортировки достаточно существующего `UnicodeLower`: `pg_c_utf8` одновременно задаёт Unicode case mapping и порядок кодовых точек. Удалён избыточный внешний `COLLATE C` и неиспользуемый аргумент session у `ordered_text`. Кириллица, расширенные символы и прежние курсоры сохраняют порядок. Семантика подтверждена [документацией PostgreSQL 17](https://www.postgresql.org/docs/17/collation.html) и сравнением двух порядков на более чем тысяче символов в настоящей БД.
- Покрытие применяет уже прочитанные и проверенные мерки/версию размера к count и окну. Повторного JOIN размера нет: строки не сравниваются с новым состоянием геометрии после чтения контекста. Постоянные границы также позволяют планировщику оценить выборку для размера с большим числом файлов. Окно в PostgreSQL читает до 36 точек через VALUES/LATERAL, каждую точку — точным индексным поиском максимум трёх файлов. Третий файл позволяет обнаружить повреждённый дубликат, а не молча спрятать его. Эта граница сохраняется и при generic prepared plan: обычный IN×IN в таком плане возвращался к широкому bitmap scan. Геометрия уже задана вычисленными координатами; повторять диапазон/остаток деления в точечных probes не требуется. SQLite использует эквивалентный IN-запрос, поскольку LATERAL не поддерживает. Точный шаг в сотых, варианты рукава, архив и версия сохраняются.
- Предикат попадания в сетку общий для сводки модели с SQL-колонками и окна с конкретными мерками. Формула и тарифы не менялись. Redis не добавлен: он не исправляет отсутствующий индекс и потребовал бы отдельной инвалидации точного покрытия.

## Границы результата

Список моделей по имени/коду читает 25 строк индекса, включая строку для определения продолжения. Проверена страница после 19 000-й позиции. Выборка последнего окна читает 36 подходящих файлов, а не отбрасывает остальные файлы размера. В этом наборе активен один вариант рукава; UI-граница остаётся 72 кнопки при двух вариантах.

Счётчик покрытия по-прежнему проверяет 100 000 файлов выбранного размера: точное число действующих координат требует чтения этих данных. Улучшение count не означает постоянную стоимость. Сортировки по агрегатным счётчикам, поиск подстроки, остальные справочники/категории и реальные production-распределения требуют отдельного профиля. Индексы не объявлены решением всех медленных страниц.

Миграция выполняет обычный транзакционный `CREATE INDEX`. Перед её применением на большой работающей БД нужен выбор окна работ или отдельной процедуры concurrent build. Здесь миграция применялась только к принадлежащим проверке БД; production не изменён.

## Проверки

`tests/integration/test_crm_directory_plans.py` выполняет реальные запросы на большом наборе и проверяет выбранные индексы, глубину курсора, число прочитанных/отброшенных строк окна и точность дробных координат. Отдельно выполняются PREPARE + EXPLAIN EXECUTE с force_generic_plan: EXPLAIN SELECT с подставленными значениями такую проверку не заменяет. Проверено, что повреждённые дубликаты не скрываются локальным пределом. Порогов времени нет: такой тест не должен зависеть от скорости машины. Данные и статистика откатываются с транзакцией.

Вторая проверка дважды проходит downgrade/upgrade 0072↔0073, проверяет наличие/отсутствие всех четырёх индексов и неизменность модели, включая версию, Unicode имя и timestamps. Общая проверка сравнивает мигрированную схему с ORM без исключения новых индексов. Прежние контрактные сценарии моделей, тканей, складов, техкарт и лекал проверяют сортировки, одинаковые значения, фильтры, курсоры, права и команды записи на SQLite/PostgreSQL.

Профильный native набор окончательной реализации: **60 passed, 0 skipped**, 31,56 с. Полный backend: **1085 passed, 0 skipped**, 333,94 с на Python3.12.12 со свежими PostgreSQL17 и настоящим MinIO. Ruff/format657 файлов прошли. Собственные процессы, БД, файлы и приватная конфигурация проверки удалены. Frontend не менялся: его предыдущие598 тестов/build/browser gate в этом этапе не повторялись.
