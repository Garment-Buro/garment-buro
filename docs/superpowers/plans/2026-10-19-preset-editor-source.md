# Ограниченная загрузка пресета для редактора

Статус: локальный этап общего рефакторинга. Основной редактор товаров — новый кабинет производства → «Пресеты».

## Проблема и изменение

Форма допускает максимум 200 вариантов, но прежний GET сначала гидратировал весь `Product.variants`, медиа товара и всех вариантов. Проверка frontend выполнялась после этого чтения и передачи ответа. Старый товар с 20 000 SKU заставлял сервер читать полный состав, который редактор всё равно не мог открыть.

Общий для identity и production сервис теперь получает `CatalogEditorSnapshot` из отдельного репозитория. Скалярные поля товара читаются по PK, варианты — отдельным SQL `WHERE product_id = :id ORDER BY id LIMIT 201`. Найденный 201-й вариант означает отказ HTTP409 с кодом `catalog_editor_variant_limit` и русским сообщением. Медиа и доступность при этом ещё не запрашиваются. Усечённый состав не передаётся форме.

При 0–200 вариантах читаются все ссылки медиа товара и один пакет ссылок медиа вариантов с JOIN объектов. Mapper принимает явные части снимка. Расчёт доступности получает ту же явную матрицу вариантов и сохраняет прежнюю формулу: физические остатки и резервы возвращаются отдельно от доступной ёмкости ткани. Свойство `Product.variants` не заполняется частичным набором; `raiseload("*")` запрещает скрытое дочитывание отношений. `populate_existing` обновляет скалярные поля при уже существующем ORM-объекте в сессии.

Входной лимит записи и предел чтения используют одну константу 200. Публичное чтение каталога продолжает использовать прежний полный mapper; его значения и фильтрация ready/public медиа сохраняются. Новый Provider и клиентский обход backend не добавлены. Существующий HTTP transport показывает `detail.message`, поэтому frontend не менялся.

## Индекс и обратимость

Миграция `20261019_0077` заменяет одиночный индекс `product_variants(product_id)` составным `(product_id, id)`. Первый столбец сохраняет прежнюю применимость, второй даёт порядок LIMIT без сортировки полного состава. ORM metadata отражает тот же индекс. Строки вариантов не переписываются. Downgrade восстанавливает одиночный индекс; перед production-выпуском остаётся оценить длительность блокировки перестроения на реальной базе.

## Проверки

Профильные 57 тестов без пропусков прошли на SQLite и собственном PostgreSQL17/MinIO, Python3.12.12:

- Полный состав 200 вариантов, SKU/ID, физические остатки 17/7 и резервы 2, доступность по ткани 11, дробные мерки 64,25×72,35, все роли медиа, порядок галереи, pending/private фильтрация и пустой пресет.
- Реальные production/identity GET возвращают одинаковую деталь и `no-store`; гость и покупатель не получают доступ, identity Bearer не заменяет производственную cookie, неизвестный ID даёт 404.

## Оставшаяся работа

Для допустимого состава до 200 SKU количество ссылок медиа пока не имеет отдельной границы. Этот этап ограничивает чтение вариантов и останавливает слишком большой состав **до** медиа; он не делает все GET постоянными по стоимости. Чтение нормативов ткани для доступности также сохраняет прежнюю стоимость.

На момент этого этапа команды PUT/DELETE использовали полный aggregate под блокировкой. Проверки перед media и потоковое удаление реализованы следующим этапом: [command source](2026-10-19-preset-command-source.md). Их нельзя переводить на частичную ORM-коллекцию: пропущенные варианты имеют семантику удаления. Следующий этап должен ограничить command source, сохранив резервы, SKU/ID, media, CAS и журнал. Отдельного архива ProductVariant в модели нет. Стоимость подстроки, применимости тканей, агрегатных сортировок и общие ворота выпуска также остаются в работе.

При следующем изменении command source сначала следует заблокировать родительский Product и проверить expected_version, затем прочитать ограниченный набор ID вариантов. Это позволит отклонять слишком большой состав до media hydration, сохраняя полный aggregate для допустимого PUT. DELETE требует отдельно сохранить семантику снимка журнала и проверки резервов; подмена полного snapshot усечённым набором недопустима.
