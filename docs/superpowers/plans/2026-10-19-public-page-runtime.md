# Открытие главной и каталога на настоящем локальном стеке

Основной редактор товаров — производство → **«Пресеты»**. Проверен настоящий
HTTP-переход `/admin/models` → `/production?section=presets` в production-сборке.

## Что изменилось

Новый посетитель больше не получает случайный ID корзины и GET отсутствующего
документа при открытии страницы. `initializeCart` завершает UI-инициализацию,
если нет ID, товаров, изменений, ожидающей записи, известной версии и конфликта.
Очередь синхронизации остаётся неинициализированной. Первое добавление создаёт
ID, читает серверное состояние и выполняет обычный PUT с версией и operation ID.

Существующий ID, даже при пустом локальном массиве, всегда требует серверного
чтения: другая вкладка могла сохранить товары. Восстановление, повтор потерянной
записи и конфликты остаются в прежней очереди. Новый Provider или кеш не добавлен.

Это сокращает один запрос браузера и один SELECT у нового посетителя. Заметное
улучшение LCP этой небольшой правкой не доказано.

## Стенд и проверки

Использованы свежие принадлежащие задаче PostgreSQL 17 и MinIO, настоящий ASGI
backend после миграций и отдельная production-сборка Next 16.3.8. Файлы `.env`
исключены из копии frontend; внешние платёжные/почтовые/доставочные провайдеры
не настроены. Три frontend-флага identity/catalog writes/CRM включены при сборке
и запуске. Общее `.next` проекта не используется.

Набор: 128 товаров, 1724 SKU, 8 опубликованных профилей и 8 сообществ.
Аватары загружены настоящим AvatarService в закрытый бакет; изображения товаров
и сообществ получены из настоящего публичного MinIO. Ответы API не подменялись.

- **617 frontend-тестов, 0 ошибок, 0 пропусков**; профиль корзины — 15 тестов.
  Новый тест сначала воспроизвёл лишнее чтение, затем проверил первую запись и
  восстановление после перезапуска store. Отдельно проверен пустой кеш с прежним ID.
- TypeScript и production build прошли. ESLint: 0 ошибок; прежнее предупреждение
  `jsx-a11y/alt-text` в CustomerMediaImage осталось.
- Восемь холодных браузерных прогонов: по три на каждую страницу при 390×844,
  CPU ×4, задержке 150 мс и 200000 байт/с; по одному на страницу при 1280×900
  без ограничения сети/CPU. HTTP-кеш выключен, новый контекст для каждого прогона.
- Замедление проверено отдельной случайной HTML-страницей 100007 байт: 543 мс.
  CDP сообщает применённое правило. ResourceTiming `responseStart` в этом Chromium
  исключает искусственную задержку заголовков; его нельзя выдавать за пользовательский TTFB.
- Без JavaScript HTML содержит 4 разных товара, 4 человека и 4 сообщества главной
  либо 24 товара каталога. Браузер не повторяет начальный GET списков. DOM-копии
  карточек главной нужны непрерывным лентам, число уникальных ID считается отдельно.
- Поиск, продолжение 24 → 48 без повторов, старый адрес редактора и полный DTO
  конструктора с 12/200 SKU проверены через настоящий API.
- Отдельный браузерный сценарий установленного приложения прошёл путь конструктора:
  до первого добавления — 0 запросов корзины; затем GET → PUT, сохранение в PostgreSQL
  и GET после новой загрузки с тем же item ID и revision. Реальных платежей нет.

Backend продукта здесь не менялся: предыдущие **1190 backend/0skip** не повторялись.
Настоящие API-сценарии этого этапа не заменяют полную backend-регрессию.

## Что показал замер

| Наблюдение | Результат | Значение |
|---|---|---|
| Медиана мобильного LCP главной | 1,248 с | LCP — надпись GARMENT; это не готовность всех карточек |
| Медиана мобильного LCP каталога | 2,208 с | LCP — изображение карточки |
| Полученные байты главной / каталога | ≈1,65 / 1,36 МБ | В пределах окна наблюдения 12 с после DOMContentLoaded |
| SQL начального списка товаров | 2 | Страница плюс картинки, без запроса на каждый товар |
| SQL людей / сообществ | по 1 | Аватары затем читаются отдельными защищёнными GET |
| Десктопный CLS каталога | 0,3025 | Воспроизведён отдельным наблюдением за DOM и layout shifts |

По переданным байтам заметны `/logo_anim_cart.mp4` (≈274 КБ), `/cartv2_bg.png`
(≈166 КБ) и четыре аватара по ≈145 КБ. Анимация корзины видна в интерфейсе;
считать её скрытым неиспользуемым ресурсом нельзя. Сжатие/производные изображений
требуют отдельной проверки качества и сохранения отзыва доступа к аватарам.

Источник скачка каталога подтверждён: ServiceProductGrid сначала отдаёт две
колонки серверного HTML, затем `useSyncExternalStore` перестраивает их в четыре.
В дополнительном прогоне 2 колонки появились на 19 мс, 4 — на 89 мс, сдвиг —
на 98 мс; источниками layout shift были колонки и карточки. На момент этого
замера исправления ещё не было. Затем выполнен отдельный этап:
[адаптивная раскладка без перестройки](2026-10-19-catalog-css-layout.md),
с сохранением порядка товаров, раскрытия карточек и клавиатурной навигации.

На одиночном локальном наборе нет основания объяснять медленную загрузку только
БД или автоматически добавлять Redis. Нагрузочное тестирование, большая история
медиа полного DTO, Docker, Actions, серверный proxy и production ещё не проверены
этим этапом. Commit/push/deploy не выполнялись; весь релиз остаётся в работе.

## Доказательства

Каталог задачи `.../01a131d3-2f27-7762-98e4-da371d9cfc34/`:
`public-runtime-results.json` — 8 прогонов и 8 проверок;
`public-runtime-functional-results.json` — 10 проверок и диагностика CLS;
`public-runtime-api-after.jsonl` — SQL/байты/длительность холодного запуска;
`public-runtime-api.jsonl` — отдельный функциональный запуск;
`public-runtime-frontend-tests.log`, `public-runtime-build.log` и снимки страниц.
Предварительный файл `public-runtime-before-unverified-throttle.json` оставлен
как сырая диагностика; ускорение LCP по нему не заявляется.

Ошибка первоначального функционального набора была в fixture: одинаковые size/color
повторялись, и конструктор корректно запрещал покупку неоднозначного SKU. Последний
функциональный запуск использует уникальные пары. Данные холодного измерения и
функциональной проверки поэтому не считаются побайтово одинаковыми наборами.
Свои процессы, БД, объекты, временная сборка и приватная конфигурация удалены.
