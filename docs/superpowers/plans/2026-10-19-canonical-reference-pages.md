# Общие страницы справочников CRM и производства

Статус: локальный этап общего рефакторинга. Основной редактор товаров — новый кабинет производства → «Пресеты».

## Что изменилось

Новый кабинет уже использовал страницы, но восемь canonical CRM GET оставались отдельной реализацией. Списки моделей загружали размеры, ID товаров и опубликованную техкарту; шесть ассортиментных списков возвращались массивами целиком. Теперь оба HTTP-входа используют одни `ReferenceDirectoryService` / `StockDirectoryService` и SQL-проекции.

| CRM GET | Общий вид справочника |
| --- | --- |
| `/api/crm/reference/garment-models` | `models` |
| `/api/crm/reference/fabrics` | `fabrics` |
| `/api/crm/assortment/fabric-requirements` | `fabric-requirements` |
| `/api/crm/assortment/accessory-categories` | `accessory-categories` |
| `/api/crm/assortment/accessories` | `accessories` |
| `/api/crm/assortment/accessory-requirements` | `accessory-requirements` |
| `/api/crm/assortment/boxes` | `boxes` |
| `/api/crm/assortment/packaging-rules` | `packaging-rules` |

Ответ — `{items,next_cursor}`, по умолчанию24, максимум100 записей. Названия связей приходят из JOIN; карточки моделей содержат счётчики без дочерних массивов, фурнитура — `model_count` без `model_ids`. `CrmReadService/Repository` теперь отвечают за проекты и производственные единицы; удалены восемь старых списковых методов и связанные агрегатные методы/DTO.

## Контракт и права

CRM продолжает требовать identity Bearer с `crm.access`. Производственный вход сохраняет собственную HttpOnly cookie и свою проверку роли. Общий сервис данных не объединяет эти учётные записи. Чтения имеют `Cache-Control: no-store`; неверный курсор возвращает422 `invalid_cursor`.

`active` заменяет прежний `is_active`. Поиск, сортировки, категория, остаток и cursor используют те же схемы, что кабинет. Фильтр `garment_model_id` сохранён для ткани/фурнитуры/упаковки и применимости фурнитуры; добавлен в общие схемы, SQL и fingerprint курсора. Это положительный32-битный ID; лишние параметры отклоняются. Для расхода ткани остаются ID модели и пагинация, без несуществующих поиска/сортировки.

Добавлен `GET /api/crm/reference/garment-models/{id}`: отдельный источник редактора, совпадающий с production source. Он читает активную сетку `LIMIT101`; при превышении100 возвращает409 `model_size_limit` без усечения. Обработка404/409/no-store общая для двух HTTP-входов.

Это намеренная замена старого read-контракта. Старые массивы, integer cursor, параметр `is_active` и дочерние коллекции не поддерживаются параллельно. В текущем frontend прямых вызовов этих восьми CRM URL не найдено; кабинет уже использует production directory API. Внешние потребители требуют согласованного перехода. Добавление поля фильтра меняет fingerprint у затронутых справочников: курсор от предыдущего выпуска отклоняется; клиент перечитывает первую страницу.

## Сохранение фурнитуры

Create/PUT возвращают только скалярный `CrmAccessoryRead`; `model_ids` удалён из DTO и frontend-типа. Команда больше не делает `selectinload` применимости. Под блокировкой перечитывается актуальная запись через `populate_existing` перед `expected_version`. Связи с моделями не изменяются. Счётчик остаётся в отдельной карточке списка.

Новых Provider, способов хранения и миграций БД этот этап не добавляет. Текущая схема остаётся0076. Ограничение размера ответа не делает агрегатный COUNT или сортировку по счётчику постоянными по стоимости: большие поисковые/агрегатные планы остаются отдельной задачей.
