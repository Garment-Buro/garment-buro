# Загрузка заказа производства без запросов на каждую единицу

Этап локального рефакторинга, 19 октября 2026. Общий релиз продолжается.
Основной редактор товаров — производство → «Пресеты»; старый `/admin/models`
перенаправляет в него. Этот этап меняет чтение производственного заказа.

Следующим [этапом запуска](2026-10-19-deployment-application-cutover.md) API/frontend
остановлены на время миграций. Совместимость прежнего образа с новой схемой
остаётся условием выпуска; результаты чтения ниже относятся к этому этапу.

## Проблема и устройство

`ProductionReadService.detail` повторно читал модель, размеры, техкарты,
файлы и раскрой для каждой единицы заказа. Поиск работы внутри цикла также
повторно обходил общий список. Новый `ProductionDetailRepository` собирает данные
одного запроса пакетами до 256 ID; service использует словари и формирует прежний
ответ. Это request-local данные, без нового кеша, Redis или Provider.

`read_repository.py` отвечает за SQL и ограничение графа текущим заказом;
`read_service.py` — за сборку ответа и проекцию роли;
`evidence.py` — за общие проверки снимка, плана, хеша и принадлежности файла.
Команды сохранения продолжают использовать тот же валидатор. Файлы из пакета
не становятся автоматически видимыми соседней единице. Private/ready и связь
с единицей/техкартой проверяются отдельно. Pending/public/чужие файлы не скрывают
причину ошибки проверки спецификации. Уже загруженный ORM-объект обновляется
из БД: изменение статуса файла другим соединением не обходится identity map.

Только технолог загружает данные редактирования. Раскрой нужен tech/cut.
Сохранены закреплённые архивные/неактивные ревизии техкарт, контрольные точки,
все единицы заказа и приоритет ткань резерва → варианта → основной нормы.

## Сравнение на PostgreSQL 17

Сохранённый прежний service и новый запускались в отдельных холодных сессиях
на одинаковых синтетических данных.24 случая:1/32 единицы, с планом/без,
шесть ролей. Все ответы полностью совпали. Счётчик включает SELECT и WITH.

| Роль и заказ из 32 единиц | Было SQL | Стало SQL |
| --- | ---: | ---: |
| Технолог, без планов |166|12|
| Остальные пять ролей, без планов |166|7|
| Технолог, с планами |360|19|
| Раскрой, с планами |359|15|
| Упаковка, с планами |360|13|

Для одной единицы без плана у технолога запросов стало 11→12:
пакетная загрузка имеет фиксированную стоимость. Ускорение каждого маленького
заказа не заявляется. Для одной запланированной единицы tech осталось 19 SQL.

## Физические планы и миграция

Само уменьшение числа SQL не ограничивало работу каждого запроса. На истории
из 10000 чужих резервов PostgreSQL выбирал глобальный PK и посещал 10001 строку
для первого резерва нужного плана. Индекс с равенством внутри correlated LIMIT
сам по себе не исправил выбор planner.

Миграция `20261019_0080` заменяет два одно-колоночных индекса составными:
резервы `(production_plan_revision_id,id) INCLUDE(fabric_id)` и нормы
`(garment_model_id,is_primary DESC,id) INCLUDE(fabric_id)`.
Резерв ищется от начала диапазона плана; проверка владельца после LIMIT не
позволяет взять следующий план при отсутствии собственного резерва.
Материализованный CTE выбирает ID ткани один раз, активность проверяется по PK,
затем загружается выбранная ткань. Это исключает полный проход справочника.

Долговременный тест исполняет 19 точных запросов reader в режимах custom/generic:
38 EXPLAIN ANALYZE BUFFERS. Набор:50 других моделей,10000 чужих резервов,
10000 посторонних файлов,10000 тканей и 10200 норм/лекал.
Резерв посещает 1 строку вместо 10001; норма 1, ткани до 2 по PK,
файлы/медиа до 2 на запрос. Выбранный слот лекал посещает 201 строку:
его собственная история остаётся линейной. Поиск активной ткани также зависит
от норм выбранной модели, если первые кандидаты неактивны. Чужие модели не просматриваются.

Downgrade/upgrade миграции выполнены дважды на непустых таблицах; имена индексов
и хеши строк проверены. ORM metadata и Alembic совпадают. Обычный DDL создания
индексов требует окна выпуска и оценки блокировок на реальных объёмах.
Работающий API во время миграций и совместимость старого образа с новой схемой
остаются отдельной проверкой выпуска; автоматического downgrade нет.

## Проверки и границы

72 профильных теста/0skip на свежих PostgreSQL 17/MinIO прошли: права/хеши,
закреплённые карты, обновление ORM, несколько моделей, все 300 единиц с пакетами
до 256, точные SQL-планы, миграции и schema drift. Ruff прошёл;700 файлов
соответствуют format. Полный строгий набор: 1266 backend/0skip, 502 с; свежие PostgreSQL 17/MinIO.
Четыре изолированные БД; временные процессы, данные и конфигурация удалены.
Карта:20 offline suites,666 валидных ссылок;320/390/736 px без переполнения.

Frontend не менялся:621 frontend/0skip, build и browser gates относятся к
предыдущему этапу Phantom UI и здесь повторно не запускались. Нет нового
браузерного замера LCP, телефонного теста, Docker, Actions или production.
Полный ответ по-прежнему растёт с количеством единиц заказа, ревизий и файлов;
пагинация единиц этим этапом не вводилась. Stage/commit/push/deploy не выполнялись.
