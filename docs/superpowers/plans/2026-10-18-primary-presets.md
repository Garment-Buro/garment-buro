# Основное управление товарами — «Пресеты» производства

Решение пользователя: новый кабинет производства является основным. Этап выполнен локально; это не выпуск на сервер.

## Поведение

- `/production?section=presets` открывает «Пресеты» после проверки производственной сессии. `product=new` открывает создание, положительный `product=<id>` — деталь товара, включая скрытые товары и товары другого источника. Неверный ID отклоняется. Закрытие прямого редактора убирает параметр товара из адреса.
- `/admin/models`, `/admin/products/new`, `/admin/products/{id}/edit` перенаправляют в соответствующий новый адрес. Старые таблица, экран списка, экран редактора и управляющий ими hook удалены. Ссылка веб-админки ведёт сразу в «Пресеты».
- Подтверждение удаления теперь доступно в карточке пресета. Отмена ничего не отправляет. Во время удаления повторное действие заблокировано; отказ показывает причину и позволяет повторить. Успех обновляет список и счётчики.
- Production DELETE использует тот же CatalogWriteService: блокировка товара, запрет активных физических/тканевых резервов, транзакция и audit checksum. Связанные записи могут запретить удаление; в таком случае предлагается скрыть товар. Контракт DELETE по явному действию сохранён без добавления CAS. Изменение товара по-прежнему требует expected_version.

## Права

Ни новые роли, ни новые разрешения пользователям не выданы. Пресеты и DELETE доступны системному администратору производства, при включённых CRM/catalog writes. Обычный сотрудник и менеджер только производства получают отказ. Старый identity-вход сам по себе не даёт производственную сессию: перенаправление сначала показывает вход. Канонический identity API сохраняет свои прежние проверки; дублирующей формы в браузере больше нет.

## Выбор товаров для коллекции

- В административной форме больше нет ограничения первыми 24 товарами. Поиск и продолжение используют ограниченный серверный запрос, максимум 24 карточки за страницу.
- Общий CollectionProductPicker отвечает только за отображение, порядок и лимит 50. Два небольших адаптера читают каталог по разным правилам: identity/canonical admin читает также скрытые товары; владелец использует только публичный каталог.
- Выбранные ID и порядок не зависят от текущего поиска/страницы. Административная форма держит максимум 50 выбранных коротких описаний в памяти открытого компонента. Владелец отдельно загружает выбранные ID; недоступный товар явно помечается, ошибка чтения не очищает выбор.
- Подтверждённая коллекция хранится на сервере. Нет JSON-файлов, localStorage или общего глобального кэша выбора. Проверки допустимости публикации остаются серверными.
- Ошибка следующей страницы оставляет ранее загруженные записи. Неверный cursor убирает неработающее продолжение и предлагает перечитать список. Новый поиск отменяет предыдущий. Пока форма сохраняется, поля блокируются.

## Проверки

- Полный backend: 1034 passed, 0 skipped; 290.54s, Python 3.12.12, отдельные PostgreSQL 17 и настоящий MinIO. Временные процессы, БД, файлы и конфигурация удалены.
- Новый HTTP тест проверяет анонимный вход, ограниченного менеджера, оба флага записи, физический резерв, успешное удаление, повторный 404 и единственное audit событие. Тканевые резервы остаются в общем сервисе и общем регрессионном наборе.
- Frontend: 547 passed, 0 skipped. Lint/build проходят с прежними предупреждениями CustomerMediaImage alt и Alumni Sans SC fallback.
- `npm run check:admin-catalog` использует настоящий standalone Next и Chromium с синтетическим HTTP API. SQL, транзакции и RBAC проверяются отдельно backend тестами. Проверки охватывают перенаправление старых адресов, общую форму/CAS/физический товар/загрузку изображений, подтверждение и повтор удаления; 130 товаров, страницы по 24, ошибку продолжения, запоздалый поиск, скрытый товар, порядок и предел 50, отправленный product_ids, оба адаптера выбора, недоступные выбранные товары и ширины 320/390/736.
