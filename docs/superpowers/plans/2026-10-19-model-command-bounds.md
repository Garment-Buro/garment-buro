# Сохранение моделей без загрузки архива размеров

Статус: локальный этап общего рефакторинга. Основной редактор товаров — новый кабинет производства → «Пресеты».

## Проблема

Ограниченный GET редактора не устранял нагрузку при сохранении: `get_garment_model_for_update` делал `selectinload` всей коллекции размеров. Этим же методом пользовались привязка товара и создание техкарты, хотя размеры им вообще не нужны. PUT возвращал весь архив через ORM-коллекцию.

## Границы команды

- Родительская модель перечитывается под `FOR UPDATE / populate_existing`, затем проверяется `expected_version`. Коллекция размеров закрыта `raiseload`: случайное обращение не запускает скрытый запрос.
- Обновление читает активную сетку по индексу `(garment_model_id,is_active,sort_order,id)` с `LIMIT 101`. Если активных размеров больше действующего лимита100, команда возвращает409 до изменения модели/размеров. Неполная сетка не архивирует невидимые строки.
- Второй запрос получает только коды из проверенного payload, максимум100, по уникальному `(garment_model_id,code)`. В одном SQL значения кодов превращаются в небольшой набор, для каждого находится ID, затем гидратируются только найденные записи. PostgreSQL материализует набор ID один раз. Запрос включает архивные совпадения и обновляет устаревшие ORM-объекты через `populate_existing`. Пустой набор не вызывает этот SELECT.
- Совпавший код сохраняет прежний ID; архивный размер реактивируется с увеличением актуальной версии. Новые коды создаются, отсутствующие активные размеры архивируются. Остальной архив не загружается и не изменяется. В успешной команде загружается не более100 активных и100 запрошенных размеров; пересечения используют один ORM-объект.
- Базовые длина/ширина вычисляются по целевой активной сетке. Привязка товара и создание техкарты блокируют только модель и не читают размеры.

Это предполагает прежнее правило: команды размеров проходят через блокировку родительской модели. Прямые SQL-изменения в обход service не приобретают такую защиту автоматически.

## Почему недостаточно обычного IN

При100 кодах, повторяющихся у101 модели, обычный `code IN (...)` выбирал последовательный проход по30 100 размерам. Даже точечный запрос мог выбрать глобальный индекс `code`, отбрасывая по100 чужих размеров перед каждым совпадением. Это реальные планы, а не вывод из наличия индекса.

Миграция `20261019_0076` удаляет глобальный индекс `code`: в приложении нет чтения размера по коду без модели; поиск вариантов всегда ограничен моделью. Уникальный индекс `(garment_model_id,code)` сохраняет прежнее правило уникальности и дополнен `INCLUDE(id)` для поиска ID. Материализация предотвращает повторение скалярных поисков при устранении дубликатов ID. План может сортировать небольшой набор из максимум100 запрошенных ID; история размеров не сортируется.

Миграция обратима, ID и строки не переписываются. Она перестраивает уникальный индекс и берёт блокировку таблицы; перед production-выпуском длительность нужно оценить на фактическом объёме данных. Этот локальный этап миграцию в production не запускал.

## Ответ и журнал

Создание и обновление возвращают явный `CrmGarmentModelReferenceRead`, построенный из скаляров модели и целевой активной сетки. Поля ответа сохранены; `sizes` теперь содержит только активные размеры в порядке `sort_order,id`, как GET редактора. DTO не выдаётся за частично загруженную ORM-коллекцию, relationship не подменяется и не очищается. Production и canonical CRM write-маршруты используют один результат. Текущий frontend после подтверждённой записи обновляет список и не использует архив из write-ответа.

Новое событие обновления содержит `active_sizes_count`, `created_sizes_count`, `reactivated_sizes_count`, `archived_sizes_count`. Прежние события остаются неизменными. Старый `retained_sizes_count` в новых событиях больше не вычисляется: для сохранения не нужен ни архив, ни полный `COUNT` истории. Хеш проверенного payload и версии события сохранены.

## Проверки

Профильные **32 теста без пропусков** прошли на SQLite и собственном PostgreSQL17/MinIO, Python3.12.12:

- 5 000 архивных размеров, реактивация глубокого кода с прежним ID/актуальной версией, новый код, архивирование прежнего активного размера, неизменность другого архива и точные базовые мерки.
- Измерение реальных SELECT/identity map: два ограниченных чтения размеров, отсутствие загрузки relationship и полного COUNT; малый PUT-ответ совпадает с последующим GET. Привязка товара/создание карты не читают таблицу размеров.
- Превышение100 активных размеров отклоняется и в GET, и в PUT; имя, версии и все активные строки остаются прежними.
- Два настоящих PostgreSQL-сеанса: второй PUT ожидает блокировку, что подтверждается `pg_stat_activity.wait_event_type='Lock'`. После commit первого второй получает конфликт версии, не меняя модель, размеры и журнал.
- Custom и настоящий `PREPARE / force_generic_plan` на20 000 архивных/активных размерах и10 100 размерах с повторяющимися кодами: активная сетка читает не более101 строки; выбор2 и100 глубоких/частых кодов проверяется по фактическим строкам индексных поисков, а не только имени индекса. Вместе с прежними editor-option проверками сохранены22 плана.
- Два понижения/повышения миграций проверяют сохранность полной строки архивного размера, его ID/версии/мерок, модели и категорий; состав уникального индекса и удаление/восстановление глобального индекса проверяются отдельно.

Полная backend-регрессия: **1105 тестов без пропусков**, Python3.12.12, свои PostgreSQL17/MinIO; runner завершился за356с и удалил собственные процессы/базы/объекты/приватную конфигурацию. Ruff/format668 прошли. Frontend этим этапом не менялся; предыдущие615 тестов, TypeScript/lint/build и standalone browser gate здесь повторно не запускались.

Доказательства: `backend-dependencies/model-commands-focused*`, `model-commands-verified*`, `model-commands-query-plans.json` в локальном каталоге задачи.
