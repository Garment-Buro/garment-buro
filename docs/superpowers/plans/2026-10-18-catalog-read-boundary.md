# Чтение товаров в управлении

18 октября реализована общая граница чтения административного каталога.
Общий релиз продолжается; stage/commit/push/deploy не выполнялись.

## Было

GET `/api/products` анонимно возвращал все товары, включая неактивные.
Отдельные admin hooks скрывали ошибку за пустым списком. Новый кабинет
«Пресеты» также получал все товары через отдельный CRM repository и фильтровал
их в браузере. Остаток зависит от ткани/резервов, а не только поля количества.

## Стало

- `/api/products`, `/counts`, `/{id}` и список категорий требуют staff permission.
  Без входа401, обычному покупателю403. В read-only конфигурации эти старые
  административные маршруты отсутствуют; публичная витрина продолжает работать.
- Identity staff, CRM reader и production admin используют один
  `CatalogAdminReadService` и repository; их проверки ролей остались отдельными.
  HTTP больше не вызывает unbounded `CatalogService.list_products`.
  Этот метод сохранён только для явно запускаемого offline comparison CLI.
  Невостребованный GET `/{id}/variants` удалён.
- Общий ответ `{items,next_cursor}`: по умолчанию24, максимум100 товаров.
  На сервере выполняются поиск по названию/slug/тегам, фильтры модели,
  категории, лендинга, источника, видимости и наличия, десять порядков сортировки.
  Cursor связан с фильтрами и сортировкой; одинаковые значения разрешаются ID.
- SQL-наличие совпадает с checkout: метры минус резерв, расход округляется
  вверх до0.001м, одна ткань не суммируется по нескольким размерам. Неявная
  ткань допустима только для модели с единственным материалом.
- Оба frontend списка читают страницы через общий `usePagedCatalog`;
  `usePublicCatalog` остаётся публичной настройкой с сохранением совпавшей SSR
  страницы. Новых Provider и глобального кеша товаров нет.
- Административное чтение имеет10-секундный deadline, no-store, отмену поиска,
  явный повтор и продолжение списка. Ошибка дозагрузки сохраняет карточки;
  неверный cursor предлагает обновить список. Customer admin проверяет
  accountEpoch; поздний ответ другого входа не показывается.
- Кабинет получает отдельные групповые счётчики. Названия модели и категории
  приходят вместе с карточкой и не зависят от первой страницы справочника.
- Ошибка детали старого редактора блокирует форму, показывает повтор;
  смена аккаунта/товара пересоздаёт форму. Перенос старых проектов читает модель
  через публичный `/api/catalog/products/{id}`, соблюдая доступность товара.

## Проверка

- Unit/HTTP: права, read-only запуск, bounded/invalid query, cursor, поиск,
  источники и наличие. Native PostgreSQL: все10 сортировок без пропусков,
  Unicode/буквальные спецсимволы, категория/модель/видимость и draft-лендинг,
  совпадение SQL-наличия с checkout.
-20 000 дополнительных товаров, половина привязана к модели/ткани: страницы
  по24, не более6 SQL. В первом локальном профильном прогоне4–42мс на страницу.
  Это синтетический стенд и время service/database, не internet latency,
  не production benchmark и не гарантия на любом распределении вариантов.
-542 frontend tests, lint (одно прежнее предупреждение alt), production build
  с включёнными session/catalog flags. `npm run check:admin-catalog`: настоящий
  standalone Next/Chromium и синтетический HTTP backend —24+9, append failure/
  retry, поздний поиск, фильтры, cursor refresh, bearer, отказ/повтор детали.
  Ширины320/390/736/1280 без переполнения и ошибок JavaScript. SQL/RBAC
  проверяются отдельно настоящими backend тестами, а не этим HTTP fixture.
- Полный backend:1026 passed,0 skipped за272.83s на Python3.12.12,
  свой PostgreSQL17, четыре отдельные БД и настоящий MinIO из pinned source
  tag. Ruff/format569 файлов прошли. После полного прогона метрика времени
  перенесена в совместимое с xunit2 поле suite; этот тест повторён отдельно.
  Процессы, БД, объекты и приватная конфигурация удалены. Это не Docker/Actions
  и не production; предупреждение Starlette о httpx TestClient остаётся.

## Следующая часть

Два редактора ещё существуют. У нового кабинета модели/ткани в выборе
ограничены первой страницей справочника, а список лендингов/его membership
всё ещё загружается целиком. У второго редактора есть дополнительные
media-поля, у нового — CRM model/fabric references и matrix вариантов.
Следует перенести нужные возможности в основной кабинет и только затем
удалить второй UI и его API записи. Этот этап закрывает чтение товаров,
а не объявляет всю административную номенклатуру масштабируемой.

Docker/Actions/public runtime, настоящий телефон, предыдущий образ/схема,
backup с реальными внешними писателями и полный платёжный E2E остаются
условиями выпуска общего релиза.

### Уточнения для следующего этапа

- `/production/admin/assortment/models` и `/fabrics` жёстко используют
  `cursor=None, limit=100`; UI не умеет продолжать их. Это не полный справочник.
- `/product-communities` вызывает `PartnerRepository.list_all_landings` и
  возвращает все `product_ids`. Следует вынести membership видимых24 карточек
  в bounded read и отдельно читать/искать лендинги.
- Список сейчас включает references вариантов, потому что публичная
  публичная `ProductVariantResponse` не содержит sku/garment_size_id/fabric_id.
  Следующий этап уже добавил `CatalogAdminDetail` с актуальными ссылками;
  карточке списка теперь достаточно count и отображаемого артикула.
  См. 2026-10-18-product-editor-integrity.md.
- Галереи `desktop_slider_images`, `mobile_product_slider_images`,
  `mobile_slider_images`, `gallery_images`, `desktop_card_images` и основные
  `image_left/image_right/mobile_card_image` ещё читаются конструктором
  (`constructor.ts`, `cartPreparation.ts`, `useConstructorDerivedState`,
  `SizeFitModal`). Их нельзя выкинуть вместе со старым экраном.
- Старые video/poster и схемы размеров требуют отдельной проверки потребителей:
  наличие поля в payload ещё не доказывает использование на живой странице.
  Не следует переносить все старые поля в новый интерфейс автоматически.
