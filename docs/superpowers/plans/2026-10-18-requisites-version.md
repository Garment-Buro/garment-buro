# Защита банковских реквизитов от устаревших форм

Этап выполнен локально, без commit/push/deployment. Основной интерфейс товаров остаётся производство → «Пресеты»; старые admin-адреса направляют туда. Этот этап продолжает независимую форму реквизитов кабинета владельца.

## Поведение

Раньше PUT блокировал существующую строку только на время записи: две формы могли по очереди успешно сохранить разные данные, и вторая затирала первую. Теперь GET возвращает служебную `version`, PUT обязательно принимает целочисленную `expected_version`. Ноль допускает создание только после подтверждённого GET null; существующие документы начинаются с версии 1. Пропущенная, логическая, строковая, дробная, отрицательная или слишком большая версия отклоняется с 422.

Сервис сначала блокирует стабильную строку PartnerProfile, затем читает реквизиты под блокировкой с populate_existing. Это сериализует и первые создания, когда строки реквизитов ещё нет, и последующие обновления. Порядок совпадает с блокировкой профиля при заявке выплаты. Версия сравнивается до шифрования и любых изменений. Устаревший запрос получает 409 с кодом `requisites_version_conflict`, без банковских данных; ciphertext, nonce, tag, digest, updated_at и версия сохраняются. Успех увеличивает версию на один. Максимальная int32 версия отклоняет дальнейшее обновление без переполнения.

Версия не входит в шифрованный документ: базовый DTO банковских полей отделён от DTO записи и ответа. Подготовка банковской выплаты выбирает только базовые поля, поэтому version, expected_version и updated_at не попадают в запрос провайдеру или банковский snapshot. Права и прежний доступ invited/non-suspended профиля к собственным реквизитам сохранены.

## Форма и оболочки

`PartnerRequisitesCard → usePartnerRequisites → RequisitesEditor` — прежний независимый блок, без нового Provider. Состояние чувствительных полей живёт только в памяти текущего аккаунта/epoch. Browser storage не используется.

После конфликта ввод остаётся на экране, повторная запись запрещена. Раскрываемое действие «Загрузить актуальные реквизиты» объясняет замену черновика; кнопка «Заменить черновик актуальной версией» запрашивает сервер явно. Только успешный GET заменяет черновик и разрешает сохранение с новой версией. Ошибка или отмена GET сохраняет прежние поля и конфликт. Закрытие/повторное открытие не перечитывает и не очищает загруженный черновик. Смена аккаунта отбрасывает запоздалые результаты. Отказ GET после подтверждённой записи не повторяет PUT.

## Миграция и выпуск

`20261018_0072` добавляет положительную integer version с default 1. Исторические ciphertext/nonce/tag/schema_version/key_version/payload_sha256/updated_at не переписываются. Обратная миграция удаляет только служебную версию; повторный upgrade устанавливает её заново в 1. Upgrade/downgrade проверены на отдельной PostgreSQL 17 с исторической записью, вставленной в схему 0071.

Миграция должна предшествовать новому backend; frontend/backend выпускаются согласованно. Старый frontend без expected_version получит 422; новый frontend не открывает сохраняемую форму по старому ответу без version. При откате схемы нужно остановить новые writers: существующие номера версий при повторном upgrade не восстанавливаются. Это локальная проверка миграции, а не подтверждение отката production образа.
