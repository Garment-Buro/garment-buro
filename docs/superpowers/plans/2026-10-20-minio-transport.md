# Runtime-запросы к MinIO: ожидание и повторы

MinIO остаётся выбранным хранилищем фотографий и файлов. Этот этап меняет
Python-клиент приложения, а не сервер, данные или storage provider.

## Воспроизведённая проблема

Установленный minio7.2.20 без собственного HTTP-клиента задаёт300 секунд
для connect/read и пять повторов через urllib3. Стандартный набор методов
включает PUT и DELETE; после неоднозначного ответа в versioned bucket возможны
лишние версии или delete markers. Retry-After может навязать долгий сон.

Новый тест использует реальный SDK и собственный ThreadingHTTPServer на
loopback с временным портом и синтетическими ключами. Регион бакета
получается обычным S3-запросом; внутренний region cache не подменяется.
До изменения приложения:2 passed/19 failed. Подтверждены шесть обращений
вместо двух для GET/HEAD и вместо одного для PUT/DELETE, отсутствие короткого
read timeout и попытка сна на60 секунд. Сон в этом тесте перехватывается,
поэтому сам тест не ждёт минуту. Ранее один первоначальный прогон упал из-за
недостающего public URL тестового конфига; после исправления fixture проблема
воспроизведена на самих сетевых операциях.

## Новое поведение

- MINIO_CONNECT_TIMEOUT_SECONDS:3, конечное число больше0, максимум30.
- MINIO_READ_TIMEOUT_SECONDS:15, конечное число больше0, максимум60.
- GET/HEAD: максимум две попытки, включая первую; общий retry budget1
  распространяется на connect/read/status, а не складывается для каждого вида.
- PUT/DELETE и multipart POST не повторяются после ответа/read failure.
  Допустим один connect retry до отправки запроса. Исключена повторная отправка
  через HTTP redirect. Небезопасная повторная запись не заменяется молчаливым успехом.
- Retry-After не задаёт sleep. Повторы5xx ограничены500/502/503/504.
- TLS требует проверенный сертификат. Сохраняется SSL_CERT_FILE, иначе certifi.
- Пул создаётся при startup и освобождается при shutdown/ошибке construction;
  повторный startup не создаёт второй пул, после shutdown можно запустить снова.
  Для внедрённого test client собственный пул не выделяется.
- HTML-ошибки proxy и SDK ServerError нормализуются в существующую transport
  boundary. API возвращает503 без proxy diagnostics, metadata остаётся failed,
  прежний avatar не заменяется, ссылки на несохранённые изображения не выдаются.
  S3Error сохранён для обработки NoSuchKey/NoSuchPolicy.

Это socket inactivity timeouts на попытку. DNS, вся загрузка файла, чтение
с непрерывно поступающими байтами и последовательность нескольких S3-операций
не получают общего дедлайна. Большие файлы не обязаны завершаться за15 секунд.
Однократный bootstrap бакетов использует отдельную политику и здесь не менялся.

Оба параметра доступны в примерах окружения и передаются local backend и
project-media-worker. Server backend/workers наследуют их из env_file.
certifi и urllib3 объявлены прямыми зависимостями. Оба lock заново сгенерированы;
все46 production/55 development versions совпадают с прежним снимком.
