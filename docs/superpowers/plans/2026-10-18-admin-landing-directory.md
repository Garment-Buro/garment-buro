# Постраничные лендинги и компактные карточки товаров

18 октября. Этап общего рефакторинга выполнен локально; общий выпуск открыт.
Stage/commit/push/deploy не выполнялись.

## Что исправлено

Раньше production «Пресеты» сразу загружал каждый лендинг и все его product_ids,
даже для стартового экрана со счётчиками. Карточка каждого товара несла весь
массив вариантов, а frontend обходил полный список лендингов, чтобы определить
членство товара. В identity `/admin/partners` список дополнительно получал весь
контент всех лендингов. Размер ответа рос с общей базой.

- Оба административных списка используют общий router adapter → service →
  repository. Query: поиск, статус, limit24 по умолчанию/max100, cursor по
  убывающему ID. Cursor проверяет фильтры. Unicode и буквальные %, _, обратный
  слеш используют существующие правила БД. Неверные query-поля отклоняются.
- Карточка лендинга содержит ID/версию/название/адрес/картинку/статус/имя владельца
  и число товаров. Content, description и product_ids не выбираются. Счётчик
  товаров вычисляет SQL через индекс FK; весь ORM лендинга не материализуется.
- Identity directory по-прежнему требует partners.manage и включённую программу;
  production — системного администратора. Публичные условия публикации не
  перенесены в административный reader: здесь видны также черновики/архив.
- Дополнительные метаданные членства включены только внутренним адаптером
  production. Identity/CRM списки товаров их не выбирают: community_count и
  счётчик лендингов — null, communities —[]. Это «не читали», а не ложный ноль.
  Передать include_communities через query нельзя. Отдельный identity directory
  проверяет partners.manage. Нативный тест проверяет отсутствие partner SQL
  при обычном чтении каталога; production HTTP — настоящие counts и превью.
- Удалён `list_all_landings`, старый frontend getAdminPartnerLandings и DTO
  ProductCommunity с product_ids. Старый API ответа массивом не сохраняется.
- Обзор production читает только счётчики; категории загружаются при открытии
  списка товаров. Лендинги читаются при открытии своего раздела. Выбранная
  карточка хранится отдельно от страниц списка, а товары запрашиваются по её
  действительному community_id. Поиск не меняет выбранный состав в браузере.
- `useAdminLandingDirectory` общий для двух способов входа: local mounted state,
  deadline10s, cancellation, ключ аккаунта/сессии. Ошибка продолжения сохраняет
  строки, неверный cursor требует обновить список. Источника данных в browser
  storage и нового Provider нет. Кабинет partners пересоздаёт формы при смене
  аккаунта; запросы и результаты мутаций проверяют владельца сессии.
- Каталог возвращает variant_count и первый непустой SKU вместо массива
  вариантов. Доступность выбирается SQL той же формулой, которая уже сверяется
  с checkout; список не читает ORM варианты. Деталь/редактор остаются полными.
- Членство товара вычисляется одним запросом только для выбранной страницы
  товаров, максимум100 ID. Window count и row_number дают точное количество
  лендингов и не более3 названий на товар. UI показывает «ещё N»; это явное
  сокращение превью, не ошибочное утверждение «Без лендинга».
- Публикация из summary отправляет только status/expected_version; полный состав
  и контент не отправляются назад. После записи список читает новую версию.

справочники требуют отдельного аудита границ. Карточка каталога ещё читает Product scalars

каталога без своего поиска/продолжения. Здесь исправлены чтение лендингов и
карточек товаров; вся административная часть ещё не объявляется масштабируемой.

предыдущий образ/схема, backup с внешними писателями и публичная оплата остаются
обязательными проверками общего выпуска.
