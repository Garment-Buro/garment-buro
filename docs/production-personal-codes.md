# Личные коды производственного терминала

Формат: 6 цифр. Первая цифра — основная категория, остальные пять генерируются криптографически случайно. Например, `604812` и `693057` относятся к ВТО; это примеры формата, не действующие коды. Коды со стартовым нулём сохраняются как строки.

| Начало | Участок |
| --- | --- |
| 0 | Технолог / руководитель цикла |
| 1 | Комплектовка |
| 2 | Раскрой |
| 3 | Печать DTF |
| 4 | Нанесение |
| 5 | Пошив |
| 6 | ВТО |
| 7 | ОТК |
| 8 | Упаковка |
| 9 | Отправка |

Префикс нужен для узнаваемости, но не выдаёт права: backend проверяет активного сотрудника и его текущие роли в БД при каждом запросе. При нескольких ролях префикс отражает выбранный основной участок, доступ определяется всеми назначенными производственными ролями. Заказные события сохраняют конкретного `actor_user_id`.

## Выдача и отзыв

Сначала заведите сотрудника в identity и назначьте нужную производственную роль штатным механизмом. Для существующих сотрудников используется `bootstrap_role.py`; почта может оставаться идентификатором кадровой записи, но для входа в терминал она не требуется. Этот этап не создаёт выдуманных сотрудников и не назначает роли по введённой цифре.

В интерактивном терминале backend, с приватным конфигом нужного окружения:

```sh
python -m scripts.production_code --user-id ID --station sewing
python -m scripts.production_code --user-id ID --revoke
```

Первая команда выдаёт новый код один раз и отключает предыдущие. Вторая отзывает доступ по коду. Не перенаправляйте вывод в логи, CI, отчёты или Git. Неизвестный ID и отсутствующая роль не позволяют выдать код. Выдачу и отзыв выполняет оператор с доступом к backend; административной веб-формы управления сотрудниками пока нет.

## Защита

- В БД хранятся только HMAC-отпечатки кодов с domain separation и секретом `IDENTITY_OTP_PEPPER`, не открытый PIN. Отозванные отпечатки остаются, чтобы старый код не достался другому работнику.
- Личные коды не используются как session token. После входа создаётся отдельная случайная серверная сессия на 8 часов, в браузере — HttpOnly/Secure/SameSite=Strict cookie с путём `/api/production`. Это не identity-сессия и не доступ к выплатам/профилю/админке.
- Выход удаляет сессию на сервере. Перевыпуск/отзыв кода, блокировка пользователя или снятие основной роли делают старую сессию непригодной.
- Счётчики попыток общие для экземпляров backend и атомарные в БД: 10 запросов входа с IP и 100 суммарно за 15-минутное окно, включая успешные. При отказе БД вход закрыт. Счётчики не откатываются при неверном коде.
- POST-запросы проверяют Origin. Прокси должен перезаписывать клиентские IP-заголовки, backend не должен быть доступен напрямую из Интернета.
- Выдача, отзыв и успешный вход попадают в security audit без кода и session token.

Шестизначный постоянный код слабее длинного пароля. Для цехового терминала рекомендуется дополнительно ограничить сеть доступа VPN или IP производства; эти сетевые ограничения данным изменением не включаются. Изменение pepper отключит все существующие коды, поэтому его необходимо резервировать вместе с секретами.

## Развёртывание

Нужна миграция `20260909_0036`, согласованное обновление backend и frontend и выдача кодов действующим сотрудникам. Обычная авторизация покупателей и партнёров остаётся прежней. Производственные API теперь принимают только отдельную cookie-сессию терминала, старый identity Bearer для этих маршрутов больше не подходит.

Перед включением подготовьте коды для действующих сотрудников в защищённом канале. Не переключайте интерфейс без этого. Миграция только добавляет таблицы и не меняет заказы. При откате кода сохраняйте новые таблицы и историю, не запускайте downgrade на рабочей БД.

## Проверка и статус на 9 сентября 2026

Реализация подготовлена локально. Общий backend check прошёл с 439 тестами и 3 пропусками; после добавления ещё одной проверки отдельный набор авторизации прошёл 6/6. Frontend: 256 тестов, TypeScript, проверка ESLint изменённых модулей и production build прошли. Проверены отдельная cookie, отказ обычному identity API, Origin, выход, отзыв, истечение сессии, блокировка сотрудника и снятие роли. PostgreSQL-конкурентный тест существующего терминала пропущен без отдельной тестовой БД; онлайн-вход настоящего сотрудника не проверялся.

На рабочем сервере новый вход **не развёрнут**, миграция и выдача кодов не выполнялись. Сборка frontend Docker-образа оборвалась с EOF после исчерпания места на Mac и остановки Docker. Удалён только воспроизводимый `frontend/.next/cache` (120 МБ). Старый production не переключался. До продолжения нужно освободить достаточно дискового места для Docker-сборки, проверить доступ к серверу и подготовить список сотрудников/их участков.
