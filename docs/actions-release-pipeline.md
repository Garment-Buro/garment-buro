# Автоматическая публикация

- `develop` → `dev.garment-buro.ru` (окружение GitHub `development`).
- `main` → `garment-buro.ru`, `www`, `partner.garment-buro.ru`,
  `production.garment-buro.ru` (окружение `production`, общая рабочая БД).
- Ветка стенда называется `develop`, не `dev`: сохраняем существующее имя.
- Feature-ветки проходят CI, но сами ничего на рабочих доменах не меняют.
- Виджет — отдельный репозиторий `Garment-Buro/garment-buro-widget`, свой `main`.

В основном репозитории `Build and deploy` запускается при push в `develop`/`main`
и вручную через `workflow_dispatch` для этих же веток. CI проверяет код,
миграции и конкурентные операции на PostgreSQL. Затем Actions собирает Linux/amd64
образы, публикует их в GHCR с SHA коммита и выполняет серверный скрипт.

Сервер не собирает код. Приложения используют уже готовые образы. Секреты
приложений остаются в серверных `.env`; в GitHub Environments находятся SSH-секреты
для развёртывания. Временный `GITHUB_TOKEN` используется для pull из GHCR и удаляется
из Docker login после завершения задания.

## Порядок выпуска

1. Проверка конфигурации, блокировка параллельных выпусков на общем сервере.
2. Загрузка образов, резервная копия PostgreSQL, legacy SQLite, uploads,
   MinIO и конфигурации. Проверка читаемости дампа и gzip архива.
3. Назначение прав runtime-роли БД и миграции владельцем схемы.
4. Обновление только backend, frontend и включённых воркеров. Базы данных
   не пересоздаются; legacy-данные не импортируются повторно.
5. Проверка готовности API, страниц и внешних HTTPS-доменов.
6. Запись SHA и образов в `.release` только после серверной проверки.

При ошибке после переключения скрипт возвращает прежние образы и Compose.
Автоматического downgrade БД нет: миграции должны быть обратно совместимы.
Копирование файлов MinIO сохраняет оригиналы, но не заменяет согласованный
disaster-recovery backup при интенсивной записи; проверка архивов не является
полным тестом восстановления.

Проверка доменов из Actions после переключения дополнительно проверяет TLS и
маршрутизацию. Её ошибка делает workflow красным, но не откатывает БД/сеть.
Сбой сети SSH после запуска требует проверки `.release` и живых контейнеров
перед повтором; завершившийся удалённый выпуск не следует считать отменённым.

Флаги платежей, выплат и СДЭК автоматически не включаются. Личные коды выдаются
отдельно выбранным сотрудникам; секретные коды не выводятся в Actions.
