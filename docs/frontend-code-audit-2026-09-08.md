## Краткий вывод

Переписывать фронтенд целиком не нужно. В проекте уже есть полезное разделение `app → components → hooks → lib/api`, отдельные доменные типы, общий HTTP-клиент и архитектурные проверки. Но часть старых сценариев существует параллельно с новыми, а несколько контроллеров стали слишком большими.

Главный приоритет — не уменьшение количества строк, а устранение расхождений между интерфейсом и реальной системой: имитация входа в новом профиле, несовместимость оформления заказа с checkout v2, демонстрационные купоны и устаревшие правила отображения статусов. После этого имеет смысл дробить конструктор, корзину и производственный терминал.

Этот документ — отчёт, не выполненный рефакторинг. Исходный код, зависимости, настройки и сервер не изменялись. Выводы о серверных контрактах относятся к коду указанного коммита, а не к проверенному состоянию production/dev.

## 1. Функциональные расхождения, которые нельзя спрятать под рефакторинг

### F01. Новый профиль — отдельная демонстрационная реализация авторизации

Доказательства: [страница профиля](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/app/profile/page.tsx:10), [контроллер поверхности](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/hooks/unfinished/useUnfinishedSurface.ts:66), [обработчик входа](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/hooks/unfinished/useUnfinishedSurface.ts:345), [ProfilePanel](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/components/unfinished/ProfilePanel.tsx:165).

- `/profile` открывает `UnfinishedSurface`, а не реальный `AuthenticatedDashboard`.
- `isProfileSignedIn` хранится в локальном `useState`. `handleProfileLoginAction` сначала переключает шаг, затем устанавливает `true` без проверки OTP через API. Эта логика не ограждена `isMockDataEnabled()`.
- Изменение имени/почты/телефона меняет только локальное состояние. Кнопки повторной отправки, удаления аккаунта и отправки сообщения в поддержку не имеют соответствующих обработчиков.
- Заказы берутся из `profileOrderFixtures`: при выключенных моках список пустой, а не загруженный из API. При включённых моках раскрытая карточка содержит жёстко заданные товары, суммы и получателя.

Это не доказательство обхода backend-авторизации: серверную сессию такая кнопка не создаёт. Проблема в том, что пользователь видит имитацию успешного входа и несохранённые данные.

Предложение: оставить нынешнюю оболочку и нахлёст панели, но подключить `useEmailAuthentication`, `authStore`, существующие `useAuthSettings` и `useAuthOrders`. Вынести демонстрационные карточки из рабочего потока. В `useUnfinishedSurface` оставить только вкладки, переходы, сохранённые дизайны и состояние панели.

Критерий готовности: неправильный код не открывает профиль; правильный создаёт реальную сессию; данные и заказы приходят с сервера; неподключённые действия не выглядят рабочими.

### F02. Два независимых checkout расходятся между собой и с новым backend

Доказательства: [useCheckout](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/hooks/checkout/useCheckout.ts:101), [useCartActionCheckout](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/hooks/cart/useCartActionCheckout.ts:78), [первый API-клиент](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/lib/api/checkout.ts:15), [второй API-клиент](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/lib/api/orders.ts:14), [схема backend](/Users/mikitaliudchyk/WorkProjects/garment-buro/backend/app/modules/orders/schemas.py:93), [router checkout](/Users/mikitaliudchyk/WorkProjects/garment-buro/backend/app/modules/checkout/router.py:96).

Оба клиента делают `POST /api/orders`, но:

1. Отправляют старые `cart_items` и `total_price`. Checkout v2 требует `items` и `claimed_total_price`. Локальная проверка характерного frontend-payload через текущую `OrderCreationCommand` подтвердила ошибки `missing` для этих двух полей.
2. Ни один клиент не отправляет `Idempotency-Key`; общий HTTP-клиент тоже не добавляет его. После исправления тела это остаётся самостоятельным препятствием: v2 требует ключ.
3. Нижняя корзина по умолчанию выбирает `qr`, а сервер при `ORDER_MODERATION_ENABLED=true` разрешает для управляемого заказа только `card`.
4. Разнятся валидация, получатель, расчёт доставки и обработка ошибок. Полноэкранный checkout проверяет наличие строк, нижняя корзина использует `validContact`; первый может сформировать доставку с нулевой ценой до получения тарифа, второй требует расчёт.

Условие проявления несовместимости: `CHECKOUT_V2_ENABLED=true`. Сначала старое тело запроса получит 422; одно лишь добавление ключа не исправит контракт. На legacy-backend поведение может быть другим — состояние работающего сервера не проверялось.

Предложение: единые `CheckoutDraft`, `CheckoutCommand`, `CheckoutResult`, валидатор и преобразование в backend-команду в `lib/checkout`; один API-метод; один контроллер отправки с двумя UI-представлениями. При переходе отдельно согласовать передачу покупателя и отличающегося получателя, а не потерять эти данные в адаптере.

Ключ запроса должен переживать неопределённый сетевой исход и повтор **той же** команды. Нельзя просто генерировать новый UUID на каждый повтор. Нужны сохранённое намерение/идентификатор, неизменяемое содержимое команды и понятный сценарий проверки результата. Не сохранять все персональные данные бессрочно в localStorage ради этого механизма.

Критерий готовности: оба интерфейса проходят один контрактный тест; повтор после таймаута не создаёт новое намерение; способы оплаты соответствуют активной серверной политике; доставка и получатель одинаково валидируются.

### F03. Демонстрационные скидки участвуют в рабочем расчёте

Доказательства: [константы купонов](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/lib/cart/constants.ts:37), [расчёт суммы](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/lib/cart/utils/cartAction.ts:19), [подключение купонов без mock-флага](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/components/cart/CartExpandedContent.tsx:179), [пересчёт итогов](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/hooks/cart/useCartActionCheckout.ts:58).

В интерфейсе купоны обещают `10%`, но любой выбранный купон вычитает фиксированные 540 ₽. Значение попадает в отправляемый `total_price`; серверная проверка права на купон не вызывается. Текущий v2 backend считает сумму как товары плюс доставка и проверяет совпадение с заявленной суммой: это будущий конфликт после устранения F02, а не подтверждённая возможность списать меньше денег.

Также в общем helper осталась фиксированная курьерская доставка 547 ₽. Новый hook заменяет её реальным тарифом, поэтому не следует утверждать, что именно 547 ₽ всегда отправляется в оплату. Но два источника расчёта всё равно вводят в заблуждение.

Предложение: не показывать рабочие купоны до появления серверного контракта проверки/расчёта. Отделить демонстрационные данные от расчёта checkout, получать подтверждённые суммы с сервера. Удалять фиксированную доставку только после проверки всех вызывающих мест и тестов.

### F04. Производственный UI блокирует разрешённое запоздалое подтверждение отправки

Доказательства: [orderBlocked](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/lib/production/workflow.ts:6), [передача blocked в действия](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/components/production/ProductionTerminal.tsx:275), [разрешение backend для dispatch](/Users/mikitaliudchyk/WorkProjects/garment-buro/backend/app/modules/production/service.py:62).

`orderBlocked` запрещает все действия, когда `order_status !== 'processing'`. Новый backend допускает `dispatch` и при `shipped/completed`: CDEK polling может обновить заказ раньше, чем сотрудник подтвердит передачу. В таком состоянии мешок ещё может ждать подтверждения в `packed`, но UI передаёт `busy || blocked` и выключает действие.

Предложение: заменить общий запрет для всех команд на чистую функцию доступности конкретного действия с причиной отказа. Сохранить ограничения роли, оплаты и остановленного производства. Не открывать редактирование производства целиком для отправленных заказов.

Критерий готовности: тест `packed + paid + shipped + shipping-role` разрешает только допустимое подтверждение, а неподходящие команды остаются закрыты.

### F06. Конструктор: не переносить монолит в ещё один hook

У [useConstructorPageController](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/hooks/constructor/useConstructorPageController.ts:51) 15 `useState`, 11 `useRef` и 75 полей в возвращаемом объекте. `ConstructorWorkspace` принимает весь `ReturnType` контроллера, поэтому UI сильно связан с внутренним устройством состояния.

Рекомендуемые границы:

- Чистые операции над документом дизайна: добавить/изменить/удалить элемент, переключить сторону, восстановить выбранную посадку. При необходимости reducer, но без обязательного переноса всего в глобальный store.
- `useConstructorRestore`: отдельные адаптеры черновика и позиции корзины, общий результат восстановления. Сейчас эффекты на строках 110 и 153 повторяют вычисление следующих ID, восстановление декораций и серию setters.
- `useConstructorDecorations`: импорт изображения, добавление/изменение текста, лимиты и ошибки загрузки.
- `useConstructorPanel`: раскрытие, подписи, действия жестов; операции сохранения оставить отдельно.
- Явные небольшие props для сцены, панели и редакторов вместо передачи всех 75 полей.

Отдельный обнаруженный риск: [жест ручки панели](/Users/mikitaliudchyk/WorkProjects/garment-buro/frontend/hooks/constructor/useConstructorPageController.ts:431) устанавливает глобальные `pointermove/pointerup`, снимая их только на `pointerup`. Нет симметричной очистки по `pointercancel` и размонтированию для этого обработчика. При разделении нужен один lifecycle жеста с обязательной очисткой; визуальные пороги менять не требуется.
