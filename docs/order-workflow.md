# Жизненный цикл заказа: холд, модерация, производство, СДЭК

## Сценарий

Новые заказы при `ORDER_MODERATION_ENABLED=true` оформляются только с ручным
подтверждением платежа (`capture=false`). Клиент не может обойти это поле запроса.
СБП в этом сценарии отклоняется до сохранения заказа: ЮKassa не поддерживает
двухстадийный СБП. Старые заказы и отдельные платёжные интеграции не переводятся
на новую схему миграцией.

| Проверенное событие | Внутренний workflow | Этап для клиента |
| --- | --- | --- |
| Заказ сохранён, покупатель ещё не авторизовал оплату | awaiting_payment | Нет производственного этапа |
| ЮKassa подтвердила waiting_for_capture и expires_at | moderation | Модерация |
| Сотрудник подтвердил заказ, capture ещё обрабатывается | capture_pending | Модерация |
| Подтверждено succeeded, зафиксированы склад и outbox | production | Производство |
| Подтверждена физическая передача отправления | shipped | Передано в СДЭК |
| Авторизованный GET СДЭК вернул DELIVERED | completed | Выполнено |

`capture_pending` — ещё не производство. `waiting_for_capture` — деньги
заблокированы, но ещё не списаны. Нажатие подтверждения сохраняет решение и задачу,
не означает успешное списание. При отказе модератора создаётся задача отмены холда;
заказ отменяется и резерв освобождается только после подтверждённого `canceled`.

Технические ошибки хранятся отдельно. Неподтверждённый исход не превращается в
успех или в доказанный отказ. В частности, списание без решения модератора
сохраняется в платежах, попадает в `attention/captured_without_approval` и не
запускает производство. Такой случай требует ручной проверки/возврата, а не
повторного списания. Автоматический возврат уже списанного платежа здесь не вводится.

Клиентские чтения возвращают `customer_stage`, `customer_stage_label`,
`workflow_state`, реальный `cdek_number`, `cdek_uuid`, `cdek_status`.
Старые `status`/`payment_status` сохранены для совместимости терминала и CRM.
UI нужно отображать `customer_stage_label`; этот этап работы не меняет верстку.

## Что обеспечивает сохранность

- PostgreSQL — единственный источник состояния заказа, неизменяемых позиций,
  решений и задач. Redis не хранит единственную копию заказов.
- Заказ + платёжное намерение + задача восстановления создаются одной транзакцией
  до обращения к ЮKassa. Решение модератора + capture/cancel-задача также атомарны.
- `order_workflows`: уникальный заказ и платёжная попытка; `order_workflow_events`:
  последовательный журнал версий; `order_workflow_jobs`: уникальные цели и FK,
  состояние, срок аренды, поколение и токен владения, ошибка и время следующей попытки.
- Worker использует `FOR UPDATE SKIP LOCKED`, аренду на 5 минут и fencing token:
  старый процесс не может подтвердить задачу, уже переданную новому процессу.
- Внешняя доставка задач — at least once. От повторных эффектов защищают сохранённые
  ключи ЮKassa, неизменяемое тело запроса, проверки состояния и уникальные ограничения.
  Это не обещание распределённого exactly once.
- Перед повторением capture/cancel сначала выполняется GET платежа. После 23 часов
  от первой операции POST больше не повторяется; продолжается сверка/ручной разбор.
  Ключ провайдера не пересоздаётся. Истёкшее окно создания платежа остаётся `unknown`,
  а не `failed`: нельзя предложить клиенту ещё одно потенциальное списание.
- Управляемый заказ не получает новую попытку оплаты через старый customer retry.
  Восстанавливается существующая попытка. Для доказанного отказа оператор разбирает
  причину; повторная покупка после отмены оформляется отдельным заказом.
- Retry: 30 секунд, экспоненциальная задержка до 30 минут + jitter; после 12 ошибок
  задача остаётся в `dead` и доступна для диагностики/явного возобновления.
- Подтверждение оплаты, расход резерва и существующий fulfillment outbox атомарны.
  Уникальные задания CRM, письма и накладной предотвращают повторную передачу заказа.
- Старый таймер резервов не отменяет управляемые заказы. Резерв удерживается до
  выяснения результата платежа, включая неопределённые исходы. Поэтому dead-задачи
  и отсутствующие платежные ответы обязательно требуют внимания оператора.
- Webhook ЮKassa сохраняется в существующий inbox, затем проверяется GET платежа.
  Существующий reconciler восстанавливает пропущенные webhook. Успешные проверки
  длительного холда не расходуют бюджет ошибок; `expires_at` определяет срок холда.

## СДЭК

Накладная создаётся существующей защищённой очередью после подтверждённого списания.
Создание накладной (`ACCEPTED`, `CREATED`) не считается передачей посылки.
Физическую передачу подтверждает сотрудник shipping с трек-номером существующего
отправления этого заказа либо статус приёмки/движения из авторизованного GET СДЭК.
Терминал проверяет совпадение номера; запоздалое подтверждение передачи допустимо,
если polling уже продвинул статус заказа.

Worker обнаруживает отправления с UUID, сохраняет отдельную задачу отслеживания,
опрашивает их каждые 5 минут. Проверяются UUID, номер заказа ИМ, трек и дата статуса.
Статусы сортируются по `date_time`, а не позиции в массиве. Недатированные и чужие
ответы не меняют этап. Старые ответы не откатывают заказ. `ACCEPTED_AT_PICK_UP_POINT`
не завершает заказ; `NOT_DELIVERED`/`REMOVED` требуют разбирательства, не означают
успешную доставку. Только `DELIVERED` переводит заказ в «Выполнено».

Неизвестный результат создания накладной не приводит к автоматическому повторному
POST. Если UUID не удалось сохранить, найдите отправление в кабинете СДЭК по
сохранённому номеру ИМ и используйте `recover-cdek`: команда выполняет только GET,
проверяет принадлежность заказа, сохраняет связь и задачу отслеживания.
Возвраты и повторные отправления требуют отдельного бизнес-процесса и здесь
автоматически не создаются. Webhook СДЭК не требуется: polling не зависит от него.

## Команды оператора (из backend)

Доступ на запись: активный пользователь с `payments.manage`. Укажите его реальный ID.
Не выдавайте эту роль покупателю или производственным участкам. Нового API модерации нет.
Сервис `OrderModerationService.decide()` сам не коммитит: вызывающий backend сохраняет
решение транзакцией. CLI коммитит решение и задачу, сетевые POST делает только worker.

```sh
python -m scripts.moderate_order list --limit 100
python -m scripts.moderate_order list --before-id 100
python -m scripts.moderate_order list --order-id 123
python -m scripts.moderate_order approve --order-id 123 --version 2 --actor-id 7 --key reviewed-order-123-v2 --note 'Макет, размеры и комплектность проверены'
python -m scripts.moderate_order reject --order-id 124 --version 2 --actor-id 7 --key rejected-order-124-v2 --note 'Невозможно изготовить макет'
```

Версии/ID в примерах условные: брать из `list`. Повтор той же команды — replay.
Другое решение/содержимое с тем же ключом или устаревшая версия отклоняются.
Подтверждение при остатке холда менее 2 минут запрещено.

После исправления причины сбоя можно явно вернуть просмотренное поколение dead-задачи:

```sh
python -m scripts.moderate_order requeue --family workflow --job-id 12 --generation 3 --actor-id 7
python -m scripts.moderate_order requeue --family reconciliation --job-id 8 --generation 12 --actor-id 7
python -m scripts.moderate_order requeue --family fulfillment --job-id 10 --generation 8 --actor-id 7
python -m scripts.moderate_order recover-cdek --order-id 123 --version 4 --actor-id 7 --provider-uuid UUID_FROM_CDEK
```

Requeue не меняет ключи/сроки провайдера, не удаляет журнал попыток fulfillment,
не снимает защиту от двойного списания. Без устранения причины задача снова остановится.
После 20 попыток fulfillment требуется отдельный разбор обработчика, а не очистка истории.
Отклонённые/чужие webhook повторять не требуется: восстановление идёт через
авторизованную сверку известного платежа.

## Запуск и эксплуатация

1. Резервная копия PostgreSQL и приватного MinIO, проверка восстановления в отдельном
   окружении. Миграция `20260908_0035`; не делать downgrade с рабочими данными.
2. Настроить существующие checkout, payment creation/management/reconciliation,
   fulfillment outbox/CRM, CDEK credentials/creation. Секреты только в серверном `.env`.
3. Поднять worker **до** включения приёма новых управляемых заказов. Compose-профили:
   `order-workflows`, `payment-reconciliation`, `payments` (если используются webhook),
   `fulfillment`, `cdek`, `notifications` (при включённых письмах). Существующие
   database/migrate dependencies и restart policy наследуются от backend-common.
4. `ORDER_MODERATION_ENABLED=true` включает новую политику только для новых checkout.
   `CDEK_TRACKING_ENABLED=true` включает сверку доставки. По умолчанию оба выключены.
   Их нельзя включать без тестирования в тестовом магазине ЮKassa/стенде СДЭК.
5. Проверить не только HTTP 200, но холд → approve → capture → CRM-задачу, отмену,
   таймаут после принятого платежа и восстановление после перезапуска worker.

```sh
python -m scripts.process_order_workflows --once --max-items 100
python -m scripts.process_order_workflows
python -m scripts.reconcile_payments
python -m scripts.process_fulfillment_jobs
python -m scripts.process_cdek_shipments
```

Для масштабирования достаточно дополнительных worker с общей PostgreSQL.
Kubernetes, Kafka и RabbitMQ не обязательны для этого объёма: корректность здесь
дают транзакционный outbox, идемпотентность и сверка, а не название брокера.

Перед боевым включением подключить оповещения по dead/unknown, возрасту pending,
просроченным lease, отсутствию свежей сверки и холдам с остатком <4 часов;
`moderate_order list` даёт эти данные без адресов/телефонов. Проверять также существующие
очереди писем и дисковое место. В этом изменении **не устанавливаются внешние алерты,
резервное копирование или HA PostgreSQL на сервере**. Без мониторинга dead-задачи
сохранены, но могут ждать человека. Один VPS не даёт защиты от утраты диска:
нужны offsite backup + WAL/PITR, а для меньшего простоя — реплика/failover.
