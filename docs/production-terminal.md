# Производственный терминал Garment Buro

## Что перенесено

Источник: `garment-buro-production-flow-code-2026-09-05` — самостоятельный HTML-прототип с демонстрационными массивами, localStorage и имитацией QR/печати. Его сценарии перенесены в основной Next.js/FastAPI-проект. Демоданные, изображения демонстрационных изделий и настройки стороннего хостинга не импортированы.

Точка входа: `/production`. Целевой домен: `production.garment-buro.ru`, отдельный PWA-манифест. Корень этого хоста перенаправляется на терминал. Это интерфейс к **основной базе заказов**, не новая независимая CRM и не копия dev-базы. Kubernetes для этого не требуется.

Рабочие участки: входящие / технолог, комплектовка, раскрой, DTF, нанесение, пошив, ВТО, ОТК, упаковка, отправка. Все сотрудники видят цикл, действия ограничены ролью; технолог — руководитель всего цикла. Обычные покупатели и партнёры доступа не имеют.

## Данные и гарантии

| Данные | Хранение и контроль |
| --- | --- |
| Оплаченный заказ | Существующие `orders`, `order_items`, подтверждённая оплата и fulfillment-outbox → CRM intake. Терминал сам не создаёт «оплаченные» заказы. |
| Физические вещи | `crm_production_units`: отдельная запись на каждую штуку. Проверяется соответствие **всех** позиций и количеств исходному заказу. |
| Один заказ — один мешок | `production_bags`, уникальный CRM-проект, общий статус и версия. |
| Задание вещи | `production_specifications`: версионный снимок заказа, кастомизации, техкарты/размера, маршрута, комплектующих, мест хранения, указаний, проверок ОТК. Контрольные SHA256; старые версии не перезаписываются. |
| Оригиналы | Существующее приватное CRM-хранилище MinIO + `crm_file_attachments`; связи `production_specification_files` с FK RESTRICT. Проверяются готовность, принадлежность, размер, SHA256 и адрес/версия объекта. URL для скачивания выдаётся временно, с проверкой прав и аудитом. |
| Физические подтверждения | `production_work_items`: документы технолога, чек-лист комплектности, печать DTF, вложение DTF, текущий этап, проблема. |
| Кто / когда / что сделал | `production_events`: сотрудник, вещь, версия мешка, параметры команды, время, ссылка на спецификацию. Последние 100 событий показаны в UI; база хранит всю историю. |
| Завершение и доставка | Закрытие вещей и CRM-проекта через существующие сервисы, трек-номер и подтверждение фактической передачи перевозчику; статус исходного заказа `shipped` и его история обновляются в той же транзакции. |

Нет localStorage для производственных данных, оптимистического «сохранено» или очереди физических операций офлайн. Команды требуют `expected_version` и `Idempotency-Key`. Изменение, версия и событие фиксируются одной транзакцией. PostgreSQL блокирует заказ → проект → вещи. Повтор того же ключа возвращает прежний результат; другой сотрудник со старой версией получает 409. При сетевой неопределённости интерфейс просит обновить заказ и проверить журнал.

Старые CRM-команды планирования/смены статуса не обходят новый маршрут: для взятых в терминал проектов/вещей они заблокированы. Уже начатые старым способом CRM-проекты автоматически не переносятся — требуется отдельная сверка и перенос, чтобы не выдумывать этапы задним числом.

## Правила движения

1. Технолог связывает каждую вещь с опубликованной техкартой и размером производственной модели, задаёт маршрут, комплектующие и указания. Для раскроя нужны сохранённые лекала; для нанесения — сохранённые файлы печати. ОТК и упаковка обязательны. Каталожный товар должен быть связан с производственной моделью в CRM-справочнике.
2. Сверяет с заказом текст, шрифты, размеры, стороны, мерки и все нанесения; фиксирует итоговые производственные параметры в указаниях. Оригиналы загружаются отдельно от экранного preview конструктора. QR и сопроводительные листы формируются реальным генератором. Кнопка печати открывает диалог браузера, а не обещает успешную работу принтера. Фактическую подготовку документов сотрудник подтверждает отдельно.
3. Комплектовщик отмечает **реальное вложение** каждой комплектующей. DTF может быть ещё не готов — это не удерживает остальной маршрут на комплектовке.
4. Раскрой подтверждает заворачивание кроя в подготовленный технологом лист с QR. Печатник отдельно подтверждает печать/нарезку и может напечатать QR мешка для пакета DTF. Только комплектовщик подтверждает вложение DTF в мешок.
5. Вещь с DTF не проходит нанесение и следующий пошив без подтверждённого вложения. Вещи без DTF проходят собственный маршрут. Когда доступные раскрой/пошив закончены, **весь мешок** возвращается на стол ожидания DTF; после вложения — обратно в цех.
6. Открытая проблема блокирует продвижение вещи. Технолог фиксирует решение или возвращает её на предыдущий этап; переделка раскроя/нанесения сбрасывает подтверждения DTF. Закрытая вещь не переоткрывается незаметно.
7. ОТК требует всех проверок. Упаковка всего мешка — только после завершения всех вещей. Существующие ограничения активных резервов материалов сохраняются. Отправка требует получателя, телефона, города, адреса/ПВЗ, трек-номера и комментария передачи.

Комплектующие с количеством/ячейкой — производственное задание и контроль вложения, **не автоматический складской расход всей фурнитуры**. Имеющийся CRM-регистр тканей продолжает работать отдельно; активные резервы необходимо штатно списать/освободить. Автоматическая генерация лекал, RIP/режимов печати и создание новой заявки СДЭК этим модулем не выполняются. Нельзя считать preview конструктора готовым печатным оригиналом.

## API и доступ

- `GET /api/production/me`, `/projects?cursor=...&limit=30`, `/projects/{id}`.
- `POST /api/production/projects/{id}/commands` — все переходы и подтверждения.
- `POST /api/production/units/{id}/files?slot=...` — технолог; неизменяемые слоты, ограничение размера/формата.
- `GET /api/production/files/{id}/download` — технолог либо соответствующий участок для закреплённого файла.
- `GET /api/qr-code?surface=production&path=/production?...` — QR содержит только ссылку/идентификаторы, **не доступ к заказу**. После сканирования всё равно нужна авторизация.

Роли: `production_tech`, `production_kit`, `production_cut`, `production_dtf`, `production_application`, `production_sewing`, `production_press`, `production_qc`, `production_packing`, `production_shipping`. Они не получают широкие CRM/admin-права. Уже существующий `admin` имеет все производственные разрешения. Для выдачи роли существующему активному пользователю используется `backend/scripts/bootstrap_role.py`: сначала `--email ... --role production_cut` для проверки, затем явные `--apply --expect-user-id ...`. Выдача записывается в аудит. Не используйте общий аккаунт для всех станков — иначе журнал не различает сотрудников.

## Включение на сервере

8 сентября выполнен перенос на отдельный rootless production-стек, подключены TLS и `production.garment-buro.ru`, назначен доступ владельцу. Актуальные проверки, ограничения и резервные копии описаны в [отчёте о переключении](production-cutover-2026-09-08.md). Ниже сохранён порядок действий для последующих развёртываний; это не список невыполненных шагов текущего запуска.

Порядок после восстановления доступа:

1. Подтвердить DNS A/AAAA, реальный основной upstream и активную разновидность nginx. Не направлять терминал на dev: там другая база. Не применять скрипт переустановки всех публичных хостов ради одного домена.
2. Сделать согласованные резервные копии PostgreSQL **и приватного MinIO**, проверить возможность восстановления. Секреты и `.env` — только на сервере, права 0600, вне Git.
3. Развернуть проверенную ревизию backend/frontend в выбранное окружение с миграцией `20260908_0034`. Не включать банковские выплаты или другие необязательные интеграции попутно.
4. В приватной конфигурации нужны `IDENTITY_API_ENABLED`, `CRM_API_ENABLED`, `CRM_WRITES_ENABLED`, `CRM_FILES_ENABLED`, `FULFILLMENT_OUTBOX_ENABLED`, `FULFILLMENT_CRM_ENABLED`, MinIO и их штатные зависимости/миграционные fingerprints. Добавить production-origin в `CORS_ORIGINS`, иначе cookie-refresh может получить 403. Для frontend включить существующий `NEXT_PUBLIC_IDENTITY_SESSION_V2_ENABLED=true` при сборке.
5. Запустить штатный fulfillment-worker; выполнить `python -m scripts.reconcile_crm` и проверить оплаченные заказы, проекты, количество вещей, справочники, файлы и остатки. Не создавать фиктивные проекты вручную ради наполнения очереди.
6. Задать `PRODUCTION_PUBLIC_BASE_URL=https://production.garment-buro.ru`, назначить подтверждённые пользователем роли. Включить `PRODUCTION_TERMINAL_ENABLED=true` только после проверки зависимостей. По умолчанию выключен; некорректная комбинация флагов не допускается настройками.
7. Получить **отдельный** сертификат этого домена через существующий ACME-webroot, не переписывая общий сертификат сайта. Подготовлены два **неактивных** примера: `deploy/nginx/production-host.conf.example` для nginx хоста и `production-docker.conf.example` для legacy Docker nginx. Использовать только подходящий вариант; сначала HTTP challenge, затем TLS-блок после появления файлов сертификата. Проверить `nginx -t` перед reload. Обеспечить renew/reload существующим механизмом сервера.
8. Приёмка: HTTPS/SNI именно нового хоста, `/` → `/production`, отдельный manifest, вход/refresh, покупатель → 403, роль участка → только свои действия, оплаченный контрольный заказ из **нужной базы**, оригиналы из MinIO, QR на реальном сканере и печать на фактическом принтере. Затем провести согласованный контрольный заказ по цеху.

Для dev-проверки тот же терминал доступен как `/production` на dev-хосте при включённых backend-флагах в dev. QR-origin должен соответствовать выбранному окружению. Никогда не соединять dev-терминал с боевой БД ради демонстрации.

## Эксплуатация

Резервируйте БД, все версии оригиналов MinIO и ключи шифрования по принятому регламенту. Не включайте lifecycle-удаление закреплённых оригиналов. Одного дампа БД недостаточно. Восстановление проверять на отдельном окружении: целостность ссылок, SHA256/размеры файлов, состав каждой вещи/мешка и история переходов. Веб-интерфейс не может сам гарантировать физическую сохранность складских вещей или исправность принтера.

Миграция добавляет таблицы, но не заполняет выдуманными данными незавершённые старые заказы. Откат: сначала отключить флаг и интерфейс, сохранить данные; не выполнять downgrade с рабочей историей — он удаляет новые таблицы. Права сотрудников при downgrade намеренно не удаляются автоматически.
