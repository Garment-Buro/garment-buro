## Предыдущий этап — backup без возобновления записей до миграций

Прежние workers и API/frontend останавливаются до резервной копии. Backup
возвращает только MinIO; приложения остаются остановленными до кандидата.
После backup/init повторно проверяется отсутствие writers. Ошибка архива или
INT/TERM возвращает прежние контейнеры; неожиданный writer блокирует миграцию.
Тем самым устранён зазор для записей между архивом и переключением схемы.

Отдельная Linux-сборка проверяет прежний зафиксированный снимок приложений;
результат и HTTP пока ожидаются. Она не проверяет новый порядок deploy-скрипта.

Окно обслуживания включает весь backup. Внешние writers, реальный restore,

## Архитектурные решения

- Next.js отвечает за маршруты, серверный рендер и интерфейс. Клиентский HTTP
  проходит через `frontend/lib/api/http.ts` и same-origin `/api`. Внешние
  платёжные, банковские и доставочные операции выполняет backend.
- FastAPI: маршруты проверяют вход и права; сервисы реализуют операции;
  repositories формируют запросы; модели и Alembic задают схему.
- PostgreSQL — источник пользовательских и бизнес-данных: каталог, избранное,
  сохранённые проекты, корзины, заказы, сотрудники, производство и партнёры.
  localStorage пригоден для предпочтений интерфейса и восстановления
  несинхронизированного ввода, но не единственный источник сохранённых данных.
- Redis — временный кэш, ограничение частоты и координация там, где нужны
  соответствующие гарантии. Отсутствие Redis у запроса само по себе не ошибка.
  Кэш не заменяет основную БД; записи требуют TTL и понятной инвалидации.
- S3/MinIO хранит файлы. JSONB для структурированной кастомизации внутри БД
  допустим; файлы JSON не служат основной базой пользовательских данных.
- Запуск не создаёт таблицы: схему меняет отдельный Alembic job. Модули не
  подключаются к внешним сервисам при импорте. Ресурсы принадлежат lifespan,
  освобождаются при частичном запуске и остановке.
- Диагностика: структурированные логи stdout, UTC, request ID, шаблон маршрута,
  метод, статус и время. Ни тело запроса, ни query string, ни токены не входят
  в access event. Readiness проверяет действительно необходимые зависимости.
- Текущий дизайн и рабочие бизнес-процессы сохраняются при замене реализации.
  Обратная совместимость допустима только на промежуточных этапах, не как
  конечное состояние релиза.

## Подтверждённая исходная точка

1. `backend/app/main.py` безусловно импортирует `backend/main.py`. Старое
   приложение создаёт SQLite engine, таблицы и каталог uploads при импорте;
   в конце factory монтируется на `/`.
2. Новые домены уже существуют; удалять их и писать всё заново не требуется.
   Factory одновременно собирает сервисы, управляет их ресурсами и регистрирует
   маршруты. В lifespan несколько вложенных finally; отдельные ошибки shutdown
   могут пропустить последующие операции освобождения.
3. `docker-compose.local.yml` запускает PostgreSQL/MinIO, но новые catalog,
   identity, cart, orders, CRM по умолчанию выключены. Документация запуска без
   Docker использует другой путь venv, чем существующий `backend/.venv`.
4. `serviceFavoritesStore.ts` сохраняет строковые preview IDs только в
   localStorage. Новая главная питается `serviceHomeData.ts`, отдельно от
   серверного каталога. Это реальная демо-логика, не постоянное избранное.
5. Общий frontend HTTP-клиент и тест границ уже существуют. Не обнаружено
   основания переносить все запросы заново; нужно проверить исключения,
   повторные загрузки, жизненный цикл и ошибки.
6. `/admin/editor` и прямой `/order/[id]` ещё используют LandingPage →
   CatalogScreen. Удаление редактора должно также убрать связанные ссылки,
   код редактирования и ненужные настройки, а заказ — получить текущий фон.
